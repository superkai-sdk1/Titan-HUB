# Тестирование Titan HUB

В проекте **отсутствуют** автоматические юнит-, интеграционные и e2e-тесты. Ни в одном из `package.json` воркспейсов нет зависимостей от тестовых фреймворков (vitest, jest, mocha, playwright, cypress) и нет скриптов `test`. Это осознанный компромисс на ранней стадии продукта: качество держится на трёх рубежах — строгой типизации TypeScript, успешной сборке всех пакетов и ручной проверке на реальном устройстве.

## Контроль качества: статический анализ и сборка

### Проверка типов (`type-check`)

Все пакеты и приложения используют TypeScript с опцией `"strict": true`. Базовый конфиг (`packages/config/tsconfig/base.json`) дополнительно включает:

- `"exactOptionalPropertyTypes": true` — нельзя присвоить `undefined` там, где поле опционально, но тип не включает `undefined` явно.
- `"noUncheckedIndexedAccess": true` — обращение по индексу к массиву или объекту возвращает `T | undefined`, что вынуждает обрабатывать граничные случаи.
- `"noImplicitOverride": true` — переопределение метода класса требует явного `override`.

Запуск проверки по всем воркспейсам через Turborepo:

```bash
pnpm -r type-check
```

Что ловит: несоответствие типов в аргументах и возвращаемых значениях роутеров Hono, неверные поля при формировании объектов Drizzle, несовместимость типов между `@titan/types`, `@titan/database` и потребителями.

Запуск только для API (`apps/api`):

```bash
pnpm --filter @titan/api type-check
```

Запуск только для веб-фронтенда (`apps/web`):

```bash
pnpm --filter @titan/web type-check
```

### Сборка (`build`)

Успешная сборка — второй рубеж контроля.

**`@titan/api` (tsc):**

```bash
pnpm --filter @titan/api build
```

`tsc` компилирует `src/` в `dist/` с `"module": "NodeNext"` и копирует SQL-миграции (`src/migrations/sql/`) в `dist/migrations/sql/`. Сборка падает при любой типовой ошибке, недостающем импорте или синтаксической проблеме.

**`@titan/web` (Next.js build):**

```bash
pnpm --filter @titan/web build
```

`next build` строит оптимизированный standalone-бандл. Падает при: ошибках TypeScript в компонентах/роутах, некорректных импортах `@titan/types`/`@titan/ui`, невалидных Server/Client Component границах.

**Полная сборка монорепо:**

```bash
pnpm build
```

Turborepo запускает пакеты в правильном порядке с учётом зависимостей (`"dependsOn": ["^build"]`): сначала `@titan/config` → `@titan/types`, `@titan/auth`, `@titan/database` → приложения.

## Ручная верификация (E2E на реальном устройстве)

Продакшн-окружение — https://titanpos.ru. Основной сценарий проверки выполняется на реальном смартфоне (iOS Safari / PWA) и включает следующие прогоны.

### Склад: полный цикл движения товара

Инвариант: `inventory.stock_quantity == SUM(delta) FROM stock_movements WHERE item_id = X`

Последовательность проверки:

1. **Начальный остаток** — открыть `/manage/inventory`, зафиксировать `stock_quantity` для тестового товара.
2. **Продажа** — в POS (`/pos`) добавить товар в чек и провести оплату. Убедиться, что остаток уменьшился на проданное количество.
3. **Возврат** — выполнить возврат по чеку. Убедиться, что остаток восстановился.
4. **Поставка (приёмка)** — создать поставку через `/manage/inventory` → вкладка «Поставки», провести через «Применить». Убедиться, что остаток вырос на количество из поставки; проверить пересчёт средневзвешенной себестоимости (WAC).
5. **Ревизия** — создать ревизию через вкладку «Ревизия», ввести фактические остатки, применить. Убедиться, что `stock_quantity` выставился в указанное значение.
6. **Списание / ручная корректировка** — через ручную правку остатка. Убедиться, что движение типа `write_off` или `adjustment` записано в журнал.

**SQL-проверка инварианта остатка** (выполнять на проде после прогона):

```sql
-- Сравнение кэша inventory с суммой по журналу.
-- Расхождение = проблема: должны возвращаться 0 строк.
SELECT
  i.id,
  i.name,
  i.stock_quantity AS cached_qty,
  COALESCE(SUM(sm.delta), 0) AS ledger_sum,
  i.stock_quantity - COALESCE(SUM(sm.delta), 0) AS drift
FROM inventory i
LEFT JOIN stock_movements sm ON sm.item_id = i.id
WHERE i.track_stock = true
GROUP BY i.id, i.name, i.stock_quantity
HAVING i.stock_quantity != COALESCE(SUM(sm.delta), 0);
```

### Балансы (депозиты / долги)

1. Открыть `/manage/balances`, зафиксировать баланс клиента.
2. Пополнить депозит через `/manage/clients` → пополнение баланса.
3. Убедиться, что `profiles.balance` изменился ровно на введённую сумму; транзакция типа `deposit` появилась в `transactions`.
4. Провести оплату чека с депозита. Убедиться, что баланс уменьшился, транзакция типа `payment` создана.
5. Проверить граничный случай: попытка превысить лимит долга (`app_settings.max_client_debt`) — система должна вернуть ошибку.

### Смены и касса

1. Открыть смену через `/manage/shifts` — ввести стартовый остаток наличных.
2. Провести несколько оплат наличными в POS.
3. Выполнить внесение и изъятие из кассы.
4. Проверить «Живой остаток» — значение должно совпадать с расчётом:
   `cashStart + наличные платежи + внесения − изъятия − зарплаты − возвраты наличными`.
5. Закрыть смену: ввести фактический остаток. При расхождении — убедиться, что система требует причину и создаёт корректирующую `cashOperation`.

### Лояльность

1. Создать тестовую скидку в `/manage/loyalty` → «Скидки».
2. Применить её к чеку в POS.
3. Проверить, что итоговая сумма чека снизилась корректно.
4. Проверить начисление бонусных баллов клиенту и их списание при следующей оплате.
5. Создать сертификат, оплатить им чек, убедиться, что баланс сертификата уменьшился.

## Рекомендации по внедрению автоматических тестов

> Раздел содержит **рекомендации** — описанное ниже не реализовано в проекте на данный момент.

### Юнит-тесты API-модулей (vitest + тестовая БД)

Наиболее высокоприоритетные кандидаты:

**`apps/api/src/modules/inventory/ledger.ts` — `recordMovement()`**

Чистая функция над транзакцией: легко тестируется с тестовой БД PostgreSQL в Docker или через `@testcontainers/postgresql`. Критичные случаи:

- `clamp=true`: остаток не уходит ниже нуля при продаже больше, чем есть.
- `receipt` + `unitCost`: WAC пересчитывается по формуле `(before * old + applied * cost) / after`.
- `requireTracked=true` + `trackStock=false`: движение пропускается, строка в журнал не пишется.
- Инвариант `qtyAfter == before + applied` для всех типов движений.

**`apps/api/src/lib/money.ts` — `computeTotals()`, `computeRental()`**

Чистые функции без зависимостей от БД — тестируются без окружения:

- Комбинации скидок (процентная + фиксированная, на чек + на позицию).
- Граничный случай: итог не уходит ниже 0 при скидке больше суммы.
- Аренда: правильный `ceil(minutes / 60)` при нецелом числе часов.

**`apps/api/src/modules/shifts/shifts.service.ts` — `getShiftCashBalance()`**

Логика расчёта остатка кассы включает пять слагаемых; важно тестировать правильность суммирования при смешанных возвратах (с `tenders` и без).

**Идемпотентность депозита** (`POST /clients/:id/balance` с `idempotencyKey`) — отправка двух идентичных запросов не должна дважды изменить `profiles.balance`.

Предлагаемый стек:

```
vitest                 — тест-раннер (ESM-нативный, подходит для "type": "module" в @titan/api)
@testcontainers/postgresql — PostgreSQL в Docker для интеграционных тестов
```

Структура тестов:

```
apps/api/src/modules/inventory/__tests__/ledger.test.ts
apps/api/src/lib/__tests__/money.test.ts
apps/api/src/modules/shifts/__tests__/shifts.service.test.ts
```

### e2e-тесты фронтенда (Playwright)

Playwright подходит для Next.js App Router и PWA-сценариев:

- Авторизация по PIN → переход на `/pos` → добавление позиции → оплата.
- Проверка обновления остатка в `/manage/inventory` после продажи.
- Открытие / закрытие смены с расхождением кассы.

Playwright поддерживает мобильную эмуляцию (`iPhone 14` preset) для воспроизведения условий реального устройства без физического телефона.
