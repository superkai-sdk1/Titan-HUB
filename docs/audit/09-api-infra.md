# Аудит: Инфраструктура API (Hono, очереди, cron, AI, загрузки)

## Summary

Инфраструктурный слой API (`apps/api`) аккуратнее, чем ожидалось: есть fail-fast по `JWT_SECRET`/`DATABASE_URL`, безопасный логгер с маскированием токенов в URL, sniffing magic-bytes при загрузке изображений, обобщённый `onError`, body-limit и rate-limit. Однако для production и особенно для SaaS есть серьёзные дыры: **полностью отсутствует graceful shutdown** (SIGTERM игнорируется → потеря in-flight запросов и SSE при каждом деплое), **нет idempotency/retry для текста уведомлений** (BullMQ установлен, но не используется ни в одной строке — вся доставка fire-and-forget через сырые `Promise.all`), **AI-модуль text-to-SQL** даёт аутентифицированному стаффу неограниченный произвольный SELECT по всей базе без лимита расходов на LLM, а **MinIO-загрузки публичны для всего мира без подписи и без привязки к клубу**. Логирование — это `console.log` без структуры, корреляции и уровней; наблюдаемость на нуле. Health-check тривиален (не проверяет БД/Redis).

## Production-readiness score: **52 / 100**

Обоснование: базовая гигиена безопасности (секреты, маскирование, sniffing, rate-limit, generic error) выполнена на твёрдую четвёрку и сильно вытягивает оценку вверх. Но три класса проблем тянут вниз: (1) operational — нет graceful shutdown, нет реальной observability, тривиальный health-check, cron на `setTimeout` без блокировки от наложения; (2) AI — мощный text-to-SQL без cost-guard и с рисками промпт-инъекции; (3) загрузки/бэкап — публичный bucket и тяжёлые операции (restore с `pg_terminate_backend`!) прямо в HTTP-хендлере без защиты от наложения. Ни одна из проблем не «теряет деньги прямо сейчас», поэтому не 30, но до коммерческого SaaS дистанция большая.

## Findings

### CRITICAL

#### C1. Нет graceful shutdown — деплой рвёт in-flight запросы, транзакции и SSE
**Файл:** `apps/api/src/index.ts:28-35` (нет ни одного `process.on('SIGTERM'|'SIGINT')` во всём `apps/api/src` — проверено grep'ом).
**Что не так:** `serve()` поднимается, но обработчиков сигналов нет. При `docker compose up -d --build` / рестарте контейнера Docker шлёт SIGTERM, Node умирает мгновенно, не дожидаясь завершения активных HTTP-запросов и не закрывая SSE-стримы и пулы (PG/Redis). Учитывая, что бэкенд делает денежные операции (POS, платежи, возвраты) и тяжёлые транзакции (бэкап/restore, начисление бонусов в cron), обрыв на середине транзакции — прямой риск.
**Почему важно:** В заметках по деплою прямо сказано, что VPS перегружен и SSH рвётся под сборкой; рестарт API при деплое — норма. Каждый деплой = пачка оборванных запросов и «висящих» SSE-клиентов на фронте.
**Фикс:** добавить graceful shutdown:
```ts
const server = serve({ fetch: app.fetch, port }, …)
let shuttingDown = false
async function shutdown(sig: string) {
  if (shuttingDown) return; shuttingDown = true
  console.log(`[shutdown] ${sig} — closing…`)
  server.close()                 // перестаём принимать новые соединения
  await new Promise(r => setTimeout(r, 3000)) // дать SSE/запросам завершиться
  process.exit(0)
}
process.on('SIGTERM', () => void shutdown('SIGTERM'))
process.on('SIGINT', () => void shutdown('SIGINT'))
```
Дополнительно повесить `/health` на режим draining (возвращать 503 во время shutdown), чтобы nginx перестал слать трафик.

#### C2. MinIO bucket публичен для всего интернета и не привязан к клубу
**Файл:** `apps/api/src/modules/upload/upload.router.ts:88-92, 98`.
**Что не так:** при первом аплоаде создаётся bucket с политикой `Principal: { AWS: ['*'] }, Action: ['s3:GetObject']` — **анонимное чтение любого объекта кем угодно по прямой ссылке**. URL отдаётся как `${MINIO_PUBLIC_URL}/titan-uploads/<ts>-<rand>.<ext>`. Имена непредсказуемы (защита через obscurity), но публичный листинг/перебор и утечка одной ссылки = вечный публичный доступ. Для SaaS это означает, что фото меню/аватары всех клубов лежат в одном глобально-читаемом bucket'е без изоляции.
**Почему важно:** в мульти-клубной модели это утечка данных одного арендатора через общий bucket; даже в single-tenant — нежелательная публичность.
**Фикс:** сделать bucket приватным и отдавать `presignedGetObject` (TTL, напр. 1 час) вместо постоянного публичного URL; либо проксировать выдачу через API с проверкой роли. Для SaaS — префикс ключа `clubId/...` и политика на уровне префикса.

### HIGH

#### H1. AI text-to-SQL: произвольный SELECT по всей базе без cost-guard и rate-limit на LLM
**Файл:** `apps/api/src/modules/ai/ai.router.ts:222-268, 596-607, 618-655`.
**Что не так:** `custom_query` берёт вопрос пользователя → отправляет в LLM с полной схемой БД (`getSchemaDoc`) → получает SQL → `sanitizeSql` (блок DML/DDL, чувствительных колонок) → выполняет в read-only транзакции с `statement_timeout=5000` и `LIMIT 200`. Защита SQL-инъекции на удивление приличная (только `select|with`, чёрный список ключевых слов, фильтр `pass|pin|hash|secret|token|...`, исключение `push_subscriptions`). Но:
- **Нет лимита расходов на LLM.** Каждый `custom_query` = до 2 вызова внешней модели (генерация SQL + финальный ответ), `max_tokens: 2048`, кэш всего 60с. Любой стафф может в цикле жечь токены. Для SaaS это прямой OPEX-риск (счёт за Polza.ai растёт линейно от числа клубов × активность).
- **Блокировка по ключевым словам обходима** регэкспами на границах слов: например имена колонок/таблиц через комментарии `/* */`, юникод-омоглифы или `SELECT` с подзапросом, дергающим `pg_catalog`/`information_schema` для разведки. `sanitizeSql` не парсит SQL, а матчит строки — это не настоящий парсер.
- **`runReadonly` использует `sql.raw(wrapped)`** (`ai.router.ts:240`) с моделью-сгенерированной строкой. Read-only транзакция и таймаут ограничивают ущерб, но `SET TRANSACTION READ ONLY` + `SET LOCAL statement_timeout` не защищают от тяжёлых аналитических запросов, которые в пределах 5с положат CPU базы.
**Почему важно:** аутентифицированный insider (или украденный токен стаффа) получает почти-произвольный доступ на чтение к базе + неограниченное жжение LLM-бюджета.
**Фикс:** (1) суточный лимит AI-вызовов на пользователя/клуб в Redis (напр. 200/день); (2) лог стоимости каждого вызова (`usage` из ответа Polza, если есть) в таблицу для биллинга; (3) понизить `statement_timeout` до 2000мс и явный `SET LOCAL work_mem`; (4) рассмотреть allowlist таблиц вместо blacklist колонок.

#### H2. Утечка внутренних ошибок наружу в нескольких хендлерах вопреки глобальному `onError`
**Файлы:** `upload.router.ts:101` (`return c.json({ error: e.message }, 500)`), `system.router.ts:119,134,149,165` (`error: e?.message`), `ai.router.ts:295,313,…` (`Не удалось…: ${String(e)}` — текст ошибки в ответ), `ai.router.ts:645` (`AI недоступен: ${String(e)}`).
**Что не так:** глобальный `app.onError` (`app.ts:124-129`) специально прячет детали и отдаёт `Internal error`, но эти хендлеры ловят ошибку сами и отдают `e.message`/`String(e)` клиенту — то есть тексты драйвера БД, пути pg_dump, сообщения MinIO/rclone утекают в UI. В `ai.router.ts` строки ошибок ещё и попадают в `userMessage` → уходят во внешний LLM (Polza.ai) (`ai.router.ts:631-639`).
**Почему важно:** раскрытие внутренней структуры (имена таблиц/колонок, пути ФС, эндпоинты инфраструктуры) — разведка для атакующего; отправка стектрейсов БД во внешний AI-провайдер — утечка за периметр.
**Фикс:** в этих хендлерах логировать полную ошибку на сервере и отдавать обобщённый текст; не подмешивать `String(e)` в `userMessage` для LLM.

#### H3. Cron на `setTimeout/setInterval` — наложение запусков, отсутствие блокировки, дрейф, нет at-least-once гарантий
**Файл:** `apps/api/src/index.ts:40-55`, логика `apps/api/src/cron/birthdays.ts`.
**Что не так:** дневной cron планируется ручным `setTimeout` до 06:00 UTC, затем `setInterval(24h)`. Проблемы:
- **`setInterval` дрейфует** (таймер не якорится к стене часов; при подвисании event-loop сдвигается) и **не переживает рестарт** — если контейнер перезапустился в 06:01, задача за этот день не выполнится вовсе (следующий `setTimeout` нацелен на завтра). То есть начисление бонусов ко дню рождения может молча пропускаться в дни деплоя.
- **Нет защиты от наложения / нет распределённой блокировки.** Сейчас единственный контейнер (в docker-compose нет `replicas`), так что двойного запуска нет — но это держится только на «один инстанс». Для SaaS/HA это сразу станет двойным начислением бонусов (хотя внутри есть идемпотентность по `bonus_history` за день — см. ниже, это спасает).
- **Идемпотентность бонусов есть и сделана хорошо** (`birthdays.ts:55-77`: проверка существующей записи за `CURRENT_DATE` + `FOR UPDATE` + лот). Это снижает риск двойного начисления. Но дедуп уведомлений (`birthdays.ts:103-114`) делает **отдельный SELECT на каждого owner×client** — N×M запросов, на крупной базе это медленно.
**Почему важно:** пропуск запуска = недоначисленные бонусы (тихая ошибка лояльности); при масштабировании — двойные уведомления/нагрузка.
**Фикс:** перейти на реальный планировщик. BullMQ уже в зависимостях (`package.json`) — использовать `Queue` с `repeat: { pattern: '0 6 * * *' }` (repeatable job переживает рестарт, гарантирует один запуск). Либо `node-cron` + Redis-advisory-lock (`SET key NX PX`) на время выполнения. Дедуп уведомлений переписать на один bulk-INSERT с `ON CONFLICT`.

#### H4. Health-check не проверяет зависимости (false-healthy)
**Файл:** `apps/api/src/app.ts:96-97` + `docker-compose.yml:86-88`.
**Что не так:** `/health` отдаёт `{ ok: true }` безусловно, даже если PG-пул мёртв или Redis недоступен. Docker healthcheck бьёт именно в этот эндпоинт, значит контейнер считается «healthy», пока процесс жив, — а API при этом может не уметь обслужить ни один запрос (БД упала). nginx будет слать на него трафик.
**Почему важно:** в заметках по ops уже зафиксированы инциденты «dead minio → 502» и «nginx-reload race → ложное API не отвечает». Тривиальный health усугубляет: оркестратор не перезапустит/не выведет из ротации реально сломанный API.
**Фикс:** сделать `/health` (или отдельный `/health/ready`) с лёгким `SELECT 1` к БД и `PING` к Redis с коротким таймаутом; для liveness оставить тривиальный `/health/live`.

#### H5. Restore БД выполняется синхронно в HTTP-хендлере и убивает все коннекты — нет защиты от наложения и от потери ответа
**Файл:** `apps/api/src/modules/system/system.router.ts:139-167` + `apps/api/src/lib/backup.ts:112-129`.
**Что не так:** `POST /system/restore` и `/restore-upload` запускают `restoreFromPath`, который делает `pg_terminate_backend(...)` по **всем** коннектам к базе (`backup.ts:115`), затем `psql` загружает дамп. Это:
- рвёт собственный пул API (как и любые параллельные POS-операции — на середине транзакции оплаты!),
- выполняется прямо в request-хендлере (долгая операция держит HTTP-соединение; при обрыве клиента — `c.req.raw.signal` не отменяет уже запущенный `exec`),
- не имеет глобальной блокировки: два одновременных restore/backup затопчут друг друга.
**Почему важно:** одна кнопка restore может оборвать активную смену/оплату; нет mutex'а между restore, backup и cron-бэкапом.
**Фикс:** ставить флаг «maintenance mode» (Redis), отбивать новые POS-операции 503 на время restore; брать Redis-lock на backup/restore; выполнять как фоновую задачу со статусом, а не синхронно в хендлере.

### MEDIUM

#### M1. Логирование — `console.log` без структуры, уровней, корреляции; нулевая observability
**Файлы:** весь слой (`app.ts:73-81` логгер, `console.error/warn/log` повсюду: `app.ts:127`, `index.ts`, `push.ts`, `birthdays.ts`, …).
**Что не так:** нет структурированных логов (JSON), нет request-id/trace-id, нет уровней (всё `console.*`), нет метрик (latency p95, error rate, очередь push, AI-расход), нет интеграции с чем-либо (Sentry/Loki/OTel). Запросный логгер печатает только `METHOD path status ms` без userId/clubId. При инциденте в проде разбираться придётся по сырому stdout контейнера.
**Почему важно:** для коммерческого SaaS это блокер на этапе поддержки: невозможно понять, какой клуб/пользователь упёрся в ошибку, нет алертов.
**Фикс:** ввести `pino` (структурный JSON, уровни), прокинуть request-id middleware и класть в лог `userId`/`role`; подключить Sentry для `onError` и unhandledRejection; экспортировать базовые метрики (Prometheus `/metrics` или хотя бы счётчики в Redis).

#### M2. Двойная верификация JWT на каждом запросе (rateLimit + requireAuth)
**Файлы:** `apps/api/src/middleware/rateLimit.ts:44-52` и `apps/api/src/middleware/auth.ts:44-49`.
**Что не так:** `rateLimit` (висит на `/api/*`) сам по себе вызывает `verifyToken(token)`, чтобы получить `userId` для ключа лимита; затем `requireAuth` снова вызывает `verifyToken` для того же токена. То есть на каждый аутентифицированный запрос — две криптопроверки подписи и двойной парсинг. HS256 дёшев, но это лишняя работа на горячем пути, а главное — дублирование логики (две точки, где можно ошибиться). SSE-тикеты (`?ticket=`) в rateLimit не учитываются вовсе — такие запросы падают в IP-bucket.
**Почему важно:** мелкая неэффективность + расхождение поведения (тикетные запросы лимитируются по IP, токенные — по user).
**Фикс:** верифицировать токен один раз (в `requireAuth`), класть payload в context; rateLimit ставить ПОСЛЕ auth и читать `c.get('user')`, либо вынести верификацию в общий хелпер с кешем по `tokenHash`.

#### M3. Утечка Redis-соединений в AI-модуле (new Redis на каждый запрос)
**Файл:** `apps/api/src/modules/ai/ai.router.ts:68-70, 622-652`.
**Что не так:** `getRedis()` в AI-модуле делает `new Redis(...)` на **каждый** запрос `/chat` (в отличие от `lib/redis.ts`, где один shared-клиент). В конце есть `redis.disconnect()` в `finally` (`:651`), но при раннем `return` по кэшу (`:625`) соединение **не закрывается** — утечка коннекта на каждый cache-hit. На активном дашборде это копит TCP-коннекты к Redis.
**Почему важно:** медленная утечка → исчерпание лимита коннектов Redis под нагрузкой (особенно с несколькими клубами).
**Фикс:** использовать общий `getSharedRedis()` из `lib/redis.ts`, убрать `disconnect()`/`new Redis` совсем.

#### M4. SSE-эндпоинты создают отдельный Redis-subscriber на каждое соединение
**Файлы:** `apps/api/src/modules/system/system.router.ts:76`, `apps/api/src/modules/notifications/notifications.router.ts:40`, `push.ts:101-103` (отдельный publish-клиент на каждый `notify`).
**Что не так:** каждый SSE-клиент открывает свой `new Redis()` subscriber; каждый `notify()` поднимает новый `getNotifRedis()` для одного publish и сразу `disconnect()`. На 10 владельцах с открытым дашбордом + поток уведомлений это десятки коннектов и постоянный connect/disconnect-churn к Redis.
**Почему важно:** масштабируемость; Redis-коннекты — конечный ресурс, churn даёт latency-спайки.
**Фикс:** один общий subscriber-клиент на процесс с fan-out по локальным слушателям; один долгоживущий publish-клиент (shared) вместо connect-на-publish.

#### M5. CORS завязан на единственный `FRONTEND_URL` — не готов к мульти-доменному SaaS, и `credentials:true`
**Файл:** `apps/api/src/app.ts:85-91`.
**Что не так:** `origin: process.env['FRONTEND_URL'] ?? 'http://localhost:3000'` с `credentials: true`. Один статический origin. Для SaaS с поддоменами на клуб (`club1.titanpos.ru`) или кастомными доменами это сломается — нужен динамический allowlist. Сейчас не критично (single-tenant, один домен), но архитектурный долг.
**Фикс:** функция-origin с проверкой по списку/regex разрешённых доменов клубов.

#### M6. `restore-upload` и `upload/image` парсят `formData()`/`parseBody()` до проверки размера; body-limit на `/api/*` = 1 МБ, но загрузки больше
**Файлы:** `app.ts:93` (`bodyLimit 1MB` на `/api/*`), `upload.router.ts:64-69` (лимит 2МБ), `system.router.ts:154-159` (лимит 200МБ).
**Что не так:** глобальный `bodyLimit({ maxSize: 1MB })` висит на `/api/*`, а это покрывает и `/api/upload/image` (заявлен лимит 2МБ) и `/api/system/restore-upload` (заявлен 200МБ). Либо глобальный лимит реально режет загрузки на 1МБ (тогда проверки 2МБ/200МБ недостижимы и это латентный баг), либо `bodyLimit` Hono не применяется к multipart как ожидается. В любом случае — три несогласованных лимита на одном пути.
**Почему важно:** либо легитимные загрузки/restore молча обрезаются на 1МБ (битый restore = катастрофа), либо защита размера не работает как написано. Требует проверки фактического поведения.
**Фикс:** убрать глобальный `bodyLimit` с путей загрузки (повесить точечно на не-загрузочные роуты) и задать корректный per-route лимит; стримить restore-файл на диск, а не держать 200МБ в памяти (`Buffer.from(await f.arrayBuffer())`, `system.router.ts:160` — весь дамп в RAM при `mem_limit: 768m`).

#### M7. `notify` fire-and-forget без ретраев и без очереди — потеря уведомлений при сбое
**Файл:** `apps/api/src/modules/notifications/push.ts:236-371`, вызовы `void notify(...).catch(()=>{})`.
**Что не так:** доставка push/Telegram идёт прямо в `notify` через `Promise.all` без ретраев. Если Redis/PG/Telegram моргнули — уведомление просто теряется (всё в `try/catch` с `console.*`). web-push корректно чистит мёртвые подписки (404/410, `push.ts:188-190`), но временные ошибки (5xx, timeout) не ретраятся. BullMQ установлен и **не используется** — идеальный кандидат вынести доставку в очередь с backoff.
**Почему важно:** «Вызов персонала» с планшета — критичный для бизнеса сигнал; молчаливая потеря = недовольный гость.
**Фикс:** вынести доставку (push + telegram) в BullMQ-воркер с `attempts: 3, backoff` и dead-letter. Это же решит M3/M4 churn (воркер держит свои коннекты).

#### M8. Раннер миграций без advisory-lock — риск гонки при параллельном старте
**Файл:** `apps/api/src/migrations/runner.ts` (нет `pg_advisory_lock`).
**Что не так:** миграции применяются на старте каждого инстанса без распределённой блокировки. Сейчас инстанс один (нет `replicas` в docker-compose) → гонки нет. Но любой переход на 2+ реплики или параллельный rolling-restart → два процесса могут одновременно начать применять одну миграцию (транзакция на файл спасает от частичного применения, но не от двойного запуска не-идемпотентного SQL и не от дедлоков).
**Почему важно:** для SaaS/HA это станет реальным риском.
**Фикс:** обернуть весь прогон в `pg_advisory_lock(<const>)` … `pg_advisory_unlock`.

### LOW

#### L1. Дефолтные креды MinIO и `useSSL:false` зашиты как fallback
**Файл:** `apps/api/src/modules/upload/upload.router.ts:52-57`.
**Что не так:** `accessKey ?? 'minioadmin'`, `secretKey ?? 'minioadmin'`, `useSSL: false`. Если env не задан — поднимется с дефолтными кредами; трафик к MinIO нешифрован (внутри docker-сети это приемлемо, но fallback-креды — анти-паттерн, как и `JWT_SECRET` без fallback в `index.ts`, который сделали правильно).
**Фикс:** fail-fast по `MINIO_*` (как для JWT), без дефолтных кредов в коде.

#### L2. Anthropic SDK и BullMQ в зависимостях, но не используются (мёртвый код/конфьюжн)
**Файл:** `apps/api/package.json` (`@anthropic-ai/sdk`, `bullmq`), при этом AI реально ходит в Polza.ai (`ai.router.ts:39-66`, OpenAI-совместимый REST), а `bullmq` не импортируется нигде.
**Что не так:** название области аудита и заметки говорят «AI (Anthropic)», но фактически модель — `google/gemini-3.1-flash-lite` через Polza.ai. SDK и очередь висят как неиспользуемые зависимости → лишний вес образа, ложные ожидания.
**Фикс:** либо удалить неиспользуемые зависимости, либо (лучше) задействовать BullMQ для доставки уведомлений/cron (см. H3/M7).

#### L3. `ticket`-путь auth не имеет rate-limit и не логирует потребление
**Файл:** `apps/api/src/middleware/auth.ts:16-27`, `rateLimit.ts` (тикеты не учтены).
**Что не так:** SSE-тикеты потребляются `getdel`, одноразовые, живут 60с — дизайн хороший. Но в rateLimit запрос с `?ticket=` не идентифицируется как пользователь → падает в общий IP-bucket. Мелочь.
**Фикс:** учитывать ticket при выборе ключа лимита, либо явно whitelist'ить SSE.

#### L4. `revoked`-проверка токена fail-open при недоступности Redis
**Файл:** `apps/api/src/middleware/auth.ts:51-56`.
**Что не так:** если Redis недоступен, проверка отзыва токена пропускается (`fail-open`). Это осознанный компромисс доступности, прокомментирован. Но означает, что при недоступности Redis отозванные (logout/блокировка) токены снова валидны до их `exp` (до 7 дней, `jwt.ts:29`).
**Почему важно:** окно для украденного/отозванного токена при сбое Redis. Низкий риск, но для коммерческого продукта стоит хотя бы алертить на fail-open.
**Фикс:** оставить fail-open, но инкрементировать метрику/лог при срабатывании, чтобы это было видно; сократить `JWT_EXPIRES_IN` (7д длинновато для POS).

## Идеи функций для мафия-клубов / антикафе

1. **AI-инсайты как фоновые задачи (BullMQ digest).** Раз в сутки воркер формирует «утреннюю сводку владельцу» (выручка вчера, должники, заканчивающийся товар, ближайшие ДР) и шлёт push/Telegram — переиспользует уже готовые `buildContext`-экшены, но без живого жжения LLM на каждый клик.
2. **Голосовой/чат-вопрос по смене для бариста-ведущего.** AI уже умеет text-to-SQL; добавить узкий пресет «что популярно сейчас», «сколько свободных столов», «у кого ДР сегодня» — кнопки в POS вместо свободного ввода (дешевле и безопаснее).
3. **Очередь печати/уведомлений кухни.** Для антикафе с кухней — BullMQ-очередь заказов с гарантией доставки на экран кухни (то, чего сейчас fire-and-forget не даёт).
4. **Алерт-движок на аномалии.** Воркер раз в N минут проверяет: расхождение кассы, аномально крупный возврат, всплеск скидок — и шлёт владельцу. Инфраструктура уведомлений уже есть.
5. **Webhook-уведомления для интеграций клуба** (Telegram-канал клуба, Discord сообщества мафии): тот же `notify`, но с пользовательскими webhook-приёмниками.

## Quick wins (< 1 часа каждый)

1. **Graceful shutdown** (C1) — ~15 строк в `index.ts`, мгновенно убирает обрывы при деплое.
2. **Health-check с `SELECT 1` + Redis PING** (H4) — небольшой эндпоинт `/health/ready`.
3. **Убрать `e.message`/`String(e)` из ответов** в `upload.router.ts:101`, `system.router.ts`, и из `userMessage` AI (H2) — заменить на generic + `console.error`.
4. **Чинить Redis-leak в AI** (M3) — заменить `new Redis()` на `getSharedRedis()`, убрать `disconnect()`.
5. **Суточный AI-лимит на пользователя в Redis** (H1, часть) — `INCR ai:quota:<user>:<day>` с `EXPIRE`, отбой 429 при превышении.
6. **Fail-fast по `MINIO_*` и `VAPID_*`** в `assertEnv()` (L1) — несколько строк рядом с уже существующей проверкой.
7. **Понизить `statement_timeout` AI** до 2000мс (H1) — одна строка в `runReadonly`.

## SaaS / мульти-клубные импликации для этой области

- **Изоляция загрузок (КРИТИЧНО для SaaS).** Сейчас один публичный bucket `titan-uploads` без `clubId`-префикса и без подписи (C2) — файлы всех арендаторов читаемы глобально и неразделимы. Перед продажей: приватный bucket, presigned URL, ключи вида `clubs/<clubId>/...`, политика на префикс.
- **AI-расходы как переменная стоимость аренды.** `custom_query` жжёт внешний LLM без учёта и лимита (H1). В SaaS это прямой OPEX, который надо (а) лимитировать на тариф, (б) учитывать на клуб для биллинга. Сейчас нет ни лимита, ни учёта `usage`.
- **Cron/очереди при HA.** `setTimeout`-cron (H3) и миграции без advisory-lock (M8) безопасны только при единственном инстансе. Любой переход на несколько реплик (неизбежен при росте) даст двойные cron-запуски и гонки миграций. BullMQ-repeatable + advisory-lock закрывают оба.
- **Observability на клуб (M1).** Без structured-логов с `clubId`/`userId` и без Sentry поддержка множества клубов невозможна — нельзя ответить «у клуба X не приходят уведомления». Это блокер коммерческой эксплуатации, а не «nice to have».
- **CORS/домены (M5).** Текущий single-origin CORS не переживёт поддомены/кастомные домены клубов — нужен динамический allowlist.
- **Rate-limit per-club.** Сейчас лимит per-user/per-IP; в SaaS нужен ещё и потолок per-club, чтобы один шумный арендатор не выедал Redis/LLM-бюджет соседей.
