## 0. Зафиксированные архитектурные решения

| Решение | Значение |
|---|---|
| **Мультитенантность** | **База-на-клуб (database-per-tenant)**. Один Postgres-сервер, отдельная БД на каждый клуб. Никакого row-level `tenant_id`/RLS. |
| **Control-plane** | Отдельная БД-реестр (`titan_control`): список клубов, подписки, суперадмин, флаги модулей, аудит. |
| **Маршрутизация клуба** | По поддомену: `<club-slug>.titanpos.ru` → nginx → API определяет клуб по `Host` → выбирает его БД. Суперадмин — `admin.titanpos.ru`. |
| **Секреты клуба** | Токены ботов, AI, Platega — в БД клуба (зашифрованы master-ключом из env). Уходят из глобального env. |
| **Два разных Platega** | (1) **Platega клуба** — клуб принимает оплату от своих гостей (СБП QR). (2) **Platega платформы** — вы берёте оплату подписки с клубов. Это разные аккаунты/ключи. |
| **Суперадмин** | Отдельный контур аутентификации (логин `superadmin` → создание пароля → пасскей при первом входе). Отдельная админка проектов. |
| **Боты** | Один процесс-менеджер ботов поднимает по экземпляру grammy на каждый активный токен клуба, привязывая его к БД этого клуба. |
| **Биллинг** | Ручной учёт периодов (триал 7д / 1 / 3 / 6 / 12 мес) с регулируемой суммой + генерация ссылки оплаты через Platega платформы. |

### Топология БД (целевая)
```
Postgres (один сервер в docker-compose)
├── titan_control      ← реестр: clubs, subscriptions, superadmins, module_flags, audit
├── club_<slug1>       ← полная схема приложения (checks, menu, customers, ...)
├── club_<slug2>       ← полная схема приложения
└── club_<slugN>
```
Провижининг нового клуба = `CREATE DATABASE club_<slug>` → прогон baseline+tenant миграций → сидинг (типы вечеров, дефолтные настройки, bootstrap владельца). Для `CREATE DATABASE` нужен админ-коннект Postgres (`CONTROL_DATABASE_URL` / `POSTGRES_ADMIN_URL` в env).

### Критический путь
```
Baseline-миграция (000) ──► Tenant-context (убрать синглтон db) ──► Control-plane + провижининг
        │                            │                                      │
   (P0 #7 аудита)            (30 файлов API + 2 бота)              Суперадмин-админка ──► Биллинг
```
Сначала **Фаза 0** (P0-фиксы — безопасно и независимо), параллельно готовится **baseline-миграция**, затем **Фаза 1** (фундамент тенантности) — она блокирует всё остальное.

## ФАЗА 1 — Фундамент мультитенантности (база-на-клуб) · ~4–6 недель · КРИТИЧЕСКИЙ ПУТЬ

### 1.1 Baseline-миграция схемы (предусловие всего) — P0 #7
- **Проблема:** базовые таблицы создаёт только `drizzle-kit push`, не вызываемый в деплое (`migrations/runner.ts` применяет только `sql/*.sql`). Новую БД клуба так не поднять.
- **Задача:** сгенерировать `apps/api/src/migrations/sql/000_baseline.sql` из текущей drizzle-схемы (`drizzle-kit generate` → собрать полный DDL всех таблиц на «нулевом» состоянии). Сделать идемпотентным (`CREATE TABLE IF NOT EXISTS`).
- **Критерий:** на ПУСТОЙ БД `runMigrations()` создаёт всю схему «с нуля» до зелёного. Smoke-тест: `empty DB → up → /health/ready = ok`.

### 1.2 Control-plane БД и схема
- Новый пакет/схема `packages/database/src/control/` (отдельный drizzle-schema), отдельный коннект `CONTROL_DATABASE_URL`.
- Таблицы:
  - `clubs` (id, slug, name, db_name, subdomain, status[active|suspended|deleted], created_at, ...).
  - `club_modules` (club_id, module_key, enabled) — флаги 24 модулей.
  - `subscriptions` (club_id, plan, period, amount, currency, started_at, paid_until, status[trial|active|expired|suspended], note).
  - `subscription_payments` (club_id, amount, period, method[manual|platega], platega_invoice_id, status, paid_at) — ручной + Platega-учёт.
  - `superadmins` (id, login, password_hash, created_at).
  - `superadmin_passkeys` (id, superadmin_id, credential_id, public_key, counter, ...).
  - `control_audit` (actor, action, target_club, payload, at) — кто что менял.
- Свой раннер миграций control-plane (`migrations/control/*.sql`).

### 1.3 Tenant-context: убрать синглтон `db` (большой рефактор)
- **Суть:** сейчас `db` — модульный синглтон (`packages/database/src/client.ts:16`), импортируется в **30 файлах API**. Нужен пер-запросный `db`.
- **Шаги:**
  1. В `@titan/database` добавить фабрику `getClubDb(dbName|connString)` с кэшом пулов (`Map<dbName, drizzle>`), `max`-пул на клуб, LRU-эвикция простаивающих.
  2. Middleware `tenantContext`: резолвит клуб из `Host` → control-plane lookup (с кэшем) → `c.set('db', getClubDb(...))` + `c.set('club', clubMeta)`.
  3. Заменить во всех роутерах `import { db } from '@titan/database'` → `const db = c.var.db`. Сервисы, не имеющие `c`, принимают `db` параметром.
  4. `appSettings.ts`, cron, backup — параметризовать по клубу.
- **Риск:** механически большой (30 файлов), но прямолинейный. Делать модуль-за-модулем за PR, держа синглтон как временный фолбэк до полной миграции.
- **Критерий:** ни один рантайм-путь не использует глобальный `db`; два клуба в разных БД полностью изолированы (тест: запрос к клубу A не видит данные клуба B).

### 1.4 Резолюция клуба + nginx + TLS
- Wildcard DNS `*.titanpos.ru` → VPS.
- Wildcard TLS-сертификат (Let's Encrypt DNS-challenge) для `*.titanpos.ru`.
- nginx: `server_name *.titanpos.ru`, проксировать `Host` в API; `admin.titanpos.ru` → суперадмин-зона.
- WebAuthn: `RP_ID` = поддомен клуба (пасскеи изолируются по клубам автоматически — это плюс). Суперадмин RP_ID = `admin.titanpos.ru`.
- Фолбэк до wildcard-сертификата: клуб на отдельном поддомене с индивидуальным сертификатом.

### 1.5 Миграции по всем БД + провижининг
- `runMigrations()` расширить: control-plane миграции → затем для **каждого active клуба** прогнать tenant-миграции (baseline + sql/*).
- Процедура `provisionClub(slug, name, ownerData)`:
  1. `CREATE DATABASE club_<slug>` (через `POSTGRES_ADMIN_URL`).
  2. Прогнать baseline + все tenant-миграции.
  3. Сидинг: типы вечеров, дефолтные `app_settings`, bootstrap-владелец (одноразовый код/пасскей-инвайт).
  4. Запись в `clubs` + дефолтные `club_modules` + триал-подписка.
- Деплой: после `up -d` миграции прогоняются по всем клубам (идемпотентно).
- **Критерий:** «создать клуб из админки → зайти на его поддомен → залогиниться владельцем → пустое рабочее заведение» проходит end-to-end.

### 1.6 Пер-клубные секреты + шифрование
- Таблица в БД клуба `integrations` (или `app_settings` с пометкой secret): `admin_bot_token`, `wallet_bot_token`, `ai_api_key`, `platega_merchant_id`, `platega_secret`, ...
- Слой шифрования: `apps/api/src/lib/secrets.ts` — AES-256-GCM, master-ключ `SECRETS_MASTER_KEY` (env). Хранить ciphertext + iv + tag.
- Чтение: Platega-роутер берёт creds клуба из его БД; AI-модуль — AI-ключ клуба; бот-менеджер — токены ботов.
- **Критерий:** в БД нет токенов в открытом виде; ротация master-ключа описана в runbook.

### 1.7 Мульти-тенантный бот-менеджер
- Переписать `apps/bot-admin` и `apps/bot-wallet` в один **менеджер ботов**: на старте читает active-клубы из control-plane, расшифровывает их токены, поднимает grammy `Bot` на каждый токен, привязывая хендлеры к БД этого клуба.
- Реакция на изменения: при смене токена/добавлении/удалении клуба — пересоздать соответствующий Bot (через Redis pub/sub сигнал из API или периодический реконсайл).
- **Критерий:** бот клуба A пишет только в БД клуба A; добавление клуба поднимает его ботов без рестарта всего процесса.

### 1.8 Per-club Platega / AI
- Platega-роутер: `merchant_id/secret` берутся из БД клуба по `Host`; вебхук валидируется per-club секретом + HMAC (см. 0.1.1).
- AI-модуль: ключ из настроек клуба (если не задан — модуль выключен/деградирует).

**Выход фазы:** платформа технически мультитенантна. Область «мультитенантность» с 8 → ~75.

## ФАЗА 2 — Админка Суперадмина · ~3–4 недели

### 2.1 Аутентификация суперадмина (bootstrap)
- Контур отдельный от клубов: отдельный JWT (`aud: superadmin`, `role: superadmin`), который **не принимается** клубными роутерами, и наоборот.
- Первый вход: логин `superadmin` без пароля → если в `superadmins` нет записи → экран «создайте пароль» → затем «зарегистрируйте пасскей» (WebAuthn на `admin.titanpos.ru`). Дальше вход: пароль + пасскей.
- Новый роутер `apps/api/src/modules/superadmin/*`, web-зона `apps/web/src/app/superadmin/*` (или поддомен admin).

### 2.2 CRUD заведений + провижининг
- Список клубов: статус, подписка (paid_until), занятые модули, ссылка на поддомен.
- Создать: форма (название, slug/поддомен, данные владельца) → вызывает `provisionClub` (1.5).
- Настроить: редактировать профиль, модули, подписку.
- Удалить: жёсткое подтверждение (ввести slug), сначала бэкап БД клуба, затем `status=deleted` (soft) и опционально `DROP DATABASE` по второму подтверждению.

### 2.3 Вкл/выкл модули по клубу
- Тогглы 24 модулей в `club_modules`.
- Энфорсмент: API-middleware `requireModule(key)` на роутерах (403 если выключен); web прячет пункты меню по `club_modules` (отдать конфиг на фронт при загрузке).
- **Критерий:** выключенный модуль недоступен и в API, и в навигации клуба.

### 2.4 Подписки: ручной учёт + Platega-ссылки
- Периоды: **триал 7 дней / 1 / 3 / 6 / 12 месяцев**, сумма редактируется вручную.
- Ручной учёт: «отметить оплачено» на период с суммой → продлевает `paid_until`, пишет в `subscription_payments(method=manual)` + `control_audit`.
- Platega-ссылка: генерация invoice через **Platega платформы** (отдельные `PLATFORM_PLATEGA_*` в env) → ссылка/QR клиенту-клубу; вебхук платформы → авто-продление `paid_until` + запись `method=platega`.
- История платежей по клубу.

### 2.5 Энфорсмент подписки
- Middleware `requireActiveSubscription`: если `paid_until < now` и не trial-grace → клубные API в режиме «только чтение» либо полная блокировка с экраном «продлите подписку» (настраивается).
- Грейс-период (напр. 3 дня) + предупреждающие баннеры в UI клуба за N дней до конца.
- **Критерий:** просроченный клуб не может пробивать чеки; суперадмин видит и продлевает.

**Выход фазы:** вы из админки заводите/настраиваете/удаляете клубы и ведёте подписки.

## ФАЗА 3 — Реорганизация «Настройки заведения» (per-club) · ~1.5–2 недели

> Текущие настройки — плоский `app_settings` (key→value) с одним экраном (`apps/web/src/app/manage/settings/page.tsx`, 181 строка) и `PATCH /system/settings` без защиты секретов (`system.router.ts:52`).

### 3.1 Модель данных настроек клуба
- **Профиль заведения:** Название, Адрес, **Рабочий день** (часы работы), **Бизнес-день** (граница операционных суток — во сколько «закрывается» день для отчётов/смен; влияет на аналитику и смены).
- **Интеграции (секреты):** Админ-бот (токен), Wallet-бот (токен), AI-бот (ключ), СБП/Platega (merchant_id + secret).
- Профиль — в `app_settings`/`club_profile`; секреты — в `integrations` (зашифрованы, 1.6).

### 3.2 API настроек с безопасной заменой секретов
- Разделить эндпоинты: профиль (`PATCH /settings/profile`) и секреты (`PATCH /settings/integrations/:key`).
- **Безопасная замена токена:**
  - GET отдаёт секрет **замаскированным** (`••••1234`, только последние 4), не сам токен.
  - Замена — явное действие на конкретный ключ, с подтверждением; пустое значение = «не менять» (нельзя случайно затереть).
  - Удаление токена — отдельное действие с типизированным подтверждением.
  - Каждая смена секрета пишется в аудит (кто/когда), опционально — повторная аутентификация (пароль/пасскей).
- Валидация формата токенов (Telegram bot token regex, и т.п.) перед сохранением + опциональная проверка «живости» (тестовый `getMe` для бот-токена).

### 3.3 Web: вкладочные настройки
- Реорг `manage/settings/page.tsx` во вкладки: **Заведение** (название/адрес/рабочий день/бизнес-день) · **Интеграции** (боты, AI, СБП — маскированные поля с кнопкой «Заменить» и модалкой-подтверждением) · **Безопасность** (PIN, сессии, пасскеи) · **Резервные копии** · **Опасная зона**.
- Паттерн «нельзя случайно»: секреты read-only по умолчанию, «Заменить» → модалка с предупреждением → ввод нового → подтверждение. Дизайн в духе «тихая роскошь» (один violet-акцент, лево-выровненные заголовки).
- Индикатор статуса интеграции (подключено/ошибка/не настроено).

### 3.4 Семантика «Рабочий день / Бизнес-день»
- Прокинуть «бизнес-день» в смены/аналитику/отчёты (граница суток вместо полуночи). Проверить `dateFmt.ts`, аналитику, смены.

**Выход фазы:** каждый клуб самостоятельно настраивает себя и свои интеграции безопасно.

## ФАЗА 5 — Рост: фичи для продажи подписки (P3) · итеративно

Приоритет по «драйвер продаж новым клубам»:
1. **Онлайн-бронирование зон** с виджетом и предоплатой через Platega/СБП + календарь занятости (БД готова под `EXCLUDE USING gist`). Фича №1 для привлечения клубов.
2. **Публичный QR-самозаказ «со своего телефона»** поверх готового конвейера `pending_orders` — рост среднего чека без планшетов в каждой кабинке.
3. **Рецептуры/техкарты (BOM)** + учёт по весу/объёму — реальная себестоимость бара/кальянной.
4. **Пакеты и капы тарификации времени** (3 часа = N₽, безлимит-вечер, первые 15 мин бесплатно) + абонементы/клубные карты — повторяющаяся выручка клуба.
5. **Триггерный CRM** поверх готовых сегментов: авто-поздравления с ДР (+бонус), реактивация спящих, лист ожидания на пиковые вечера, рейтинг ведущих.
6. **White-label тема под клуб** (логотип/акцент) — апсейл старшего тарифа.
7. **Тарифные планы** Start/Pro/Network с фич-гейтами (привязка к `club_modules`).

## Сквозные задачи

- **Стратегия миграций:** baseline + инкременты; раннер прогоняет control-plane и все клубские БД; идемпотентность обязательна.
- **Бэкапы per-DB:** `backup-db.sh` → цикл по всем `club_*` + `titan_control`; restore по конкретной БД клуба.
- **Деплой:** `deploy.sh` дополнить шагом «реконсайл клубов» (новые миграции по всем БД) + ожидание `/health/ready`.
- **Тесты:** изоляция тенантов (A не видит B), провижининг empty→green, энфорсмент модулей и подписки, безопасная замена секретов, P0-регрессии (скидки, зарплаты, бронь, вебхук).
- **Наблюдаемость:** метрики на клуб (кол-во активных, ошибки), алерты по подпискам (истекают через N дней).
- **Runbook:** провижининг клуба, ротация master-ключа секретов, восстановление БД клуба, отключение/удаление клуба.
