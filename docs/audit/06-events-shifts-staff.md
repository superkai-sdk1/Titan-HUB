# Аудит: Мероприятия, пространства, смены, персонал, зарплата

## Summary

Денежное ядро смен реализовано грамотно: закрытие смены идёт под `FOR UPDATE`-блокировкой строки, расхождения кассы фиксируются обязательной операцией с причиной, выплата зарплаты идемпотентна и согласована со сверкой кассы. Однако зона мероприятий и пространств имеет несколько содержательных дефектов: проверка пересечения событий ломается на «ночных» мероприятиях (через полночь) и на сменах часовых поясов, **POS-аренда пространства вообще не защищена от двойного бронирования** (два открытых чека на один стол/кабинку одновременно), а гранулярные `permissions` сотрудников хранятся, но нигде в API не проверяются. Зарплата считается по жёстко зашитой в код формуле (`700 + …`), не привязана к конкретному сотруднику и доступна на чтение по чужому `staffId`. Для SaaS-модели всё перечисленное усугубляется отсутствием мульти-клубной изоляции: тарифы, формула зарплаты, типы вечеров и пространства — глобальные синглтоны.

## Производственная готовность: 62 / 100

**Обоснование.** Критический денежный путь (открытие/закрытие смены, сверка кассы, выплата ЗП) — зрелый, с транзакциями, блокировками и идемпотентностью: это тянет оценку вверх. Снижают: реальная дыра двойного бронирования пространств в POS (потеря выручки/конфликт), сломанная логика пересечений для ночных событий (ядро анти-кафе работает ночью), неэнфорсимые `permissions` (ложное чувство контроля доступа), утечка зарплатных данных между сотрудниками, хардкод формулы ЗП и тотальная одно-клубность. Для одного клуба в проде система работоспособна с оговорками; для коммерческого SaaS требуется доработка.

## Findings

### 1. [CRITICAL] Двойное бронирование пространства в POS — нет защиты от двух открытых чеков на один стол/кабинку
**Файл:** `apps/api/src/modules/pos/pos.router.ts:547-572` (`POST /checks`), схема `OpenCheckSchema` там же `:53-59`.
Проверка пересечений (`findOverlappingEvent`) есть **только для мероприятий** (`events.router.ts:107-128`). При открытии обычного арендного чека (`spaceId` + `spaceStartAt = now()`) **никакой проверки занятости пространства нет**: можно открыть два (и более) параллельных открытых чека на один и тот же стол/VR/PS5/кабинку. Для мафия-клуба/анти-кафе с поминутной арендой это прямая потеря денег и конфликт (два гостя «арендуют» один стол; биллинг идёт по обоим). Уникального индекса «один открытый чек на space» в схеме нет (`checks.ts:50-51` — `spaceStartAt/spaceEndAt` без ограничений).
**Почему важно:** деньги/операционный конфликт — ядро бизнес-модели почасовой аренды.
**Fix:** перед вставкой проверять `SELECT 1 FROM checks WHERE space_id = $1 AND status='open' LIMIT 1` и возвращать 409 с указанием конфликтующего чека; параллельно добавить частичный уникальный индекс `CREATE UNIQUE INDEX checks_one_open_per_space ON checks (space_id) WHERE status='open' AND space_id IS NOT NULL` (по образцу `032_one_open_shift.sql`) для защиты от гонки. Сделать вставку и проверку в одной транзакции.

### 2. [HIGH] Проверка пересечения событий ломается на ночных мероприятиях и сравнивает время как строку
**Файл:** `apps/api/src/modules/events/events.router.ts:107-128` (`findOverlappingEvent`), `:544-545` (та же проблема при расчёте длительности — там хотя бы есть `+= 24*60`).
Пересечение считается как лексикографическое сравнение строк `start_time`/`end_time` в рамках одной `date`. Два изъяна:
1. **Через полночь.** Событие 22:00–02:00 имеет `endTime < startTime`. Условие `COALESCE(end_time, start_time) >= startA AND start_time <= endA` для такого интервала даёт ложные результаты: ночное событие, заходящее за полночь, либо не поймает реальное пересечение, либо его время вообще «схлопывается». Дата второго дня (02:00 уже завтра) в модели `date+time` как отдельных текстовых полей не учитывается вовсе.
2. **`endTime` отсутствует** (частый кейс — открытое окончание): тогда `endA = startA`, и событие считается «точкой» — следующее событие на ту же зону через 10 минут не поймается как пересечение, хотя по факту зона занята.
**Почему важно:** анти-кафе/мафия работают ночью; именно ночные брони пересекаются чаще всего. Ложно-отрицательная проверка = двойная бронь зоны под мероприятие.
**Fix:** хранить событие как полноценный `tstzrange` (или пара `timestamptz start/end` с переносом конца на след. сутки при `end<=start`) и использовать `&&` (overlap) PostgreSQL-оператор / `EXCLUDE USING gist` constraint. Минимально — детектировать `end<=start` и добавлять сутки к концу перед сравнением, плюс трактовать пустой `endTime` как «занято до конца дня» или требовать `endTime` для titan-событий с `spaceId`.

### 3. [HIGH] Гранулярные `permissions` сотрудника хранятся, но НИГДЕ не проверяются
**Файл:** схема `packages/database/src/schema/profiles.ts:46` (`permissions jsonb`); запись — `apps/api/src/modules/staff/staff.router.ts:35-41,137-166` (`UpdateStaffSchema.permissions`). Энфорсмента нет: `grep` по API находит `permissions` только в SELECT/UPDATE стаффа; middleware (`apps/api/src/middleware/auth.ts:64-72`) реализует исключительно `requireRole(...roles)` по полю `role`.
Владелец в UI настраивает галочки прав доступа, но API их полностью игнорирует — доступ определяется только грубой ролью `owner`/`staff`. Это ложное чувство безопасности: «ограниченному» сотруднику по факту доступно всё, что доступно роли `staff`.
**Почему важно:** контроль доступа к данным персонала/деньгам — это и прод-, и SaaS-требование; настройка, которая визуально работает, но не действует, опаснее её отсутствия.
**Fix:** либо ввести `requirePermission('key')`-middleware, читающий `user.permissions`/профиль и проверяющий конкретное право (и встроить его в чувствительные роуты), либо убрать UI прав до реализации. Права должны попадать в JWT или подгружаться из БД по `sub`.

### 4. [HIGH] Утечка зарплатных данных: `staff` может прочитать выручку и расчётную ЗП другого сотрудника
**Файл:** `apps/api/src/modules/salary/salary.router.ts:59,78` (`GET /salary/estimate`, `requireRole('owner','staff')`, `staffId = c.req.query('staffId') ?? user.sub`).
Эндпоинт расчёта доступен роли `staff`, и `staffId` берётся из произвольного query-параметра без проверки, что это «я». Любой сотрудник может запросить `?staffId=<чужой_uuid>` и узнать выручку и рассчитанную зарплату коллеги. (Списки `GET /salary` и `POST /salary/pay` корректно ограничены `owner` — здесь проблема только в `estimate`.)
**Почему важно:** конфиденциальность зарплат; в РФ это чувствительные данные, в SaaS — нарушение между арендаторами тем более.
**Fix:** для роли `staff` игнорировать переданный `staffId` и форсить `user.sub` (`const staffId = user.role === 'owner' ? (query.staffId ?? user.sub) : user.sub`).

### 5. [MEDIUM] Хардкод формулы зарплаты в коде (дублирован на фронте и бэке), не привязан к сотруднику/часам
**Файл:** `apps/api/src/modules/salary/salary.router.ts:19-22` (`calculateSalary`), дубликат `apps/web/src/lib/salary.ts:1-3`.
Формула `revenue<=7000 ? 700 : 700 + ceil((revenue-7000)/1000)*100` зашита в двух местах. Проблемы: (а) не настраивается владельцем (разные клубы платят по-разному — для SaaS это блокер); (б) расчёт идёт от **выручки клуба за бизнес-день**, а не от вклада конкретного сотрудника — если в смене двое, формула выдаст одинаковую сумму обоим, завышая ФОТ; (в) для ролей ведущего/гейм-мастера (host/game-master) нет ни почасовой ставки, ни ставки за вечер — модель ЗП не покрывает специфику мафия-клуба, где ведущий оплачивается за игру/вечер.
**Почему важно:** деньги (ФОТ) + прямой блокер мульти-клубной продажи.
**Fix:** вынести параметры формулы в `app_settings`/таблицу `salary_rules` (база, шаг, ставка за шаг, порог); добавить тип оплаты «за смену/за час/за вечер» и роль-специфичные ставки (ведущий). Держать одну реализацию (общий пакет), а не копию на фронте.

### 6. [MEDIUM] `OpenShiftSchema` отвергает кастомные типы вечеров, которые сам же продукт позволяет создавать
**Файл:** `apps/api/src/modules/shifts/shifts.router.ts:17-22` (`eveningType: z.enum([...5 фикс. значений])`).
Миграция `025_tariffs_evening_types.sql:7-15,42-48` ввела управляемый справочник `evening_types` (владелец создаёт/удаляет типы), а колонка `shifts.evening_type` переведена в `text` (`shifts.ts:34-35`). Но Zod-схема открытия смены по-прежнему хардкодит исходные 5 ключей. Если владелец создаст новый тип вечера, открыть смену с ним нельзя — `zValidator` вернёт 400.
**Почему важно:** функция справочника заявлена, но частично нерабочая; пользователь упрётся в неочевидную ошибку валидации.
**Fix:** заменить `z.enum` на `z.string()` с проверкой существования ключа в `evening_types` (или `z.string().min(1)` + FK-валидация в сервисе).

### 7. [MEDIUM] Мягкое удаление пространства не разрывает активные брони и не чистит привязки
**Файл:** `apps/api/src/modules/spaces/spaces.router.ts:52-55` (`DELETE` → `isActive=false`).
Деактивация пространства не проверяет, есть ли открытые чеки/активные мероприятия на этой зоне. `events.spaceId` ссылается на `spaces.id` без `ON DELETE`-стратегии (`events.ts:21`), а арендный чек продолжит тарифицироваться по `hourlyRate` уже неактивной зоны. Удалённую зону можно «потерять» вместе с идущей арендой.
**Почему важно:** операционные «висяки», потенциально неверный биллинг по скрытой зоне.
**Fix:** при деактивации проверять отсутствие открытых чеков/активных событий на зоне (или предупреждать), и/или запрещать деактивацию занятого пространства.

### 8. [MEDIUM] Расчёт ЗП за бизнес-день жёстко завязан на МСК (UTC+3) — нет настройки часового пояса
**Файл:** `apps/api/src/modules/salary/salary.router.ts:66-67,86-87` (`new Date(\`${day}T09:00:00+03:00\`)`), аналогично `getBirthdaysToday` `apps/api/src/modules/shifts/shifts.service.ts:144-147` (`Date.now()+3*3600*1000`).
Бизнес-день (09:00→06:00) и дни рождения вычисляются по фиксированному смещению +03:00. Для одного московского клуба корректно, но: (а) при сезонных/региональных особенностях это уже неверно для клуба в другом поясе; (б) граница бизнес-дня 09:00 захардкожена — клуб с другим графиком получит «съехавшую» выручку и ЗП.
**Почему важно:** прямая корректность денег для не-МСК клубов (SaaS).
**Fix:** хранить таймзону и час начала бизнес-дня в настройках (per-club для SaaS) и строить границы по ним.

### 9. [LOW] `closedBy`/`openedBy` фиксируют лишь одного сотрудника на смену — нет учёта нескольких работников
**Файл:** `packages/database/src/schema/shifts.ts:26-30`, `apps/api/src/modules/shifts/shifts.service.ts:44,119`.
Смена знает только кто открыл и кто закрыл. В клубе на одной смене часто работают несколько (ведущий + бариста + хостес). Это согласуется с тем, что ЗП считается «на смену», но не позволяет ни корректно распределить ФОТ, ни вести табель/график (host/game-master scheduling из ТЗ не реализован вовсе).
**Почему важно:** нет данных для графиков смен и справедливого расчёта ЗП — функциональный пробел, а не баг.
**Fix:** таблица `shift_staff (shift_id, profile_id, role, check_in, check_out)`; ЗП считать по участникам смены.

### 10. [LOW] `participationFee`/`prizeFund` и др. суммы без верхней границы — риск переполнения numeric и абуза
**Файл:** `apps/api/src/modules/events/events.router.ts:67-82` (`EventSchema`: `fixedAmount/manualAmount/participationFee/prizeFund/...` — `z.number()` без `.max()`).
В отличие от `SpaceSchema` (`spaces.router.ts:13-14`, где явные `.max(1_000_000)`), денежные поля события не ограничены сверху. `participationFee`/`prizeFund` — `numeric(12,2)` (`events.ts:41-44`), `fixedAmount` — `numeric(10,2)`: огромное значение упадёт ошибкой БД (некрасиво) либо пройдёт абсурдная сумма в чек/расход.
**Почему важно:** устойчивость к ошибкам ввода/абузу, единообразие с уже принятым в `spaces`.
**Fix:** добавить `.min(0).max(...)` на денежные поля `EventSchema` (и согласовать с precision колонок).

### 11. [LOW] `tablet-link-code` генерируется через `Math.random()` и создаёт новое Redis-соединение на каждый вызов
**Файл:** `apps/api/src/modules/spaces/spaces.router.ts:64-71`.
6-значный код привязки планшета берётся из `Math.random()` (не криптостойко) и хранится 5 минут; на каждый запрос поднимается отдельный `new Redis(...)` вместо общего пула (`getSharedRedis()` используется в middleware). Перебор 10⁶ кодов за 5 минут маловероятен, но код привязывает планшет к зоне — лучше крипто-случайность; отдельные коннекты — мелкая утечка ресурсов под нагрузкой.
**Почему важно:** низкий риск безопасности + гигиена ресурсов.
**Fix:** `crypto.randomInt(100000, 1000000)`; переиспользовать `getSharedRedis()`; завести rate-limit на эндпоинт.

## Что сделано хорошо (подтверждено чтением кода)

- **Закрытие смены — образцово.** `closeShift` (`shifts.service.ts:84-140`): всё в одной транзакции с `FOR UPDATE` на строке смены, повторная проверка статуса и открытых чеков, расчёт остатка под блокировкой — защищает от гонки с webhook-оплатой Platega и двойного закрытия.

- **Один открытый шифт гарантирован на уровне БД** — частичный уникальный индекс `032_one_open_shift.sql`, ловится код `23505` (`shifts.service.ts:66-72`).

- **Рейтинг и статистика ведущих** (сколько игр провёл, средний чек на его сменах) — геймификация для персонала.
- **Повторяющиеся мероприятия** (еженедельная «Городская мафия» по пятницам) — генерация серии броней одним действием.

## SaaS / мульти-клубные импликации для этой зоны

Подтверждено `grep`-ом: ни одна таблица зоны (`events`, `spaces`, `shifts`, `salary_payments`, `cash_operations`, `evening_types`, `event_hourly_rates`, `tariffs`) **не имеет колонки tenant/club/org** — система строго одноклубная. Конкретные последствия для продажи другим клубам:

- **`event_hourly_rates` (PK = `hours`)** и **`evening_types` (PK = `key`)** — глобальные синглтоны. Два клуба не могут иметь разные почасовые тарифы мероприятий или разные наборы типов вечеров: `event_hourly_rates.hours` — первичный ключ без `club_id`.
- **Один открытый шифт на всю БД** (`shifts_one_open` — индекс по `status` без `club_id`). В мультиарендной БД это означало бы, что одновременно во всей системе может быть открыта лишь одна смена — фатально.
- **Формула ЗП зашита в код** для всех — продать клубу с другой схемой оплаты нельзя без передеплоя.
- **Бизнес-день и таймзона зафиксированы как МСК** — клуб в другом часовом поясе получит неверные границы выручки/ЗП (находка 8).
- **`permissions` не энфорсятся** (находка 3) — для multi-tenant это вдвойне опасно: нет рабочего слоя разграничения доступа даже внутри одного клуба.
- **Пространства/зоны глобальны** — нужен `club_id` на `spaces`, `events`, и на проверки пересечений/занятости (находки 1, 2), иначе зоны разных клубов смешаются.

**Вывод по зоне для SaaS:** до мультиарендности требуется (1) добавить `club_id` во все перечисленные таблицы и во все WHERE/уникальные индексы (включая `shifts_one_open`, `event_hourly_rates`, `evening_types`); (2) сделать тарифы мероприятий, формулу ЗП, таймзону и час начала бизнес-дня настройками уровня клуба; (3) реализовать рабочий слой прав. Это крупная, но обязательная работа — текущая архитектура зоны к продаже нескольким клубам не готова.
