# Аудит: Архитектура фронтенда и состояние

## Summary

Фронтенд Titan HUB (Next.js 15 App Router PWA, React 19) построен зрело: единый источник навигации, единый `StateView` для loading/empty/error, react-query как основной слой данных (30 страниц), грамотная защита сессии (PIN/Passkey, lock по бездействию, разблокировка только своего профиля), корректная запись свежего чека в кэш и продуманная защита оплаты от двойного списания и гонки с вебхуком Platega. Однако есть несколько реальных дефектов, опасных именно в продакшене кассы: SSE-поток уведомлений «умирает» после первого сетевого сбоя (одноразовый тикет + опора на авто-реконнект браузера), flow обновления Service Worker может уронить активного кассира на «Failed to load chunk» без graceful-reload, offline-fallback ссылается на несуществующий роут `/offline`, а единственный глобальный ErrorBoundary сбрасывает весь интерфейс (включая открытый чек) при любой ошибке рендера. Плюс системные долги: shared-типы `@titan/types` не используются во фронтенде вообще (250+ `any`), нулевое code-splitting при компонентах на 2400 строк, и 13 legacy-роутов-редиректов в `manage/*`.

## Production-readiness score: 68 / 100

**Обоснование.** База солидная и большинство денежных путей защищены (оплата, гонка с вебхуком, double-submit). Минус баллы за: (1) хрупкий SW update-flow на боевой кассе, (2) тихую смерть live-уведомлений после сетевого сбоя, (3) отсутствие route-level error boundaries и битый offline-fallback, (4) системный долг по типобезопасности и бандлу, который станет блокером при масштабировании на множество клубов (SaaS). Ни одного дефекта «потеря денег прямо сейчас» не найдено — поэтому не ниже 60; но перечисленное надо закрыть до коммерческого запуска — поэтому не выше 70.

## Findings

### 1. [HIGH] Live-поток уведомлений умирает после первого сетевого сбоя
**Файлы:** `apps/web/src/lib/sse.ts:8-13`, `apps/web/src/components/NotificationsProvider.tsx:182-198`
`openSse()` берёт **одноразовый** тикет с TTL 60с и открывает `EventSource(.../stream?ticket=...)`. В `onerror` стоит комментарий «EventSource реконнектится сам» и больше ничего. Но браузер при авто-реконнекте дёргает **тот же URL с уже истёкшим/израсходованным тикетом** → сервер ответит 401 → поток окончательно закрывается. После любого блипа Wi-Fi (а на iPhone-PWA это норма: блокировка экрана, переключение сети) кассир перестаёт получать живые уведомления (заказы гостей, события) до полной перезагрузки страницы — молча, без индикатора.
**Почему важно:** в анти-кафе/мафия-клубе поток заказов от гостя в чек — операционно-критичный канал; «тихая» потеря = пропущенные заказы и претензии гостей.
**Фикс:** реализовать собственный реконнект: на `onerror` вызвать `es.close()`, и через backoff (1с→2с→5с, с jitter) заново вызвать `openSse()` (новый тикет). Останавливать при `document.hidden`, возобновлять на `visibilitychange`. Тот же паттерн нужен для SSE в `CheckChat`/`CheckDetailView` (поток событий чека).

### 2. [HIGH] Flow обновления Service Worker может уронить активного кассира
**Файлы:** `apps/web/public/sw.js:15-33`, `apps/web/src/components/ServiceWorkerRegister.tsx`, `apps/web/src/app/manage/about/page.tsx:254-268`
SW делает `skipWaiting()` на install и `clients.claim()` на activate — то есть новый воркер мгновенно перехватывает уже открытую вкладку со **старым** JS. При этом:
- В `sw.js` **нет** `message`-листенера на `SKIP_WAITING` → строка `reg.waiting?.postMessage({ type: 'SKIP_WAITING' })` (about/page.tsx:262) — мёртвый код.
- В `ServiceWorkerRegister` **нет** слушателя `controllerchange`, который перезагрузил бы страницу при смене контроллера.

Сценарий боли: во время деплоя у кассира открыта вкладка на старой сборке; новый SW активируется и claim'ит вкладку; пользователь открывает модалку/переходит на роут, который тянет lazy-чанк со старым хэшем → 404 → `ChunkLoadError` → срабатывает глобальный ErrorBoundary (см. п.3) и весь экран сбрасывается. На iPhone-PWA вкладки живут сутками — вероятность высокая.
**Почему важно:** деплой может «убить» интерфейс активного кассира в середине обслуживания.
**Фикс:** (а) добавить в `sw.js` `self.addEventListener('message', e => { if (e.data?.type === 'SKIP_WAITING') self.skipWaiting() })` и **убрать безусловный `skipWaiting()` из install**; (б) в регистрации слушать `reg.onupdatefound` → показывать ненавязчивый тост «Доступна новая версия — обновить», и только по клику слать `SKIP_WAITING`; (в) на `navigator.serviceWorker.addEventListener('controllerchange', () => location.reload())` с защитой от двойного reload. Это превращает деплой в управляемое пользователем обновление вместо случайного краша.

### 3. [HIGH] Нет route-level error boundaries; единственный ErrorBoundary сбрасывает весь интерфейс
**Файл:** `apps/web/src/app/providers.tsx:8-33` (и отсутствие `app/**/error.tsx`)
Единственный ErrorBoundary обёрнут на самом верху дерева. Любая ошибка рендера на любой странице (в т.ч. `ChunkLoadError` из п.2, или необработанный кейс в `CheckDetailView`) роняет **весь** экран в «Что-то пошло не так» с кнопкой полной перезагрузки. Открытый чек, незакоммиченные данные модалки, шаг оплаты — теряются. В App Router нет ни одного `error.tsx` (проверено: `grep error.tsx` → пусто).
**Почему важно:** одна ошибка на второстепенном виджете дашборда выкидывает кассира из активного чека.
**Фикс:** добавить `app/error.tsx` (глобально) и точечные `app/pos/error.tsx`, `app/pos/[checkId]/error.tsx`, `app/manage/error.tsx`, `app/dashboard/error.tsx` с локальным `reset()` вместо `location.reload()` — ошибка изолируется в своём сегменте, остальной интерфейс живёт. Специально обработать `ChunkLoadError` (имя ошибки) → тихий `location.reload()`.

### 4. [MEDIUM] Offline-fallback ссылается на несуществующий роут `/offline`
**Файл:** `apps/web/public/sw.js:129-138`
`networkFirst` при оффлайне и HTML-навигации пытается отдать `cache.match('/offline')`, но роута `/offline` в `app/` нет (проверено). В итоге пользователь оффлайн получает сырой JSON `{"error":"Offline"}` со статусом 503 вместо понятной страницы. PWA-обещание «работает оффлайн» не выполняется на навигации.
**Почему важно:** для PWA, которую владелец тестирует на реальном iPhone, оффлайн-экран — часть базового UX и доверия к продукту.
**Фикс:** создать `app/offline/page.tsx` (статичная страница «Нет сети, переподключаемся») и прекэшировать её на install SW, либо убрать недостижимую ветку и отдавать корректный кэш корня.

### 5. [MEDIUM] `reorderItems` без `onError` — тихий рассинхрон порядка позиций меню
**Файл:** `apps/web/src/app/manage/menu/page.tsx:273-276` (ср. с `reorderCats:278-282` и `moveItem:284-287`, у которых `onError` есть)
Drag-n-drop сортировки позиций оптимистично пишет локальный `setSortedItems` (строки 330-334). Мутация `reorderItems` при ошибке сети **не откатывает** оптимистичное состояние и не показывает тост и не инвалидирует кэш — в отличие от соседних `reorderCats`/`moveItem`. Кассир видит «сохранённый» порядок, которого на сервере нет; после перезагрузки порядок прыгает обратно.
**Почему важно:** немой рассинхрон состояния — кассир уверен, что меню переставлено, а оно нет.
**Фикс:** добавить `onError: () => { show('Не удалось изменить порядок', 'error'); qc.invalidateQueries({ queryKey: ['menu', 'items'] }) }` по образцу `reorderCats`.

### 6. [MEDIUM] Shared-типы `@titan/types` не используются во фронтенде — 250+ `any` на границе API
**Файлы:** весь `apps/web/src` (`grep '@titan/types' apps/web/src` → 0 импортов кода; пакет лишь в `transpilePackages`)
Пакет `@titan/types` (enums, roles, zod-schemas) подключён в API, но во фронтенде **не импортируется ни разу**. Типы ответов API объявлены инлайн и в основном через `any`: `: any` — 249 вхождений, `<any>` — 62, паттерн `api.get<{ shift: any }>` — ~50. Контракт API↔UI держится «на честном слове».
**Почему важно (особенно для SaaS):** при продаже многим клубам и эволюции API любое переименование поля молча проходит мимо компилятора и всплывает рантайм-ошибкой у клиента. Это главный долг по сопровождаемости.
**Фикс:** вывести response-типы (или хотя бы zod-схемы ответов) в `@titan/types`/`@titan/contracts`, импортировать их в `lib/api.ts`-обёртки и хуки. Поэтапно: начать с денежных путей (`CheckData`, `SplitPart`, shift, payments), заменив инлайн-`any`.

### 7. [MEDIUM] Нулевое code-splitting при компонентах-гигантах
**Файлы:** `apps/web/src/components/CheckDetailView.tsx` (2406 строк), `app/dashboard/page.tsx` (1829), `app/pos/page.tsx` (1372), `components/Icon.tsx` (1261); `grep next/dynamic|React.lazy` → 0
Ни одного `next/dynamic`/`lazy()`. Тяжёлые редко-используемые куски (графики дашборда, drag-n-dnd `@dnd-kit`, `framer-motion`-анимации, шторки оплаты `CheckDetailView`) попадают в общий бандл. Для iPhone-PWA по мобильной сети это медленный первый запуск кассы — самого критичного экрана.
**Почему важно:** время до интерактивности кассы напрямую влияет на скорость обслуживания; на слабом 4G лишние сотни КБ ощутимы.
**Фикс:** обернуть в `next/dynamic` тяжёлые модальные/вкладочные части: платёжные шторки `CheckDetailView`, графики дашборда, `manage/menu` drag-редактор. `Icon.tsx` на 1261 строку — вероятно инлайн-словарь SVG; вынести в отдельный чанк или генерировать спрайт.

### 8. [LOW] ~38 мутаций без `onError`; `pay` (путь «0 ₽») без обработки ошибки
**Файлы:** по проекту 135 `useMutation`, 97 c `onError`; напр. `CheckDetailView.tsx:815-827` (`pay`) — без `onError`
Основной денежный путь оплаты идёт через `finishPayment` (`:905-934`) с корректной обработкой ошибки и гонки вебхука — это хорошо. Но прямой вызов `pay.mutate(...)` для закрытия чека на 0 ₽ (`:1375`) полагается только на `pay.isPending` для блокировки кнопки; при сетевой ошибке пользователь не увидит причину (хотя `isPaid` не выставится, и кнопка вернётся). Часть второстепенных мутаций тоже молчит при ошибке.
**Почему важно:** не критично (денег это не теряет), но ухудшает диагностируемость для персонала.
**Фикс:** добавить `onError: toastError` к `pay` и провести ревизию мутаций без `onError` — как минимум во всех денежных/сменных модулях.

### 9. [LOW] 13 legacy-роутов-редиректов и недостижимый из меню `/manage/refunds`
**Файлы:** `apps/web/src/app/manage/{security,expenses,spaces,discounts,certificates,deposits,ai,supplies,bonuses,cashops,notifications,debtors,revision}/page.tsx` (все — клиентские `router.replace`), `apps/web/src/app/manage/refunds/page.tsx` (301 строка, живой, но не в `nav.ts`)
13 страниц `manage/*` — это клиентские редирект-заглушки на новые объединённые экраны. Они работают, но: (а) дают «вспышку» пустого экрана перед `replace` (клиентский редирект вместо `redirect()`/middleware); (б) раздувают карту роутов и сбивают навигацию по коду. Отдельно `manage/refunds` — полноценная страница (301 строка), убранная из `nav.ts`, но достижимая по прямому URL/закладке — «полу-мёртвый» функционал без точки входа.
**Почему важно:** для SaaS чистая карта роутов важна для предсказуемости и онбординга; «вспышки» редиректов выглядят непрофессионально на iPhone.
**Фикс:** заменить клиентские заглушки на серверный `redirect()` в Server Component (без мигания) либо на `redirects()` в `next.config`. По `refunds` — решить явно: вернуть в меню под фиче-флагом или удалить роут.

### 10. [LOW] `staleTime` 2 мин + `refetchOnReconnect` не настроен — риск устаревших чеков после блипа
**Файл:** `apps/web/src/app/providers.tsx:39-47`
Глобально `staleTime: 2min`, `refetchOnWindowFocus: true`, но `refetchOnReconnect` явно не задан (по умолчанию в react-query он `true`, так что сеть восстановит данные). Активные чеки страхуются `refetchInterval: 5000` (`pos/page.tsx:212`) — это ок. Замечание скорее на будущее: для чисто событийных списков без интервала (балансы, долги) 2-минутный `staleTime` после возврата из блокировки экрана может показать устаревшие суммы до фокус-рефетча.
**Почему важно:** низкий риск, но для денежных списков стоит явно задать `refetchOnReconnect: 'always'`.
**Фикс:** явно выставить `refetchOnReconnect: true` в дефолтах и точечно `staleTime: 0` для денежных списков (балансы/долги/депозиты).

## Что сделано хорошо (не требует правок)

- **Защита оплаты от двойного списания и гонки с вебхуком Platega** — `CheckDetailView.tsx:905-934` (`isProcessing`-guard + сверка статуса чека) и `:606-638` (поллинг QR со сверкой `closed`). Образцовая обработка денежного пути.
- **`writeCheck` через `setQueryData`** (`:642`) вместо invalidate+refetch — мгновенный отклик корзины без сетевой задержки.
- **Безопасность сессии:** разблокировка строго своего профиля по `userId` (`SessionLock.tsx:73-84, 111-114`), lock на каждом холодном старте (`auth.store.ts:77-88`), исключение планшетов-киосков. Логаут не зацикливается на 401 (комментарий и обход api-клиента, `auth.store.ts:47-54`).
- **SSE без JWT в URL** — одноразовый тикет (`sse.ts`), JWT не утекает в логи nginx. Концепция верная (баг — только в реконнекте, п.1).
- **SW не кэширует `/api/`** (`sw.js:50-52`) — данные балансов/чеков не оседают в кэше и не утекают между сессиями на киоске. Это правильное решение для мульти-смены на одном устройстве.
- **Единые `StateView` и `nav.ts`** — устранено дублирование loading/empty/error и списков навигации.

## Идеи новых фич (для мафия-клубов / анти-кафе)

1. **Офлайн-очередь чека (write-behind).** Открытие чека и добавление позиций при пропаже сети складывать в IndexedDB и синхронизировать при возврате связи — анти-кафе с плохим Wi-Fi не теряют заказы. Сейчас SW намеренно не кэширует `/api/`, так что мутации оффлайн просто падают.
2. **«Стол/зона в реальном времени» через тот же SSE.** Live-карта занятости кабинок/залов на одном экране для админа (кто за каким столом, таймеры аренды) — у вас уже есть таймеры в `pos/page.tsx` и SSE-инфраструктура.
3. **Индикатор «новая версия доступна».** Превратить п.2 findings в фичу: ненавязчивый тост обновления PWA повышает доверие при коммерческой эксплуатации.
4. **Звуковой/вибро-сигнал нового заказа гостя** даже когда вкладка в фоне (через Web Push, который уже есть в `sw.js`) — для шумного зала.
5. **Быстрый «режим турнира/события»** — отдельный лёгкий экран с минимумом данных (только активные столы + таймеры), грузящийся быстро на слабом устройстве; кандидат №1 на code-splitting.

## SaaS / мульти-клуб: последствия для этой области

- **Типобезопасность контракта (п.6) — главный SaaS-риск этой области.** При обслуживании множества клубов с разными версиями PWA на iPhone (SW кэширует сборку надолго) расхождение клиента и API неизбежно. 250+ `any` означают, что несовместимость всплывёт рантайм-крашем у клиента, а не на CI. Shared-контракты в `@titan/types` + версионирование API — обязательны до продажи.
- **SW update-flow (п.2) масштабируется в инцидент.** На одном владельце «случайный краш при деплое» терпим; на сотне клубов это шквал тикетов поддержки при каждом релизе. Управляемое обновление с тостом и `controllerchange`-reload — предпосылка для безопасных частых деплоев в SaaS.
- **Бандл и code-splitting (п.7) — стоимость онбординга.** Новый клуб впервые открывает кассу по мобильной сети; «тяжёлый» первый запуск — плохое первое впечатление и фактор оттока. Split критичных vs. редких экранов снижает time-to-interactive.
- **Изоляция арендатора в состоянии.** Сейчас стор однопользовательский (`titan-auth` в localStorage, без `clubId`/`tenantId`). При мультитенантности ключи react-query (`['checks','active']`, `['menu','items']` и т.п.) должны включать идентификатор клуба, иначе кэш одного клуба «протечёт» в другой при переключении/общем устройстве. Сейчас это не баг (single-tenant), но прямой блокер мультиклубности — закладывать `tenant` в queryKey и в `name` persist-стора заранее.
- **Чистая карта роутов (п.9)** упрощает фиче-флаги по тарифным планам подписки (включать/выключать модули per-club) — 13 «теневых» редиректов и недостижимый `refunds` этому мешают.
