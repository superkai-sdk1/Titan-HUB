# Аудит: Мультитенантность и готовность к SaaS-подписке

## Summary

Titan HUB на сегодня — **строго одно-клубное (single-tenant) приложение**. Во всей схеме БД (`packages/database/src/schema/*`) нет ни одной колонки изоляции арендатора (`tenant_id` / `club_id` / `venue_id` / `org_id`) — проверено grep'ом по схеме и всему `apps/api/src` (0 совпадений). JWT несёт только `sub/role/nickname` без клейма арендатора (`packages/auth/src/jwt.ts:14-20`), все запросы фильтруют исключительно по ID сущности/статусу/дате (напр. `inventory.router.ts:23` — глобальный `SELECT … WHERE deleted_at IS NULL`), а `app_settings` — глобальный key→value стор на весь инстанс (`notifications.ts:52`). Никакой подписочной/биллинговой модели (планы, лимиты, триалы, оплата самой подписки), онбординга арендатора и пер-клубного брендинга **не существует**. Это **ключевой блокер роста**: продать продукт второму клубу сейчас можно только подняв отдельный инстанс БД+API на каждого (db-per-tenant вручную), что не масштабируется как SaaS.

## Production-readiness score: 8 / 100

Обоснование: для текущей цели (один клуб владельца) архитектура работает корректно. Но **заявленная цель — SaaS-подписка для других клубов** — не поддержана ничем: нет изоляции данных, нет биллинга, нет онбординга, нет пер-арендаторного RBAC и конфига. Это не «доработка», а смена фундамента данных. Балл низкий именно относительно цели SaaS. Если бы цель была «один клуб» — было бы ~75.

## Стратегия изоляции арендатора (рекомендация)

**Выбор: `tenant_id` (row-level, shared DB) + Postgres RLS.** Обоснование под этот проект:

- **db-per-tenant** — самый сильный изолятор, но для PWA на одном VPS (см. ops: VPS уже перегружается на сборке) это операционно неподъёмно: N инстансов миграций, бэкапов, коннект-пулов. Отложить как премиум-опцию для крупных сетей.
- **schema-per-tenant** — компромисс, но усложняет миграции (047 файлов × N схем), Drizzle и пулинг; ledger/идемпотентность и так на месте.
- **row-level `tenant_id` + RLS** — лучший баланс для текущего масштаба. RLS (`CREATE POLICY … USING (tenant_id = current_setting('app.tenant_id')::uuid)`) даёт защиту в самой БД — даже забытый `WHERE` в коде не утечёт. Middleware делает `SET LOCAL app.tenant_id` на коннекте/транзакции из JWT-клейма `tid`.

### Таблицы, требующие `tenant_id` (полный список из схемы)

`profiles`, `client_tiers`, `spaces`, `customers`, `menu_categories`, `inventory`, `modifiers`, `tariffs`, `checks`, `check_items`, `check_item_modifiers`, `check_payments`, `check_discounts`, `pending_orders`, `chat_messages`, `discounts`, `client_discount_rules`, `certificates`, `transactions`, `bonus_history`, `bonus_lots`, `supplies`, `supply_items`, `supply_corrections`, `analytics_events`, `stock_movements`, `expenses`, `refunds`, `salary_payments`, `cash_operations`, `revisions`, `revision_items`, `shifts`, `evening_types`, `events`, `notifications`, `user_notification_settings`, `push_subscriptions`, `app_settings`, `passkeys`, `tg_link_requests`. (Платформенные таблицы `tenants`, `plans`, `subscriptions`, `platform_users`, `_migrations` — без `tenant_id`.)

## Фазовый план миграции (оценка усилий)

- **Фаза 0 — Подготовка (1–2 нед):** ввести `tenants`, `platform_users`, дефолтный «tenant 0» для существующего клуба, бэкфилл. Риск: низкий (ничего не ломаем, колонки nullable→backfill→NOT NULL).
- **Фаза 1 — `tenant_id` везде + RLS (3–5 нед):** добавить колонку во все таблицы (список выше), индексы `(tenant_id, …)`, RLS-политики, составные UNIQUE (#5), `app_settings` PK (#6). Риск: высокий — затрагивает все запросы; обязательны интеграционные тесты на утечку.
- **Фаза 2 — Скоуп в коде + JWT `tid` (2–4 нед):** `tid` в токене, контекст `tenantId`, `SET LOCAL app.tenant_id` в middleware, аудит каждого `.where()`. Закрыть ИИ-text-to-SQL (#3). Риск: высокий.
- **Фаза 3 — Биллинг и подписка (3–5 нед):** `plans/subscriptions`, гейт доступа, триал, рекуррентная оплата (ЮKassa/CloudPayments), пер-клубный эквайринг (#8). Риск: средний.
- **Фаза 4 — Онбординг/провижининг + конфиг/брендинг (2–3 нед):** self-serve `signup`, сидер справочников, пер-клубный брендинг в `app_settings`, экспорт/удаление (#10). Риск: средний.

**Итого: ~3–4.5 месяца** силами 1 fullstack-разработчика. Главный риск — перекрёстная утечка при неполном скоупе; митигируется RLS (защита в БД) + автотесты «арендатор A не видит данные B».

## Идеи фич (для мафия-клубов / анти-кафе)

- **Сеть клубов под одним владельцем:** иерархия `tenant` → филиалы, сводная аналитика по сети, перенос остатков/тарифов между точками.
- **Маркетплейс шаблонов:** готовые наборы «типы вечеров / тарифы / меню» для нового клуба в один клик (ускоряет онбординг).
- **Пер-клубный брендинг гостевого планшета и Wallet-бота:** логотип/цвет клуба (в рамках «тихой роскоши» — допускать только смену акцента и лого, не ломать backdrop-filter).
- **Реферальная программа между клубами:** клуб приводит клуб → скидка на подписку (виральный рост в нише).
- **Тариф «по объёму»:** план привязан к числу столов/часов/чеков в месяц — естественные лимиты для анти-кафе.

## Quick wins (<1 ч)

- Добавить в JWT-клейм поле `tid` (пока = «tenant 0») и прокидывать в контекст `requireAuth` — заранее, чтобы код привык к `ctx.tenantId` (`auth.ts`, `jwt.ts`). Без БД-изменений.
- Завести таблицу `tenants` (id, name, created_at, status) и один сид-ряд для текущего клуба — каркас, ни на что не влияет.
- Префиксовать Redis-ключи `t:{tid}:` в `revoked:`/`sse:` (auth.ts) — дешёвая будущая защита.
- **Зафиксировать в README/доке: «ИИ text-to-SQL (`ai.router.ts`) НЕ включать для второго арендатора до RLS»** — предотвращает катастрофическую утечку при пилоте.

## SaaS / multi-club implications

Это **центральный блокер** монетизации. Без row-level `tenant_id` + RLS продукт нельзя продать второму клубу безопасно — только дорогой db-per-tenant вручную. Биллинг, онбординг, пер-клубный конфиг и экспорт/удаление ПДн (152-ФЗ) — обязательны для коммерческого запуска. Особое внимание: TITAN AI text-to-SQL и глобальный `app_settings` — два места, где мультитенантность ломается тише всего и опаснее всего (утечка/перезапись чужих данных). RLS в Postgres — рекомендуемая «страховка от забытого WHERE».
