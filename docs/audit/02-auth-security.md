# Аудит: Аутентификация и безопасность

## Summary

Базовая гигиена аутентификации в Titan HUB заметно выше среднего для продукта такого размера: JWT-секрет обязателен и проверяется на старте, PIN/пароли хэшируются bcrypt, есть rate-limit, отзыв токенов через Redis-blacklist, anti-replay для Telegram initData, magic-byte-проверка загрузок, защита от IDOR для планшетов в POS, маскирование токенов в логах и обобщённые ошибки наружу. Однако для **коммерческого SaaS** есть структурные блокеры: приложение **полностью одно-тенантное** (нет изоляции клубов — любой staff-токен видит все данные всех будущих клиентов), основной секрет персонала — **4-значный PIN** с глобальным счётчиком-фоллбеком, который сам по себе является вектором DoS-блокировки всего персонала, JWT хранится в `localStorage` (XSS-эксфильтрация) с TTL 7–30 дней и без отзыва при смене роли/пароля, а `requireAuth` работает **fail-open** при недоступности Redis. Для продакшна одного клуба система пригодна после устранения quick-wins; для SaaS требуется полноценный re-design модели тенантов и сессий.

## Production-readiness score: 62 / 100

**Обоснование.** Для **одиночного клуба** (текущая модель) — крепкая «4-» (около 72): нет очевидных дыр на чтение/запись чужих данных в пределах ролей, деньги защищены транзакциями и блокировками, секреты не хардкодятся. Но оценку тянут вниз системные вещи, критичные именно для коммерции и масштабирования: одно-тенантность (для SaaS — блокер), слабый PIN как первичный фактор персонала, `localStorage`-JWT без серверной инвалидации сессий по событию, fail-open авторизация при падении Redis, отсутствие журналирования событий безопасности (аудита входов/смены прав). Итоговая взвешенная оценка с учётом цели «продать другим клубам» — **62**.

## Findings

### CRITICAL

#### C1. Полное отсутствие изоляции тенантов (multi-club) — блокер SaaS
- **Где:** все роутеры `apps/api/src/modules/*/*.router.ts`; схема `packages/database/src/schema/*`; JWT-payload `packages/auth/src/jwt.ts:14` (`{ sub, role, nickname }` — нет `clubId/tenantId`).
- **Что не так:** в JWT и в запросах к БД нет признака клуба/организации. `requireRole('owner','staff')` пускает любого владельца ко **всем** строкам таблиц (`profiles`, `checks`, `transactions`, `spaces`, …). Как только в одной базе появятся данные двух клубов, owner клуба A прочитает и изменит данные клуба B (полный horizontal-BOLA: клиенты, выручка, зарплаты, бэкапы БД через `/system/backup`).
- **Почему важно:** это прямая утечка коммерческих и персональных данных между платящими клиентами SaaS, нарушение 152-ФЗ и доверия. Без этого подписочная модель неработоспособна.
- **Фикс:** ввести `tenant_id` (organization) во ВСЕ доменные таблицы; добавить `tenantId` в JWT; на уровне middleware/ORM принудительно фильтровать каждый запрос по `tenant_id` (Drizzle-обёртка или Postgres Row-Level Security с `SET app.tenant_id`). Бэкапы/восстановление и AI-SQL — пер-тенант. До внедрения держать строго один клуб на инстанс/БД и продавать как «изолированный деплой».

#### C2. `requireAuth` отзыв токенов — fail-open при недоступности Redis
- **Где:** `apps/api/src/middleware/auth.ts:53-56` (`catch { /* fail-open */ }`).
- **Что не так:** проверка blacklist (`revoked:<hash>`) при ошибке Redis молча пропускается. Значит при недоступном/перегруженном Redis (а по `project_deploy_ops.md` VPS реально перегружается под сборкой) **отозванные/после-logout токены снова валидны**. Тот же fail-open в rate-limit (`rateLimit.ts:78-80`) и в глобальном PIN-backstop.
- **Почему важно:** logout, увольнение, компрометация токена перестают работать ровно в момент инфраструктурного стресса — наихудший момент. Уволенный сотрудник с украденным токеном восстановит доступ, перезагрузив Redis.
- **Фикс:** для проверки отзыва выбрать политику осознанно. Минимум — не fail-open для критичных мутаций (POST/PATCH/DELETE денежных и staff-эндпоинтов): при недоступности Redis отвечать 503, а не пускать. Альтернатива — короткий TTL access-токена (5–15 мин) + refresh, тогда blacklist менее критичен.

### HIGH

#### H1. 4-значный PIN — первичный фактор персонала; глобальный счётчик = вектор DoS-локаута
- **Где:** `apps/api/src/modules/auth/auth.router.ts:135-204` (`/login/pin`), `:44-45` (`PIN_GLOBAL_FAIL_KEY`, `PIN_GLOBAL_MAX = 50`); `:69-133` (`/tablet-session` — тот же fan-out).
- **Что не так:** при входе без `userId` один 4-значный PIN сверяется со **всеми** staff/owner (пространство ключей всего 10⁴, а с ростом числа сотрудников вероятность коллизии растёт). Per-IP лимит сознательно объявлен «вежливым» (заголовки подделываемы), реальная защита — **один глобальный счётчик на весь деплой** (50 неудач/15 мин). Это палка о двух концах: (а) атакующий с ботнета быстро выбирает 50 попыток и далее перебирает медленно, но непрерывно; (б) что хуже — **любой может намеренно загнать счётчик в потолок и заблокировать вход всему персоналу** (DoS, особенно болезненно для киоск-планшетов и кассы во время смены).
- **Почему важно:** PIN — это вход в кассу, деньги, зарплаты. Слабый фактор + общий счётчик-локаут создают и риск подбора, и риск саботажа конкурентом/уволенным.
- **Фикс:** (1) сделать вход с явным `userId` основным путём (per-account lockout вместо глобального); (2) убрать/ограничить fan-out без `userId` (или требовать ник+PIN); (3) поднять энтропию PIN до 6 цифр; (4) добавить экспоненциальную задержку per-account и капчу/cool-down вместо глобального жёсткого локаута; (5) логировать всплески неудач для алертинга.

#### H2. JWT в localStorage + длинный TTL + нет инвалидации по событию
- **Где:** `apps/web/src/store/auth.store.ts:67-90` (persist в `localStorage` под ключом `titan-auth`); `packages/auth/src/jwt.ts:29` (TTL по умолчанию `7d`, планшет `30d` — `auth.router.ts:123,318`); «блокировка» по перезагрузке/бездействию — **только клиентская** (`auth.store.ts:85-87`, `INACTIVITY_TIMEOUT_MS`).
- **Что не так:** (а) токен в `localStorage` крадётся любым XSS и переживает «локскрин» — серверный токен остаётся полностью валидным, lock косметический; (б) отзыв — только пер-токенный blacklist по факту logout, при этом **смена пароля, смена роли, снятие permissions и даже увольнение НЕ инвалидируют уже выданные токены** (увольнение чистит passkey и `deletedAt`, но активный JWT живёт до `exp` — до 7 дней; см. отсутствие проверки `deletedAt` в `requireAuth`).
- **Почему важно:** понизили сотрудника из owner в staff или уволили — он сохраняет прежние права на дни. Для SaaS это недопустимо.
- **Фикс:** короткий access-TTL + refresh-ротация; либо хранить «session epoch»/`tokenVersion` в профиле и сверять его в `requireAuth` (инкремент при смене пароля/роли/увольнении мгновенно гасит все токены). Рассмотреть httpOnly-cookie + CSRF-токен вместо `localStorage`. Проверять `profiles.deletedAt`/актуальную роль в `requireAuth`, а не только при passkey-входе.

#### H3. Энумерация пользователей и хранение plaintext-паролей
- **Где:** `auth.router.ts:228` (`/login/password` отдаёт `404 'User not found'` при неизвестном нике против `401 'Invalid password'`); `packages/auth/src/password.ts:13-15` + `auth.router.ts:232-237` (ветка `isPlaintext` сравнивает пароль с полем как с открытым текстом и лениво хэширует).
- **Что не так:** (1) разные коды/тексты ответа позволяют перечислять валидные ники staff (полезно для последующего таргетинга PIN/passkey). (2) Наличие ветки `isPlaintext` означает, что в БД **есть/были пароли в открытом виде**; до первого успешного входа такого пользователя его пароль лежит plaintext и сравнивается `password === hash` (не constant-time).
- **Почему важно:** энумерация ускоряет атаки; plaintext-пароли — прямая утечка при компрометации БД/бэкапа (а бэкапы уходят на Google Drive через rclone).
- **Фикс:** для логина возвращать единый `401` с одинаковым текстом и (желательно) одинаковым таймингом при неизвестном нике и неверном пароле. Провести разовую миграцию: всем профилям с `isPlaintext(passwordHash)` форсировать сброс пароля (или прохэшировать на месте миграцией и потребовать смену), затем удалить ветку plaintext из кода.

### MEDIUM

#### M1. AI выполняет сгенерированный LLM SQL через `sql.raw` (блок-лист обходим)
- **Где:** `apps/api/src/modules/ai/ai.router.ts:222-243` (`sanitizeSql` — regex-блоклист; `runReadonly` → `sql.raw(wrapped)`).
- **Что не так:** защита построена на блок-листе ключевых слов и «только один SELECT/WITH». Блок-листы исторически обходятся (вложенные подзапросы, функции, `pg_sleep`, чтение `pg_*`/`information_schema`, побочные эффекты через функции). Смягчено: транзакция `SET TRANSACTION READ ONLY` + `statement_timeout 5s` + `LIMIT 200` + эндпоинт под `requireRole('owner','staff')` + фильтр чувствительных колонок в схеме (`SENSITIVE_COL`).
- **Почему важно:** READ ONLY и таймаут снимают остроту (нет записи, нет долгих запросов), но чтение «не своих» данных/метаданных и в перспективе кросс-тенантная утечка (см. C1) остаются. В мульти-клубе это становится HIGH.
- **Фикс:** перейти от блок-листа к allow-list (разрешённый набор таблиц/вью), выполнять под отдельной БД-ролью с `GRANT SELECT` только на безопасные вью, в мульти-тенанте — обязательно навешивать `tenant_id`-фильтр на сгенерированный запрос (или RLS под ролью с выставленным `app.tenant_id`).

#### M2. IDOR: планшет читает баланс/бонусы любого клиента по id
- **Где:** `apps/api/src/modules/pos/pos.router.ts:443-455` (`GET /players/:id`, роль `tablet` разрешена, без проверки зоны/принадлежности) — возвращает `balance`, `bonusPoints`, `linkedSpaceId`.
- **Что не так:** гостевой планшет-киоск (токен живёт 30 дней, лежит на чужом устройстве) перебором UUID может вытащить баланс/бонусы любого клиента. Чувствительность невысокая (не деньги, не PII вроде телефона), а UUID не перечисляются последовательно, но это всё же раскрытие данных другого пользователя устройству-киоску.
- **Почему важно:** нарушает принцип наименьших привилегий для самого недоверенного актора (tablet). В мульти-клубе — утечка между клубами.
- **Фикс:** для роли `tablet` отдавать только данные клиента, привязанного к открытому чеку его зоны (или вовсе скрыть `balance` от планшета). owner/staff — без ограничений.

#### M3. Per-IP идентификация частично подделываема (X-Forwarded-For)
- **Где:** `apps/api/src/lib/clientIp.ts:7-10` (берёт `x-real-ip`, иначе **последний** элемент XFF), используется в `rateLimit.ts` и в PIN-лимитах.
- **Что не так:** код корректно предпочитает `X-Real-IP` от nginx и берёт последний (доверенный) элемент XFF. Это правильно — **но только при гарантии**, что приложение всегда стоит за этим nginx и порт API не доступен в обход прокси. Если API-порт открыт наружу (или nginx сконфигурирован иначе), `X-Real-IP`/последний XFF подделываются, и per-IP бакеты обнуляются за запрос.
- **Почему важно:** обход per-IP rate-limit на логине/пароле/tablet-pair (для PIN-fan-out остаётся глобальный backstop, но для `/login/password` по нику и `/tablet-pair` глобального потолка нет — только per-IP).
- **Фикс:** заблокировать прямой доступ к API-порту (только через nginx) на уровне docker/firewall; зафиксировать в деплой-доках. Для `/login/password` и `/tablet-pair` добавить глобальный/пер-аккаунтный backstop по аналогии с PIN.

#### M4. Telegram-логин: `JSON.parse` непроверенного `user` и широкая проверка по двум ботам
- **Где:** `auth.router.ts:338-361`; `packages/auth/src/telegram.ts:3-25`.
- **Что не так:** подпись initData проверяется корректно (HMAC + anti-replay по `auth_date`, окно 24 ч). Но `JSON.parse(userStr)` (`:355`) без try/catch — кривой (хоть и подписанный) `user` уронит хендлер в 500 (через `onError`). Проверка валидна, если совпало с **любым** из двух токенов (wallet/admin) — приемлемо по бизнесу, но расширяет доверенную поверхность на оба бота.
- **Почему важно:** DoS-мелочь и расширение доверия; сам вход безопасен (без привязки `tgId` — 404).
- **Фикс:** обернуть `JSON.parse` в try/catch → 400; убедиться, что окно anti-replay (24 ч) достаточно узкое для вашего сценария (можно сократить до 5–15 мин).

#### M5. Нет журнала событий безопасности (audit log)
- **Где:** отсутствует сквозной аудит входов/выходов, смены ролей/permissions (`staff.router.ts:137-166`), сброса PIN (`:186`), удаления passkey, восстановления БД (`system.router.ts:139-167`).
- **Что не так:** критичные привилегированные действия (выдача owner-прав, reset-pin чужого аккаунта, restore БД поверх текущей) нигде не фиксируются с актором/временем/IP.
- **Почему важно:** без аудита невозможно расследовать инцидент, доказать «кто слил выручку», обеспечить требования B2B-клиентов SaaS.
- **Фикс:** таблица `audit_log(actor_id, action, target_id, ip, meta, created_at)`; писать на login success/fail, logout, staff CRUD, role/permission change, reset-pin, restore/backup, удаление passkey. Для SaaS — обязательный пункт.

### LOW

#### L1. Утечка `e.message` в ответах upload/restore/backup
- **Где:** `upload.router.ts:101` (`{ error: e.message }`), `system.router.ts:134-135,149-150,164-165`.
- **Что не так:** при ошибке наружу уходит текст исключения (имя бакета MinIO, путь, детали psql). Эндпоинты owner/staff-гейтед, поэтому риск низкий, но это раскрытие инфраструктуры привилегированному, но потенциально скомпрометированному клиенту.
- **Фикс:** логировать детально на сервере, наружу — обобщённое сообщение (как уже сделано в `app.ts:124-129`).

#### L2. WebAuthn `userVerification: 'preferred'` (а не `required`)
- **Где:** `auth.router.ts:548,640` (`userVerification: 'preferred'`).
- **Что не так:** passkey может пройти без user-verification (биометрия/PIN устройства) → ослабляет «второй фактор владения+знания» до просто «владения». Counter-проверка на клоны корректна (`:726-730`), discoverable-вход без `userId` ищет ключ по `response.id` — это нормально.
- **Фикс:** для staff/owner поднять до `userVerification: 'required'` на register и authenticate.

#### L3. `WEBAUTHN_RP_ID/ORIGIN` — глобальные env (не пер-тенант)
- **Где:** `auth.router.ts:24-26`.
- **Что не так:** при будущем мульти-доменном SaaS (клуб A на `a.titanpos.ru`, клуб B на `b.…`) единый `RP_ID/ORIGIN` сломает passkey-привязку/проверку для поддоменов.
- **Фикс:** учесть при переходе на мульти-тенант (вычислять RP_ID/Origin из запроса/тенанта с allow-list доменов).

#### L4. CSRF — не применимо, но зафиксировать инвариант
- **Где:** `app.ts:85-91` (CORS `credentials:true`, origin = `FRONTEND_URL`); токен передаётся как `Bearer`, не как cookie (`auth.store.ts`).
- **Что не так:** классический CSRF не угрожает (нет cookie-сессий), но `cors({ credentials:true })` при единственном origin безопасен **только** пока origin строго ограничен. Если в будущем добавите cookie-аутентификацию (см. H2-фикс) — потребуется CSRF-защита.
- **Фикс:** документировать, что переход на cookie-сессии обязывает добавить CSRF-токены/SameSite=strict.

## Что работает хорошо (подтверждено чтением кода)

- **JWT-секрет обязателен** и проверяется на старте (`index.ts:9-23`, `jwt.ts:6-12`) — нет небезопасных фолбэков, минимум 32 символа.
- **Нет опасных дефолтов секретов в проде:** `docker-compose.yml` использует `${VAR:?required}` для пароля Postgres и MinIO (падает, если не задано). `minioadmin`/`redis://…` — только как code-фолбэки для dev.
- **IDOR-защита планшета в POS** реализована последовательно: единый хелпер `tabletZoneForbidden` (`pos.router.ts:67-72`) применён ко всем мутациям чека (`:760,814,923,942,957,996,1008,1065,1252`), список чеков жёстко скоупится по `linkedSpaceId` (`:463-466`), `GET /checks/:id` и `/events` проверяют зону (`:651-654,664-667`).
- **Платёжный вебхук Platega** аутентифицируется constant-time-сравнением merchant/secret (`platega.router.ts:24-39`), идемпотентен (`status !== 'open'` → no-op, `:64`), сверяет сумму и работает в БД-транзакции с `FOR UPDATE` (`:60,160`). Закрытие чека — только из вебхука.
- **Логи маскируют токены** в query (`app.ts:45-71`), наружу — обобщённые ошибки (`app.ts:124-129`).
- **Загрузка файлов**: magic-byte sniffing, запрет SVG, лимит 2 МБ, тип из реальных байтов (`upload.router.ts:21-96`).
- **Бэкап/restore**: пароль БД не попадает в командную строку (`backup.ts:19-29`), restore-by-name защищён `SAFE_NAME`-regex от path-traversal (`:119-129`), нет mass-assignment.
- **Авторизация присутствует на всех роутерах**: каждый доменный роутер навешивает `requireAuth` (+ роль) глобально или поэндпоинтно. Деструктивные/денежные операции (delete категорий/товаров/событий, тарифы, зарплаты, настройки, бэкап/restore) корректно ужесточены до `requireRole('owner')`.
- **`/auth/me` и `/auth/me/*`** строго скоупятся по `user.sub` — нет IDOR на собственные данные кошелька (`auth.router.ts:371-475`).
- **SQL-инъекции**: доменные запросы — параметризованный Drizzle; единственные «сырые» интерполяции (`clients.router.ts:326-334`) используют `sql.identifier()` с именами из `pg_constraint` (метаданные, не пользовательский ввод) — безопасно.
- **Telegram initData** проверяется по HMAC с anti-replay (`telegram.ts`).
- **Удалённый сотрудник**: passkey-вход и telegram-вход учитывают `deletedAt` и подчищают осиротевшие ключи (`auth.router.ts:357,744-748`).

## New feature ideas (для мафия-клубов / антикафе)

- **Пер-устройство «киоск-доверие»**: привязка планшета не только к зоне, но к отпечатку устройства; owner видит список активных планшетов и может одним тапом отозвать токен конкретного устройства (сейчас отзыв — только пер-токен по logout).
- **«Режим вечеринки/закрытого мероприятия»**: временный QR-пропуск для приглашённого администратора-гостя с авто-истечением и ограниченной ролью (provision-time-boxed access) — типичный сценарий для разовых турниров/корпоративов.
- **Журнал смены с подписью**: при открытии/закрытии смены фиксировать вход кассира (PIN/passkey) в audit-log с суммой кассы — спорные «недостачи» закрываются журналом «кто и когда».
- **Step-up auth на деньги**: повторный passkey/PIN перед особо чувствительными действиями (restore БД, выдача owner-прав, ручная корректировка баланса клиента > порога) — снижает урон от украденного токена.
- **Owner security dashboard**: «последние входы», «активные сессии/устройства», «неудачные попытки PIN», кнопка «разлогинить всех» (session epoch bump) — продаётся как премиум-фича SaaS.
- **Гео-/IP-allowlist на админ-вход**: владелец задаёт «вход в управление только из клуба (по IP)» — антифрод для франшиз.

## SaaS / multi-club implications для этой области

- **Изоляция тенантов — обязательное условие №1** (см. C1). Без `tenant_id` + принудительной фильтрации (RLS/ORM-обёртка) продавать подписку нельзя: первая же пара клубов в одной БД = взаимная утечка выручки, клиентов, зарплат и **бэкапов целой БД** через owner-эндпоинт `/system/backup`.
- **Сессии/отзыв прав должны быть мгновенными** (H2): в мультиарендной среде увольнение/понижение/смена тарифа клуба обязаны немедленно гасить токены. Нужен `tokenVersion`/session-epoch или короткий access-TTL + refresh.
- **Аутентификация владельцев должна быть сильнее PIN** (H1): для разных клубов разделить keyspace по тенанту, убрать глобальный fan-out и глобальный счётчик (иначе атака на один клуб = DoS-локаут для всех клубов на инстансе). PIN — только локальный «быстрый разлок» внутри уже аутентифицированной сессии устройства, не первичный фактор для входа в управление.
- **AI-SQL (M1) в мультиаренде становится критичным**: запрос обязан быть ограничен `tenant_id` (allow-list вью под ролью с выставленным `app.tenant_id`), иначе owner клуба A через «свободный вопрос» вытащит данные клуба B.
- **Audit-log (M5) — требование B2B-продаж**: корпоративные клиенты антикафе/сетей запросят журнал доступа и действий; добавить заранее.
- **Per-tenant WebAuthn RP/Origin и MinIO-неймспейсы** (L3): при мульти-домене/поддоменах вынести RP_ID/Origin и префиксы объектов в конфиг тенанта.
- **Backup/restore — пер-тенант**: текущий `pg_dump` всей БД и restore поверх неё в SaaS недопустимы (restore одного клуба снесёт всех). Нужен логический экспорт по `tenant_id`.
