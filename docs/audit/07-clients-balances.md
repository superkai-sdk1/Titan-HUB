# Аудит: Клиенты, депозиты, долги, балансы

## Summary

Депозиты и долги хранятся как **один** столбец `profiles.balance numeric(12,2)` (плюс — депозит, минус — долг), а таблица `transactions` ведётся как параллельная история. Критические денежные пути (оплата чека депозитом/в долг в `pos.router.ts`, возврат на баланс в `refunds.router.ts`, ручная корректировка в `clients.router.ts`) **корректно блокируют строку клиента (`SELECT … FOR UPDATE`) внутри одной транзакции** — это сильная сторона, гонок на самом балансе нет. Однако: (1) нет двойной записи / инварианта «баланс == сумма проводок», поэтому баланс и история могут разъехаться; (2) экран `/manage/clients` шлёт корректировку баланса **без ключа идемпотентности** (в отличие от `/manage/balances`), что возвращает риск двойного списания; (3) PII (телефон, ФИО, ДР) хранится в открытом виде без согласия/аудита/экспорта — критично для коммерческой эксплуатации по 152-ФЗ; (4) справочник «Заказчики» допускает дубли и хардкор-удаление.

## Production-readiness score: 62 / 100

Обоснование: ядро согласованности баланса под нагрузкой реализовано грамотно (row-lock + идемпотентность на серверном эндпоинте + лимит долга в транзакции), поэтому «деньги не теряются» в основном сценарии. Балл снижают: отсутствие инварианта целостности баланса (нет способа доказать, что баланс не повреждён), пропущенная идемпотентность на одном из двух UI-входов, полное отсутствие приватности/аудита PII (юридический риск для платного продукта в РФ) и отсутствие мульти-клубной изоляции (баланс глобальный — блокер для SaaS).

## Findings

### 1. [HIGH] Баланс не является двойной записью — нет инварианта целостности
**Файлы:** `packages/database/src/schema/profiles.ts:37`, `packages/database/src/schema/finance.ts:53-69`, `apps/api/src/modules/clients/clients.router.ts:438-440`

`profiles.balance` — единственный источник истины, `transactions` лишь «история». Для склада в проекте явно объявлен инвариант `inventory.stockQuantity == SUM(delta)` (см. `finance.ts:159` и миграцию 044), а для денег такого инварианта **нет**. Проводки пишутся как `amount = Math.abs(...)` + `type` (deposit/withdrawal), знак теряется — восстановить баланс из истории и сверить с `profiles.balance` нельзя одной агрегацией.

**Почему важно:** если хоть один путь обновит `balance`, но не запишет проводку (или наоборот), расхождение никто не заметит — нет сверки. Для платного продукта это означает «деньги клиента есть в одной таблице и нет в другой», и доказать правильность невозможно.

**Фикс:** хранить в `transactions` **знаковую** дельту баланса (`signed_amount`) для всех денежных типов и добавить регулярную проверку/CI-инвариант `profiles.balance == COALESCE(SUM(signed_amount),0)` по каждому клиенту (хотя бы `cron`-сверка с алертом при расхождении). Идеально — перейти на расчёт баланса как материализованной агрегации проводок.

### 2. [HIGH] Экран «Клиенты» меняет баланс без ключа идемпотентности
**Файл:** `apps/web/src/app/manage/clients/page.tsx:153` (и `confirmAdj` :167-176)

Мутация `adjBal` вызывает `POST /clients/:id/balance` с `{ amount, reason }` — **без** `idempotencyKey`. Сравните с `apps/web/src/app/manage/balances/page.tsx:130`, где ключ генерируется (`crypto.randomUUID()`). Серверный эндпоинт защищён только при наличии ключа (`clients.router.ts:434-436`): `if (idempotencyKey && ins.length === 0)`. Без ключа `onConflictDoNothing` не срабатывает и повтор задваивает баланс.

**Почему важно:** ровно тот сценарий, ради которого писалась миграция 045 (двойной клик / сетевой ретрай → задвоение депозита/долга), снова открыт на втором, не менее используемом UI-входе.

**Фикс:** добавить `idempotencyKey: crypto.randomUUID()` в `adjBal.mutate` (и в payload запроса). 5-минутная правка.

### 3. [HIGH] PII клиентов без согласия, шифрования, аудита и средств экспорта/удаления (152-ФЗ)
**Файлы:** `packages/database/src/schema/profiles.ts:41-45` (`phone`, `birthday`, `fullName`, `tgId`, `tgUsername`), `customers.ts:5-10`

Телефон, реальное имя, дата рождения, Telegram хранятся открытым текстом. По всему репозиторию **нет** ни одного упоминания согласия на обработку ПДн, анонимизации, экспорта данных субъекта, журнала доступа к PII (grep по `152-ФЗ|consent|согласие|анонимиз|audit_log` — пусто). `delete /:id/permanent` обезличивает FK, но это инициирует владелец, а не субъект данных, и факт удаления нигде не логируется.

**Почему важно:** для коммерческой эксплуатации в РФ обработка ПДн без согласия и без уведомления РКН — прямой штраф; для SaaS, продаваемого другим клубам, оператором ПДн становится каждый клуб, и продукт обязан давать инструменты (согласие, экспорт, удаление, журнал). Сейчас этого нет.

**Фикс:** (1) флаг/таблица согласия на обработку ПДн при создании клиента; (2) журнал доступа/изменений PII (кто и когда смотрел/менял телефон/баланс); (3) эндпоинты экспорта и удаления данных субъекта; (4) шифрование чувствительных полей в покое или хотя бы маскирование в логах/ответах для роли staff.

### 4. [MEDIUM] Дубли заказчиков: гонка read-then-insert + нет уникальности телефона
**Файлы:** `apps/api/src/modules/events/events.router.ts:215-226`, `packages/database/src/schema/customers.ts:5-10`, `apps/api/src/modules/customers/customers.router.ts:26-30`

Автосохранение заказчика делает `SELECT … WHERE phone = ? LIMIT 1` затем `INSERT` **вне транзакции** и без уникального индекса на `customers.phone`. Параллельное создание двух событий с одним телефоном → два заказчика. Плюс сравнение по точному совпадению строки — `+79001234567` и `+7 900 123-45-67` считаются разными. Ручное создание (`customers.router.ts:26`) дублей вообще не проверяет.

**Почему важно:** справочник захламляется дублями, автоподбор при планировании мероприятий начинает предлагать «того же человека» несколько раз, аналитика по заказчикам искажается.

**Фикс:** нормализовать телефон (только цифры/`+7…`) перед сравнением и хранением; уникальный индекс на нормализованный телефон + `INSERT … ON CONFLICT DO NOTHING/UPDATE`; то же в `customers POST`.

### 5. [MEDIUM] Жёсткое удаление клиентов/заказчиков с балансом и историей
**Файлы:** `apps/api/src/modules/customers/customers.router.ts:42-45` (`db.delete`), `apps/api/src/modules/clients/clients.router.ts:291-340`

Заказчик удаляется физически (`DELETE`), без soft-delete и без проверки связей. Клиента можно перевести в архив (`deletedAt`) и затем удалить «навсегда»; пермач-удаление само по себе аккуратно (чистит FK), но **не проверяет, что `balance != 0`** — можно безвозвратно удалить клиента с непогашенным долгом или невыплаченным депозитом, потеряв обязательство заведения.

**Почему важно:** удаление клиента с депозитом = заведение «забыло» о предоплате клиента; с долгом = списало дебиторку без следа. Это денежная потеря/искажение отчётности.

**Фикс:** запретить permanent-delete при `balance <> 0` (или требовать явного обнуления с проводкой-списанием и причиной); для `customers` ввести soft-delete.

### 6. [MEDIUM] `POST /clients/:id/balance` не ограничивает сумму (amount) и допускает дробную грязь
**Файл:** `apps/api/src/modules/clients/clients.router.ts:380`, расчёт `:411-412`

Схема: `amount: z.number()` — без `min/max`, без `.finite()`, без шага. Сравните с бонусным эндпоинтом, где есть `.min(-1_000_000).max(1_000_000)` (`:489`). Расчёт `newBalance = currentBalance + amount` идёт **без `round2`** (хотя в POS/refunds везде `round2`); сохранение в `numeric(12,2)` округлит, но промежуточный JS-float может дать `…0000001`, а отсутствие границ позволяет передать `1e15` или `NaN`-подобные крайности через API.

**Почему важно:** опечатка/злоупотребление через прямой API-вызов (staff имеет токен) может загнать баланс в абсурд; отсутствие `round2` — потенциальный источник копеечного дрейфа при ручных дробных корректировках.

**Фикс:** `amount: z.number().finite().min(-10_000_000).max(10_000_000)` и применить `round2(currentBalance + amount)` перед записью.

### 7. [LOW] Нет пагинации/лимита на выборках балансов и нет агрегатов на сервере
**Файл:** `apps/api/src/modules/clients/clients.router.ts:62-105`

Фильтры `debtors`/`balances`/`deposits` возвращают **всех** подходящих клиентов без `LIMIT` (`return { total: safe.length }`). Сумма депозитов/долгов считается на клиенте (`balances/page.tsx:69-71`) по всему массиву.

**Почему важно:** при росте базы (а тем более при SaaS на несколько клубов) экран «Депозиты и долги» начнёт тянуть всю таблицу и считать сальдо в браузере — деградация и неверные итоги, если когда-нибудь добавят серверную пагинацию.

**Фикс:** считать `SUM(balance)`/счётчики на стороне БД, отдавать пагинированный список + готовые тоталы.

### 8. [LOW] История на экране балансов фильтруется только по `deposit/withdrawal` — оплаты чеком невидимы
**Файл:** `apps/web/src/app/manage/balances/page.tsx:80`

`history = transactions.filter(type === 'deposit' || 'withdrawal')`. Списание депозита за чек пишется как `withdrawal` (попадёт), но движения типа `payment`/`refund` по балансу клиента — нет. Возврат на баланс (`refunds` пишет `type:'deposit'`) попадёт, но семантику «возврат» пользователь не увидит.

**Почему важно:** владелец видит неполную картину движения денег клиента в карточке депозита; спор «почему баланс такой» сложнее разрешить.

**Фикс:** показывать все денежные типы с понятными подписями, либо добавить серверный эндпоинт «выписка по балансу» с уже посчитанным `balanceAfter`.

## Идеи фич (мафия-клубы / антикафе)

- **Выписка по депозиту/долгу одной кнопкой** — PDF/ссылка с историей и текущим сальдо, чтобы отправить гостю в Telegram при споре.
- **Авто-напоминания должникам** — пуш/Telegram через Wallet-бот: «долг N₽ висит 7 дней», эскалация владельцу. Инфраструктура `notifyClient` уже есть.
- **Депозит-пакеты / абонементы** — «внеси 5000 — на счёт 6000» (бонус за предоплату), типично для антикафе с тарификацией по времени.
- **Лимит долга по статусу клиента** — сейчас один глобальный `max_client_debt`; резиденту можно больше, новичку — 0. Привязать к `clientTier`.
- **«Семейный»/групповой баланс** — общий депозит на компанию, типично для бронирования мафия-стола на команду.
- **Заморозка/арбитраж баланса** — пометка «спорный долг» с причиной, чтобы он не уходил в авто-напоминания.

## SaaS / мульти-клубные импликации

- **Блокер №1 — единый глобальный баланс.** `profiles.balance` и `customers` не имеют столбца клуба/тенанта (подтверждено: grep по tenant/club/venue — пусто). При продаже другим клубам депозит гостя клуба А виден и расходуется в клубе Б. Нужна колонка `club_id` на `profiles`, `transactions`, `customers`, `bonus_history`, `bonus_lots` и сквозная фильтрация во всех выборках этого модуля.
- **Лимит долга и ставки бонусов** (`max_client_debt`, `bonus_*`) лежат в глобальном `app_settings` — в мульти-тенанте должны быть per-club.
- **PII-оператор — каждый клуб.** В SaaS каждый клуб становится самостоятельным оператором ПДн: продукт обязан давать на уровне клуба согласие, экспорт, удаление и журнал доступа (см. Finding 3). Без этого подключение второго клуба = тиражирование юридического риска.
- **Сверка баланса по клубам.** Инвариант из Finding 1 в мульти-тенанте критичнее: расхождение нужно ловить в разрезе клуба, иначе один баг «протечёт» деньгами между арендаторами.
- **Уникальность ника** (`profiles.nickname UNIQUE`) глобальна — в мульти-клубе два клуба не смогут завести гостя с одним ником; уникальность должна стать `(club_id, nickname)`.
