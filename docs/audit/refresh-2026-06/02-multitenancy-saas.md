# Аудит: Мультитенантность & SaaS (2026-06-18)

> Базовые документы: `docs/audit/14-multitenancy-saas.md` (12.06, оценка 8/100, тогда — чистый single-tenant) и `docs/audit/PLAN-PHASE1-TENANCY.md` (13.06, план «database-per-club»). Этот рефреш проверяет, что РЕАЛЬНО реализовано в коде на 18.06, и ищет дыры в изоляции тенантов.

## Оценка готовности к мультитенант-запуску: 68/100

С 12 июня проделан огромный объём: модель «база-на-клуб» реализована целиком (control-plane реестр, провижининг с нуля, резолюция по поддомену, энфорсмент подписки и модулей, суперадмин-контур, онбординг). Архитектура изоляции на уровне БД — **корректная и чистая**: каждый запрос ходит в БД своего клуба, нет общего пула на чужую БД, нет text-to-SQL в чужую БД. Оценку держат ниже 80 **три верифицированных P0** — все в плоскости «токен/тикет не привязан к клубу» и «вебхук без поддомена» — плюс известная незакрытая площадь (Redis-неймспейсинг уведомлений, глобальный PIN-счётчик). Это не дефект фундамента, а недокрытие на стыках: их закрытие — точечная работа, после которой проект уверенно выходит на 85+.

## Архитектура изоляции (как реально устроено)

**Database-per-club.** Один Postgres-сервер, отдельная БД `club_<slug>` на каждого арендатора. Control-plane (`titan_control`, отдельная БД) — реестр клубов/подписок/модулей/суперадминов. На каждый запрос `tenantContext` (`apps/api/src/middleware/tenant.ts`) по заголовку `Host` определяет клуб: быстрый путь для основного/служебного домена (`titanpos.ru`, localhost, IP, `www`/`admin`, любой неизвестный хост) → дефолтный синглтон `db` + `club=null` БЕЗ обращения к control-БД (поведение байт-в-байт прежнее); клубный поддомен `<slug>.titanpos.ru` → резолв через control-plane (кэш host→клуб TTL 60с), подстановка `getClubDb(connString)` (пул `max:5` на клуб, кэш по строке). `c.var.db` инжектится в контекст, все 22 роутера читают его; сервисы (`shifts.service`, `ledger`, `loyalty`, `appSettings`, `push`, `bonusLots`) принимают `db`/`tx` параметром (импорт синглтона остался только как ТИП). Запрос НИКОГДА не пишет в чужую БД на штатном (браузерном, по поддомену) пути. **Слабое место не в выборе БД, а в авторизации:** JWT и SSE-тикеты несут `{sub, role, nickname}` БЕЗ клейма клуба, подписаны единым `JWT_SECRET`, а тенант выбирается ТОЛЬКО по `Host` — значит токен любого клуба структурно валиден на чужом поддомене (ловится лишь там, где роут перепроверяет `sub` в БД; SSE-роуты этого не делают). Fail-safe выбран верно: основной домен → дефолт ДО любых обращений к БД; ошибка резолюции на клубном поддомене → 503 (не синглтон), несуществующий клуб → 404. Энфорсмент подписки/модулей fail-open при `club=null` (основной домен) и при недоступности обогащения (`subscription===undefined`), fail-closed для арендаторов.

## Находки по severity

### [P0] SSE-тикет (и JWT) не привязаны к клубу → межтенантное чтение live-данных
**Файл:** `apps/api/src/modules/auth/auth.router.ts:758-771` (выпуск тикета), `apps/api/src/middleware/auth.ts:16-27` (потребление), SSE-роуты `apps/api/src/modules/system/system.router.ts:98`, `apps/api/src/modules/notifications/notifications.router.ts:40`, `apps/api/src/modules/pos/pos.router.ts:744`.
**Суть:** `/auth/sse-ticket` кладёт в Redis `sse:<ticket>` → `{sub, role, nickname}` БЕЗ клуба (строка 764). `requireAuth` потребляет тикет, ставит `c.var.user` и пропускает — ничего не сверяет тикет с клубом. `tenantContext` выбирает БД/канал ИСКЛЮЧИТЕЛЬНО по `Host`. Тикет (или JWT через `?token=`), выпущенный на `a.titanpos.ru`, реигрывается на `b.titanpos.ru`: запрос аутентифицируется как owner/staff клуба A, но подписывается на канал `titan:updates:<clubB_id>` / `titan:staff-notifications:<clubB_id>` клуба B. SSE-роуты гейтят ТОЛЬКО по `role` (из тикета, без перепроверки `sub` в БД), поэтому owner-клуба-A читает живой POS/чек/уведомительный поток клуба B.
**Риск:** прямая межтенантная утечка реалтайм-данных (создание/оплата/закрытие чеков, чат, заказы, уведомления с нагрузкой — ники клиентов, суммы депозитов/долгов, названия позиций low_stock). Нужен лишь валидный вход в ЛЮБОЙ клуб (или собственный клуб-арендатор атакующего).
**Исправление:** добавить клейм клуба в JWT (`tid`/`club`) и в payload SSE-тикета (`club: c.var.club?.id` на строке 764); в `requireAuth`/`tenantContext` отвергать, если `club` токена/тикета ≠ резолвленный по `Host`. Это же закрывает `?token=` JWT-путь.

### [P0] Вебхук Platega (дефолтный СБП-провайдер) без поддомена → запись в дефолтную БД, не в БД клуба
**Файл:** `apps/api/src/modules/platega/platega.router.ts:232` и ветки `:236-395` (check/resident settle на `c.var.db`); создание платежа без callback-URL: `apps/api/src/modules/pos/pos.router.ts:1469-1489`, `apps/api/src/modules/auth/auth.router.ts:681-690` (`payload: rp.id`, без clubId).
**Суть:** Platega — дефолтный провайдер. В `transaction/process` НЕТ поля notificationUrl → Platega бьёт в ОДИН фиксированный URL дашборда (корневой домен). Вебхук приходит на `titanpos.ru` → `tenantContext` (быстрый путь, `tenant.ts:37-41`) ставит дефолтный синглтон `c.var.db`. Settle ищет `checks`/`residentPayments` по id в ДЕФОЛТНОЙ БД (`:236`, `:257`) → у реального клуба B чек не закроется / резидент-платёж не зачислится (обычно 404 `CHECK_NOT_FOUND`); при коллизии id — запись в ЧУЖУЮ БД.
**Контраст:** (а) ветка подписки `handleSubscriptionPayment` (`:39-115`, вызов `:228`) — БЕЗОПАСНА: парсит `sub:<clubId>:<period>` и пишет в control-БД через `getControlDb()`. (б) Эквайеры T-Bank/YuKassa/Сбер/Альфа (`pay.router.ts`) — БЕЗОПАСНЫ: `notificationUrl` строится из `new URL(c.req.url).origin` (поддомен клуба), вебхук возвращается на нужный поддомен.
**Риск:** платежи резидентов/чеков клубов-арендаторов через дефолтный СБП-провайдер не зачисляются (потеря денег/доверия) либо пишутся в чужую БД.
**Исправление:** резолвить клуб из платёжной записи: либо передавать clubId в `payload` Platega (`<clubId>:<rpId>`) и резолвить клуб через control-plane как в TG-вебхуке (`tg.router.ts:266-282` — эталон), либо хранить в control-plane маппинг `transactionId→clubId`, либо сделать callback-URL Platega пер-клубным.

### [P1] Часть `notify()` публикует уведомления в общий канал `:default` вместо канала клуба
**Файл:** хелпер `apps/api/src/modules/notifications/push.ts:243-307` (per-club канал, если передан `clubId`); пропуски `clubId`: `pos.router.ts:678,687,877,947,988,1083,1830,1852`, `clients.router.ts:259,703,713`, `events.router.ts:242,405`, `shifts.service.ts:82,133,139` (сигнатуры `openShift`/`closeShift` вообще не получают `clubId`; вызовы `shifts.router.ts:43,57` его не пробрасывают).
**Суть:** канал-хелпер `realtime.ts` корректно неймспейсит (`titan:staff-notifications:<clubId>`, suffix `'default'` при `undefined`). Подписчик `notifications.router.ts:43` слушает `<c.var.club?.id>`. Но перечисленные `notify(...)` зовутся БЕЗ `clubId` → публикуют в `:default`. Итог двойной: (1) собственный персонал клуба НЕ получает эти пуши на своём канале (функциональный баг); (2) слушатель канала `:default` (основной домен `GET /api/notifications/stream`, `club=null`) получает уведомления ВСЕХ клубов с нагрузкой (ники клиентов, суммы смен/депозитов/долгов, названия позиций).
**Риск:** межтенантная утечка нагрузки staff-уведомлений на слушателя дефолт-канала + потеря уведомлений у самого клуба.
**Исправление:** прокинуть `c.var.club?.id` во все эти вызовы; добавить параметр `clubId` в `openShift`/`closeShift` и пробросить из `shifts.router`.

### [P1] Глобальный PIN-счётчик brute-force блокирует вход ВСЕХ клубов разом
**Файл:** `apps/api/src/modules/auth/auth.router.ts:83,87` (`pin:fail:global`, `pin:fail:global:tablet`), использование `:129-148, :205-239` (`PIN_GLOBAL_MAX=50`).
**Суть:** жёсткий backstop для fan-out PIN-входа (`/login/pin` без userId и `/tablet-session`) — ОДИН счётчик на весь деплой, не пер-клуб. У каждого клуба свой набор staff в своей БД, т.е. пространство перебора пер-клубное, а потолок — общий. Брутфорс одного клуба (или умышленный триггер злонамеренным арендатором) лочит PIN-вход у ВСЕХ клубов.
**Риск:** межтенантный отказ в обслуживании логина (availability).
**Исправление:** неймспейсить счётчик `pin:fail:global:<clubId>` (на клубном поддомене `c.var.club?.id` доступен).

### [P1] Внутренний `/api/internal/bot-clubs` отдаёт расшифрованные токены ВСЕХ клубов под `JWT_SECRET`
**Файл:** `apps/api/src/modules/internal/internal.router.ts:31-37,43` (guard = `x-internal-secret == process.env['JWT_SECRET']`), `:49-81` (перебор всех клубов, отдаёт `admin_bot_token`/`wallet_bot_token` расшифрованными).
**Суть:** эндпоинт по дизайну дампит конфиги всех клубов бот-менеджеру. Защита — секрет, РАВНЫЙ `JWT_SECRET`, который к тому же (а) подписывает все JWT, (б) сидирует все TG-webhook-секреты (`lib/tgWebhook.ts:10`). Один секрет — тройное переиспользование, нет пер-клуб скоупа. Утечка `JWT_SECRET` → подделка любых токенов + дамп всех бот-токенов (per-club секреты) одним запросом.
**Риск:** при компрометации `JWT_SECRET` — тотальный межтенантный слив бот-токенов. Не эксплуатируется без секрета (это гигиена, не дыра auth).
**Исправление:** ввести отдельный `INTERNAL_API_SECRET` (и желательно отдельный ключ под TG-webhook-сиды), отвязать от `JWT_SECRET`.

### [P2] Глобальный `schemaCache` в ИИ-модуле течёт схемой между клубами
**Файл:** `apps/api/src/modules/ai/ai.router.ts:207` (`let schemaCache` — модульный синглтон, не по клубу), `:211-231` (`getSchemaDoc`, TTL 5 мин).
**Суть:** ВАЖНО — сам text-to-SQL исполняется КОРРЕКТНО на `c.var.db` (`:633` `const db = c.var.db`, прокидывается везде; `runReadonly` открывает `db.transaction` тенанта; глобальный `db`-синглтон в модуле НЕ импортируется как значение). Утечки СТРОК данных между клубами НЕТ. Но `schemaDoc` (список таблиц/колонок из `information_schema`) кэшируется глобально → клубу B может достаться схема клуба A. Схемы почти идентичны (общие миграции), сенситивные таблицы/колонки вырезаны, на несуществующей колонке запрос упадёт и `answerFromDb` вернёт null → фолбэк. Это метаданные, не строки.
**Риск:** низкий (структурная метадата-утечка, не данные).
**Исправление:** ключевать `schemaCache` по строке подключения/clubId.

### [P2] `tablet:pair:<code>` и `rl:ip:<ip>` — глобальные ключи Redis
**Файл:** `apps/api/src/modules/spaces/spaces.router.ts:75` (set `tablet:pair:<code>`), `apps/api/src/modules/auth/auth.router.ts:341,347` (get/del); `apps/api/src/middleware/rateLimit.ts:64` (`rl:ip:<ip>`).
**Суть:** `tablet:pair:<code>` — короткий код без клуб-неймспейса; при коллизии двух клубов клуб B спарит чужой `spaceId`, НО потребитель ищет space в `c.var.db` клуба B → чужой UUID не резолвится, fail-closed (не утечка). `rl:ip:<ip>` общий — один IP (общий NAT) троттлится между клубами (минор availability).
**Риск:** низкий (коллизия/троттлинг, не утечка данных).
**Исправление:** неймспейсить `t:<clubId>:` для гигиены.

### [P3] DELETE клуба — только мягкое удаление; нет дропа БД + экспорта ПДн (152-ФЗ)
**Файл:** `apps/api/src/modules/superadmin/clubs.router.ts:504-520` (status='deleted', БД не дропается; TODO на `/destroy`).
**Суть:** при оттоке клиента БД `club_<slug>` остаётся навсегда; нет эндпоинта экспорта/жёсткого удаления ПДн гостей (ФИО/телефон/ДР). Юридическое требование РФ.
**Исправление:** `POST /clubs/:id/destroy { confirmSlug }` с бэкапом перед DROP + `GET /clubs/:id/export`.

### [P3] Cron/backup-итерация по клубам и бюджет соединений — проверить на проде
**Файл:** `apps/api/src/lib/clubResolver.ts:229` (`listActiveClubDbNames`), пулы `packages/database/src/client.ts:48` (`max:5` на клуб), нет LRU-эвикции простаивающих пулов.
**Суть:** пер-клуб пул `max:5` без эвикции: при N клубах Σ соединений = N×5 + control(5) → при ~18 клубах упор в дефолтный `max_connections=100`. Кэш host→клуб и пулы не инвалидируются при смене статуса клуба суперадмином (до 60с suspended-клуб обслуживается).
**Исправление:** LRU-эвикция простаивающих пулов по idle-TTL; pub/sub-инвалидация кэша при смене статуса; мониторинг `pg_stat_activity`; при росте — PgBouncer.

## Возможности апгрейда

1. **Tenant-клейм в токенах как системный фикс P0.** Один источник корня обоих P0-токенных проблем — авторизационные артефакты без привязки к клубу. Ввести `club` в JWT и SSE-тикет и асёртить равенство резолвленному по `Host` в `requireAuth`. Это закрывает и SSE-replay, и `?token=`-replay одним системным изменением, а заодно даёт защиту в глубину поверх database-per-club.
2. **Единый «вебхук-резолвер клуба» по образцу TG.** `tg.router.ts:266-282` (clubId в пути → control-plane → явный `getClubDb`) — готовый паттерн. Вынести в хелпер и применить к Platega-вебхуку (P0), что снимает зависимость от поддомена для всех внешних callback'ов и даёт точку для пер-клубных секретов Platega.
3. **Разделение секретов + RLS как страховка.** Развести `JWT_SECRET` / `INTERNAL_API_SECRET` / TG-webhook-seed (закрывает P1-internal) и параллельно ввести Postgres RLS (`SET app.tenant_id`) даже в модели database-per-club — дешёвая защита от «забытого WHERE» и опора для будущего перехода на shared-DB премиум-тариф. Плюс пер-клуб неймспейс ВСЕХ Redis-ключей/каналов (`t:<clubId>:`) разом снимает P1/P2 утечки и DoS.
