# Полный аудит Titan HUB — SaaS + клиентский сервис (2026-06-18)

Свежий аудит поверх базового от 12.06 (HEAD ff813ca). За 6 дней добавлено ~30 коммитов:
платёжный слой СБП, фискализация 54-ФЗ, бронирование, маркетинг, Tai-подписка, сборы,
**SaaS-мультитенантность («база-на-клуб») и клиентский сервис Titan Resident** — базовый
аудит этот код не покрывал. Проведён 8 параллельными доменными аудиторами.

## Вердикт

**К продакшну на ОДИН клуб (основной домен) — близко (≈75/100).** Денежное ядро POS,
шифрование секретов, фискализация, изоляция БД сделаны грамотно.

**К SaaS-запуску (продажа клубам по поддоменам) — НЕ готов.** Сам механизм мультитенантности
структурно недоделан в двух местах, каждое из которых = тотальный отказ для клуба-арендатора.
Это не «доработать», это «не запускать продажи, пока не закрыто».

## P0 — блокеры (не запускать SaaS, пока не закрыто)

Жирным — подтверждено двумя независимыми аудиторами.

1. **Клуб-БД не получают схему. (DB + DevOps)**
   `runMigrations()` (`migrations/runner.ts:22`) выполняется ТОЛЬКО на синглтоне, не обходит
   `club_*`. А `baseline.sql` — грязный pg_dump: содержит 001–049+051+052, но пропускает 050
   и 053–059, при этом `provisioning.ts:243` помечает ВСЕ миграции применёнными → раннер их
   пропускает. Итог: новый клуб поднимается без таблиц `bookings/collections/fiscal_receipts/
   integrations/wallet_login_codes/resident_payments`; существующие клубы не получат будущих
   миграций. Тотальный 500 на поддоменах арендаторов. **Это #1 блокер.**

2. **Кросс-тенантная утечка живых данных через токены. (Auth + Multitenancy)**
   JWT и SSE-тикеты несут `{sub, role, nickname}` без клейма клуба; тенант выбирается только
   по `Host`. Owner клуба A переигрывает свой тикет на поддомене клуба B и читает живой
   POS/уведомительный поток клуба B (`auth.ts:16-27`, SSE-роуты `system/notifications/pos`).
   Усугубляется единым `JWT_SECRET` на 4 контура (клуб/суперадмин/internal/диплинки).

3. **Platega-вебхук сломан под мультитенант. (Multitenancy + Payments)**
   (а) Вебхук на фиксированном URL пишет в `c.var.db` = дефолтный синглтон, а не БД клуба →
   платежи арендаторов не зачисляются (`platega.router.ts`, `pos.router.ts:1469`).
   (б) Вебхук смонтирован ПОСЛЕ `requireActiveSubscription`/`requireModule` (`app.ts:148`) →
   у клуба с истёкшей подпиской гость заплатил по СБП, чек не закрылся; продление подписки
   тоже блокируется (тупик).

4. **Задвоение возвратов. (Backend)** `refunds.router.ts:73-244` — `FOR UPDATE` на `checks`
   не сериализует возвраты, `prevRefunds` читается без блокировки → два параллельных возврата
   проходят лимит. Прямая потеря денег.

5. **Задвоение зарплаты + неверная база. (Backend)** `salary.router.ts:112-163` — дедуп на
   nullable `idempotencyKey`, `onConflictDoNothing` всегда вставляет; `:76-106` — при 2+
   сотрудниках каждый получает % от ПОЛНОЙ выручки клуба.

6. **Удаление клиента теряет деньги. (Backend)** `clients.router.ts:502-566` — удаление
   игнорирует ненулевой баланс, перманентное зануляет `transactions.player_id` → невосстановимая
   потеря финансовой истории.

7. **Брутфорс кода входа резидента. (Resident + Auth)** `bot-wallet/src/bot.ts:254-277` — бот
   ищет любую pending-строку по 4-значному коду (9000 вариантов), без лимита попыток → перехват
   чужих login-сессий.

8. **Restore БД небезопасен. (DevOps)** `backup.ts:116` `psql ON_ERROR_STOP=0`, хендлеры
   `system.router.ts:173-201` синхронны, без mutex/maintenance, доступны владельцу из UI →
   тихая порча финансов + обрыв оплаты на середине.

## P1 — критично (закрыть до масштабирования)

- **Межтенантный DoS:** глобальный `pin:fail:global` блокирует логин ВСЕХ клубов (`auth.router.ts:83`).
- **Fail-open отзыва токена** при сбое Redis — отозванные/logout-токены снова валидны (`auth.ts:59`).
- **`/api/internal/bot-clubs`** отдаёт расшифрованные бот-токены всех клубов под `JWT_SECRET` (`internal.router.ts:43`).
- **notify() в общий канал `:default`** — утечка уведомлений (ники/суммы) между клубами (`shifts.service.ts:82`).
- **Фискальный чек на товарную сумму**, а принято ×1.08+чаевые → риск 54-ФЗ (`cron/fiscalize.ts:56`).
- **RBS verifyWebhook** возвращает `ok:true` без проверки checksum (`pay/providers/rbs.ts:79`).
- **Идемпотентность платежа** без unique-индекса (`settle.ts:95`, `059_resident_payments.sql:11`).
- **Касса уходит в минус** при изъятии без сверки (`cashops.router.ts:42`).
- **Двойная бронь зоны** — дырявая детекция пересечений (`events.router.ts:112`).
- **Публичный booking lookup** отдаёт чужой `claim_token` по телефону без auth (`bookings.router.ts`).
- **Бюджет Postgres-соединений:** ~15-16 клубов → `too many connections` (нет PgBouncer/TTL пулов).
- **Нет observability/алертинга:** только `console.*`, `/health` = `{ok:true}` при мёртвом PG.
- **Деплой собирает на проде** → SSH-разрывы, build-кэш переполняет диск 45G.
- **MinIO bucket публичен**, без изоляции по клубу (`upload.router.ts:88`).
- **SW `skipWaiting()`** роняет открытую кассу при деплое ChunkLoadError (`web/public/sw.js:17`).
- **SSE не переоткрывается** после блипа сети — заказы молча не приходят (`NotificationsProvider.tsx:197`).
- **Нет Service Worker** у resident-PWA + **нет logout** в UI (30-дн сеанс в localStorage).
- **Дрейф схемы:** Drizzle не содержит `bookings`/`fiscal_receipts` (живут только в raw-SQL).

## Дорожная карта (приоритет)

**Спринт 0 — разблокировать SaaS (P0 #1, #2, #3):**
явный `BASELINE_THROUGH` + миграции по всем `club_*` + CI-тест «baseline+migrate == прод-дамп»;
tenant-клейм в JWT/SSE + асёрт по Host; единый вебхук-резолвер клуба + вынос вебхуков до гейтов.

**Спринт 1 — деньги и эксплуатация (P0 #4-8, ключевые P1):**
advisory-locks на возвраты/ЗП/брони; защита баланса при удалении клиента; rate-limit входа
резидента; безопасный restore (mutex+maintenance); фискальная сумма = принятая; PgBouncer; Sentry+health/ready.

**Спринт 2 — апгрейды клиента и фронта:**
Service Worker + Web Push в Resident; декомпозиция `page.tsx`; управляемое обновление PWA;
error boundaries; CI/CD со сборкой образов вне прода.
