# Аудит аналитики Titan HUB — сводка (2026-06-18)

3 параллельных аудитора: корректность метрик, производительность/мультитенант/безопасность, фронтенд.
Объём: `analytics.router.ts` (1434 стр., ~18 эндпоинтов) + `dashboard/page.tsx` (1973 стр.).
Детальные отчёты: `analytics-01-correctness.md`, `analytics-02-perf-security.md`, `analytics-03-frontend.md`.

## Вердикт

Структурно аналитика сделана **зрело** (изоляция клубов чистая, lazy-загрузка вкладок, таймзоны МСК
аккуратны, чаевые/эквайринг корректно вне выручки). Но есть **P0 корректности, из-за которых цифры
на главных экранах завышают выручку**, и пробел в доступе: рядовой кассир видит прибыль/ФОТ/ПДн.

## 🔴 P0 — цифры вводят в заблуждение

1. **Возврат не вычитается из «выручки».** `analytics.router.ts:224-242,454-468,936,1083,1136`.
   После полного возврата чек остаётся `closed` с полной `total_amount`. Выручка дня/месяца, график
   `/revenue`, выручка смены, траты игрока, топ-спендеры — **завышены**. Возвраты учтены только в
   `net`-ветке (`:124-128`), а экраны показывают gross.
2. **paymentBreakdown считает долг/депозит/бонус/сертификат как «оплачено».** `:285-290,401-406,523-532,1148`.
   `debt` (деньги НЕ получены) и `deposit` (деньги прошлого периода) подаются как собранные → завышает
   фактический денежный приток.
3. **Нет индекса `checks(status, created_at)`.** Почти каждый агрегат фильтрует `status='closed' AND
   created_at>=X` → **seq-scan всей `checks`** в /dashboard,/overview,/revenue,/payments,/clients.
   Сейчас терпимо, с ростом данных дашборд начнёт тормозить.

## 🟠 P1

- **Двойной счёт выручки мероприятий** — `/events` берёт полный чек, а /dashboard,/overview считают ту
  же сумму в общем gross (`:638,658`).
- **Кассир (`staff`) видит финблок, ФОТ и ПДн** — прибыль/COGS, `salaryPayments`, телефоны/ФИО клиентов
  (`/players/:id`, `/checks/:id`). Утечка коммерческой тайны и ПДн линейному персоналу (`router :15`).
- **`/api/analytics` без `requireModule('analytics')`** — арендатор с выключенным модулем всё равно
  получает аналитику (`app.ts:179`).
- **`analytics_events` растёт безгранично** — нет ретенции/чистки (`036_*.sql`, `/track`).
- **Сегменты new/active/sleeping не покрывают «ушедших»; retention фиксированные 14 дней** (`:850-906`).
- **Себестоимость в /staff и /checks/:id по текущему `cost_price`**, не зафиксированному на момент продажи
  (`:1024,1044,1426`) — после закупки COGS прошлых продаж «плывёт».
- **Фронт:** бар-чарт «по дням» пропускает нулевые дни → провалы выручки невидимы (`page.tsx:880-895`);
  hero-полоса «фин. здоровье» рисует «Прибыль» даже при убытке `net<0` (`:666,685-690`); a11y ≈ 0.

## 🟡 P2

- `/products`, `/tariffs`, top-items не сходятся с выручкой (разбивки без аренды/события/скидок).
- `/track` без спец-rate-limit, `props` до 1 МБ → раздувание таблицы.
- JS-Map агрегации вместо SQL (O(n) память) в /events, /clients, /segment-members.
- KPI анимируются с 0 при каждом refetch (мигание, лишние rAF на iPhone).
- Бары нормированы к локальному максимуму блока → «полные» бары значат разные суммы.
- Мёртвый код: `MiniBarChart` не рендерится; `ExpensesTab.tsx` лежит в dashboard/, используется в manage.

## Сильные стороны

Мультитенант: ВСЕ хендлеры читают `c.var.db` — чтения чужой БД нет, межтенантный IDOR невозможен.
Денежная база `total_amount` одинакова во всех путях закрытия чека. Чаевые/эквайринг 8% вне выручки.
COGS основного пути — по зафиксированному `stock_movements.unit_cost`. ЗП из единого источника.
Lazy-загрузка вкладок (React Query `enabled`), N+1 в /shifts устранён, графики без тяжёлой либы (CSS-бары).

## Приоритет исправлений

1. **Вычесть возвраты из выручки везде** (P0 #1) + витрина возвратов.
2. **Починить paymentBreakdown** — отделить реальный денежный приток от долга/депозита (P0 #2).
3. **Индекс `checks(status, created_at)`** + refunds/salary_payments по дате (P0 #3).
4. **Финблок/ПДн только owner** (или право `analytics:finance`); вырезать phone/ФИО/ФОТ из ответов staff.
5. **Фронт честности:** нулевые дни в графике, hero-полоса при убытке, базовая a11y.
6. Ретенция `analytics_events`; `requireModule('analytics')`; единая база разбивок = выручке.

## Возможности апгрейда

«Чистая выручка после возвратов» как первичная метрика; экран «денежный приток vs товарооборот» +
дебиторка (Σ долгов); когортный retention + LTV + сегмент `lost`; сравнение с предыдущим периодом
(пунктир); тач-first drill-down вместо hover-тултипов; единый экспорт сводки периода.
