# Аудит: Клиентский сервис Titan Resident (2026-06-18)

## Оценка: 72/100

Зрелый, продуманный consumer-PWA с грамотной серверной частью (строгая авторизация «только своё», вебхук-подтверждение денег, идемпотентность, magic-bytes для загрузок). Снижают балл: дыра в брутфорсе кода входа на стороне бота, отсутствие Service Worker (PWA офлайн не работает и не проходит критерии установки), монолитный `page.tsx` на 920 строк со styles-в-JS, отсутствие logout/смены аккаунта в UI, ноль accessibility-атрибутов.

## Как устроен сервис

Titan Resident — публичный PWA (`apps/wallet`, Next standalone, `basePath=/residents`), отдаётся на поддомене каждого клуба (`kbr.titanpos.ru/residents`), мультитенантность достигается тем, что все запросы идут same-origin на `/api/...`, а `tenantContext` (middleware/tenant.ts) резолвит клуб по Host. Авторизация двумя путями: внутри Telegram Mini App — по `initData` (`/auth/login/telegram`); из браузера/PWA — клиент жмёт «войти», PWA получает 4-значный код (`/auth/wallet-code/start`), клиент шлёт код боту-кошельку (`apps/bot-wallet`), бот помечает строку `wallet_login_codes` как claimed+profileId, PWA опрашивает `/wallet-code/status?ticket` и получает JWT на 30 дней (хранится в localStorage). Экран — три вкладки (Лента/Оплата/Профиль): голографическая карта с 3D-наклоном и бонусами, плитки депозит/долг, прогресс к статусу, единый фид «деньги+бонусы», детали чека. Оплата — онлайн-СБП через эквайер клуба (Platega и ЮKassa/Сбер/Альфа), три назначения (долг/депозит/Фонд клуба), к сумме добавляется +8% эквайринга; деньги зачисляются ТОЛЬКО при подтверждении вебхуком (`settleResidentPayment`), идемпотентно. Все `/me/*` эндпоинты строго ограничены `user.sub` — клиент видит только своё.

## Находки по severity

### [P0] Брутфорс кода входа на стороне бота → угон чужой login-сессии
- **Файл** `apps/bot-wallet/src/bot.ts:254-277`, `apps/api/src/modules/auth/auth.router.ts:459-479`
- **Суть.** Бот на любой текст `^\d{4}$` от привязанного пользователя ищет ЛЮБУЮ pending-строку `wallet_login_codes` с этим кодом по всей БД клуба (без привязки к отправителю) и клеймит её на профиль отправителя. На стороне бота НЕТ лимита попыток (`grep` по `apps/bot-wallet` пуст). Пространство кодов — всего 9000 (1000–9999), TTL 5 мин; троттлинг есть только на `/wallet-code/start` (15/10мин по IP), но не на угадывание.
- **Риск.** Злоумышленник с привязанным к клубу аккаунтом шлёт боту 9000 кодов за минуты — гарантированно попадает в активный код, инициированный ДРУГИМ человеком, и клеймит его на СВОЙ профиль. Жертва, открывшая PWA, при поллинге получит токен… своего же профиля (код клеймится на atакующего, значит жертва не войдёт), но обратный сценарий опаснее: атакующий не получает чужой токен (токен выдаётся тому, кто держит ticket), однако он может массово «гасить» чужие коды (DoS входа) и, что хуже — если бот claim'ит код на профиль атакующего, а ticket держит атакующий же в своём PWA, он входит в СВОЙ аккаунт — вреда нет; реальный вектор: code предъявляется по `code`, а токен выдаётся по `profile_id` из claimed-строки → атакующий, заклеймивший чужой pending-код на свой профиль, не крадёт данные, но **ломает вход всем** (любой код, угаданный атакующим, становится недоступен жертве). Плюс отсутствие лимита = неограниченный перебор всего адресного пространства.
- **Исправление.** (1) Лимит попыток в боте: счётчик неверных 4-значных кодов на `tgId` (Redis/память), напр. 5/час → иначе игнор. (2) Жёстче: код входа должен быть длиннее (6 знаков) ИЛИ при `start` дополнительно показывать его рядом с никнеймом инициатора и требовать подтверждение в боте кнопкой, а не свободным текстом. (3) Логировать и алертить аномалию массовых неверных кодов.

### [P1] Нет Service Worker → PWA не работает офлайн и формально неустановочна
- **Файл** `apps/wallet/public/` (нет `sw.js`), `apps/wallet/src/app/layout.tsx` (нет регистрации SW)
- **Суть.** В `apps/wallet` Service Worker отсутствует полностью (`grep serviceWorker|sw.js|workbox` пуст), в отличие от основного web (`apps/web/public/sw.js`). Manifest есть, иконки есть, но без SW: нет офлайн-фолбэка, нет кэша оболочки, при потере сети — белый экран; iOS/Android могут не предлагать установку (Chrome требует SW с fetch-обработчиком для beforeinstallprompt).
- **Риск.** Клиент в клубе с плохим Wi-Fi открывает «приложение» → пустой экран. Потерян ключевой смысл PWA (быстрый повторный запуск, работа в плохой сети у барной стойки).
- **Исправление.** Добавить минимальный SW (cache-first для статики `/residents/_next/*` + app-shell, network-first для `/api/*` с офлайн-баннером), зарегистрировать в layout. Учесть `basePath /residents` в scope. Не забыть `CACHE_VERSION`-бамп при деплоях (как для web).

### [P1] Нет выхода/смены аккаунта в UI; токен на 30 дней в localStorage
- **Файл** `apps/wallet/src/app/page.tsx` (нет кнопки logout на вкладке «Профиль»), `auth.router.ts:477` (JWT 30д)
- **Суть.** На общем/семейном устройстве клиент не может выйти и войти под другим — токен живёт 30 дней в localStorage, кнопки logout нет (бэкенд `/auth/logout` есть, фронт его не вызывает). XSS-кражи токена нет «из коробки», но 30-дневный незавершаемый сеанс — это и приватность (чужой человек видит баланс/историю/телефон), и невозможность исправить ошибочный вход.
- **Риск.** На планшете-«стойке» или одолженном телефоне предыдущий клиент остаётся залогинен; новый видит чужие деньги и ПДн.
- **Исправление.** Кнопка «Выйти» на вкладке Профиль → `POST /auth/logout` + `localStorage.removeItem` + сброс в экран кода. Рассмотреть TTL короче (7д) с тихим refresh.

### [P1] Монолит `page.tsx` 920 строк, весь UI на inline-styles
- **Файл** `apps/wallet/src/app/page.tsx:1-920`
- **Суть.** Один клиентский компонент держит весь стейт (≈30 useState/useRef), три экрана, поллинг входа, поллинг оплаты, 3D-наклон, загрузку аватара, модалку чека и ~110-строчный объект `styles`. Нет разбиения на компоненты/хуки, нет тестов, дублируется fetch-логика (`loadWallet`/`refreshData`).
- **Риск.** Высокая стоимость изменений и регрессий в денежном UI; невозможно покрыть тестами; styles-в-JS пересоздаются на каждый рендер (мелкие перерисовки на наклоне карты).
- **Исправление.** Вынести `useWalletData` (загрузка/refresh), `useLoginCode`, `usePayment` хуки; экраны Feed/Pay/Profile — отдельные компоненты; стили — в `globals.css`/CSS-модули или хотя бы `useMemo` для статичных объектов.

### [P2] Слабая обработка ошибок оплаты и «висящий» спиннер
- **Файл** `apps/wallet/src/app/page.tsx:457-495`
- **Суть.** После `window.open(paymentUrl)` поллинг статуса идёт 8 минут; если пользователь закрыл вкладку банка/передумал — `paying=true` держится до таймаута, кнопка заблокирована, нет «Отменить». На iOS `window.open(_blank)` из async-колбэка (после await) часто блокируется popup-блокером → ссылка не откроется молча, а текст обещает «Открыли страницу оплаты». Нет ретрая/диплинка в банк-апп.
- **Риск.** Клиент думает, что оплата идёт, на деле окно не открылось; UX-тупик на 8 минут.
- **Исправление.** Открывать платёж синхронно по клику (или показывать явную ссылку-кнопку при блокировке popup); кнопка «Отменить ожидание»; явный статус «окно не открылось — нажмите ссылку».

### [P2] Нет accessibility и реакции на prefers-reduced-motion; жёсткие тач-таргеты
- **Файл** `apps/wallet/src/app/page.tsx` (нав/кнопки/инпуты без `aria-*`, `role`, `aria-current`), `globals.css` (нет `prefers-reduced-motion`)
- **Суть.** Нижняя навигация — `<button>` без `aria-current`/`aria-label` (иконки только декоративные SVG без подписи для скринридера, хотя визуальная подпись есть — ок). Модалка чека без `role="dialog"`/focus-trap/Esc. Бесконечные анимации `holo`/`spin` без `prefers-reduced-motion`. `user-select:none` на всём body мешает выделить телефон/сумму. Контраст `#64748B` на `#15121b` (подсказки) ниже AA.
- **Риск.** Недоступно для части пользователей; вестибулярный дискомфорт от непрерывной голо-анимации.
- **Исправление.** `aria-current="page"` на активной вкладке, `role="dialog" aria-modal` + Esc/закрытие на модалке, `@media (prefers-reduced-motion: reduce)` отключает `holo`/наклон, поднять контраст вторичного текста до ≥4.5:1.

### [P3] Денежная математика +8%: корректна, но есть мелкие зазоры
- **Файл** `auth.router.ts:649` (charged = round2(amt*1.08)), `residentSettle.ts:44-48`, `platega.router.ts:296-317`
- **Суть.** Дизайн верный: клиент платит base×1.08, в баланс/фонд зачисляется BASE (amt), вебхук отклоняет недоплату (`verifiedAmount < amount-0.01`), переплату допускает — то есть надбавку оплатил клиент, владелец получает чистую базу. Это согласовано с кассовой логикой. Зазоры: (1) для resident-платежей сверка только «не меньше базы» — нет верхней границы, теоретически кто-то заплатил 1.08×, но мог и больше, разницу никто не учитывает (не критично, это в пользу клуба). (2) Фронт показывает «эквайринг 8%», но при `purpose=fund` суть надбавки клиенту не очевидна (платит 8% сверху взноса). (3) Минимум 1 ₽ дублируется на фронте и бэке — ок.
- **Риск.** Низкий: деньги не теряются, кассовая согласованность сохранена. Скорее прозрачность для клиента.
- **Исправление.** Явно писать «+8% берёт банк-эквайер, не клуб» в подсказке; для фонда — «итого спишется N ₽ (взнос M ₽ + 8% эквайринг)».

### [P3] Поллинг вместо realtime; нет дебаунса множественных оплат
- **Файл** `page.tsx:295-312` (вход, 2.5с), `page.tsx:475-491` (оплата, 3с)
- **Суть.** Два независимых `setInterval`-поллера. На бэкенде уже есть `publishEvent('resident:paid')` (SSE/realtime), но клиент его не слушает — крутит HTTP-поллинг. Кнопка «Оплатить» защищена `paying`, но при нескольких быстрых платежах состояние `payPollRef` перезатирается (старый интервал чистится — ок), однако несколько pending `resident_payments` могут накопиться.
- **Риск.** Лишняя нагрузка/батарея; задержка обновления баланса до тика.
- **Исправление.** Подписка на `resident:paid` через `/auth/sse-ticket` + EventSource; поллинг как фолбэк.

## Возможности апгрейда

### Продуктовые (по приоритету)

1. **[Высокий] Push-уведомления о деньгах прямо в PWA.** Бэкенд уже шлёт уведомления в Telegram (`walletNotifyEnabled`), но веб-PWA молчит. Web Push (через тот же SW из P1) о начислении бонусов, пополнении, «бонусы сгорают через 3 дня», «оплата прошла» — резко повышает retention. На iOS 16.4+ Web Push в установленном PWA поддержан.

2. **[Высокий] Полноценный онбординг + объяснение статусов/бонусов.** Сейчас первый экран — голый код входа с одной подсказкой. Добавить: что такое Резидент и зачем (карточка «вы в N визитах от статуса» уже есть — расширить до экрана «как это работает»), правила сгорания бонусов, как читать депозит/долг. Пустые состояния («Операций пока нет») заменить на мотивирующие («Сделайте первый заказ — начислим бонусы»).

3. **[Высокий] QR/диплинк вместо ручного ввода 4 цифр.** Сейчас клиент копирует код и руками шлёт боту — трение. Лучше: PWA показывает QR/кнопку `t.me/<bot>?start=login_<ticket>` (как уже сделано для account-linking с подписанными ссылками в `bot.ts`), бот подтверждает вход одной кнопкой. Это заодно закрывает P0-брутфорс (подписанный ticket вместо угадываемого кода).

4. **[Средний] Оплата чаевых/счёта из приложения.** У клиента есть деталь чека, но платить можно только долг/депозит/фонд. Логичный апгрейд — «оплатить открытый счёт» и «оставить чаевые» прямо в Resident (вебхук-инфраструктура для чеков и tip уже есть в `platega.router.ts`).

5. **[Средний] Реферальная и промо-механика.** «Пригласи друга — оба получите N бонусов», персональные акции ко дню рождения (`birthday` уже собирается). Дёшево добавить поверх существующих bonus-лотов.

6. **[Средний] История с фильтрами и экспортом.** Единый фид хорош, но при росте операций нужны фильтры (только бонусы / только платежи / период) и «скачать историю». Сейчас грузится `limit=200` без пагинации сервером (только клиентский «показать ещё»).

### Технические (по приоритету)

7. **[Высокий] Service Worker + офлайн-оболочка** (см. P1) — фундамент для push, офлайна и установки.

8. **[Высокий] Декомпозиция `page.tsx` + базовые тесты** (см. P1). Минимум — unit-тесты на денежную математику фида (фильтр дублей `withdrawal+checkId`, агрегация бонусов/денег, +8% превью) и e2e на флоу входа.

9. **[Средний] SSE вместо двойного поллинга** (см. P3) — `resident:paid` уже публикуется, осталось подписаться.

10. **[Средний] Жёсткий rate-limit и аудит входа** — лимит угадываний кода в боте (P0), лог попыток, алерт на аномалии; на `/wallet-code/start` дополнить лимит по «ticket per IP», а не только по count.

11. **[Низкий] Производительность карты** — `holo`/`spin` бесконечные анимации + пересоздание `styles` каждый рендер; вынести в CSS, добавить `prefers-reduced-motion`, `content-visibility` для длинного фида.

12. **[Низкий] i18n/локали сумм** — местами `toLocaleString('ru')`, местами `Intl.NumberFormat('ru-RU')`; унифицировать; вынести лейблы для будущей мультиязычности (клубы в разных регионах).
