# Аудит: Auth & Security (2026-06-18)

Базовый аудит: `docs/audit/02-auth-security.md` (12 июня). Этот файл — обновление по
ТЕКУЩЕМУ коду после крупного SaaS-рефакторинга (мультитенант database-per-club,
контур суперадмина, онлайн-оплаты Titan Resident, вход в кошелёк по 4-значному коду).

## Оценка: 68/100

Контур аутентификации заметно усилился с 12 июня: закрыты несколько quick-wins из
старого аудита (энумерация ников → единый 401; tablet больше не получает полноценный
staff-JWT; добавлен ленивый re-hash plaintext-паролей; разделены контуры клуб/суперадмин
обязательным `scope`-клеймом; SSE перешёл с `?token=` на одноразовые `?ticket=`). Появилась
реальная изоляция тенантов (database-per-club c fail-safe 503 на клуб-поддомене) — это
снимает C1 старого аудита для архитектуры «БД на клуб». Но добавились НОВЫЕ структурные
риски именно от мультитенанта и control-plane: единый `JWT_SECRET` теперь несёт ТРИ роли
(подпись клубных JWT + подпись суперадмин-JWT + bearer-секрет внутреннего контура ботов +
HMAC-ключ линк-подписей бота) — компрометация одного значения роняет всё; CORS жёстко
завязан на один `FRONTEND_URL` и не покрывает клуб-поддомены; код привязки планшета
генерится через `Math.random()`. Плюс не закрыты структурные пункты старого аудита:
fail-open отзыва токена при сбое Redis, отсутствие инвалидации токенов по событию
(увольнение/смена роли живут до `exp`, до 30 дней у планшета/кошелька), нет audit-log.

Для коммерческого SaaS оценку тянут вниз: переиспользование `JWT_SECRET` через контуры,
30-дневные токены клиента/планшета без серверной инвалидации, fail-open авторизации.

## Что исправлено с 12 июня

- **Энумерация ников (старый H3, quick-win #1)** — ИСПРАВЛЕНО. `/login/password`
  (`auth.router.ts:271-294`) теперь отдаёт единый `401 «Неверный логин или пароль»` и при
  неизвестном нике, и при неверном пароле. Аналогично в суперадмин-логине
  (`superadmin/auth.router.ts:260-268`).
- **Tablet под полноценным staff-JWT (старый блокер)** — ИСПРАВЛЕНО. Введён `/auth/tablet-session`
  (`auth.router.ts:113-178`): PIN лишь подтверждает ответственного сотрудника, но устройству
  выдаётся УЗКИЙ токен `role='tablet'`, привязанный к `linkedSpaceId`, с IDOR-проверками по зоне.
- **SSE-токен в URL (утечка в логи, реиграбельность)** — ИСПРАВЛЕНО. `/auth/sse-ticket`
  (`auth.router.ts:758-771`) выдаёт одноразовый UUID-тикет (Redis, TTL 60с, `getdel`);
  `requireAuth` (`auth.ts:16-27`) потребляет его однократно. Логгер маскирует `*token*` в query
  (`app.ts:57-83`).
- **Разделение контуров клуб/суперадмин** — ДОБАВЛЕНО. Суперадмин-JWT несёт обязательный
  `scope='superadmin'` (`superadmin-token.ts`); клубный `requireAuth` явно ОТКЛОНЯЕТ такой токен
  (`auth.ts:53-55`), а `verifySuperadminToken` отклоняет клубный. Суперадмин-вход —
  пароль + ОБЯЗАТЕЛЬНЫЙ passkey-второй-фактор (`superadmin/auth.router.ts:279-305`), TTL 12h.
- **Изоляция тенантов (старый C1)** — СНЯТО для архитектуры database-per-club. `tenant.ts`
  резолвит клуб по поддомену, на клуб-поддомене любая ошибка → 503 (НЕ дефолтная БД).
  Каждый роутер читает `c.var.db` клуба. Это устраняет кросс-клубный BOLA на уровне БД.
- **Плейн-текст пароли (старый H3, ч.2)** — ЧАСТИЧНО. Ленивый re-hash при первом успешном
  входе (`auth.router.ts:281-286`) есть, но разовая миграция/принудительный сброс старых
  plaintext НЕ выполнены (ветка `isPlaintext` всё ещё в коде, сравнение `===` не constant-time).
- **Глобальный backstop для fan-out PIN** — РАСШИРЕНО: отдельные глобальные счётчики для
  `/login/pin` и `/tablet-session` (`PIN_GLOBAL_FAIL_KEY` / `_TABLET`), изолированный blast-radius.

НЕ исправлено из старого аудита: fail-open отзыва токена (C2), нет инвалидации по событию и
проверки `deletedAt`/роли в `requireAuth` (H2, quick-win #5/#6), passkey `userVerification:'preferred'`
(L2), `e.message` наружу в upload/shifts (L1), нет audit-log (M5), AI-SQL на блок-листе (M1).

## Находки (по severity)

### [P0] Единый `JWT_SECRET` обслуживает 4 независимых контура безопасности
- **Файл:** `apps/api/src/modules/superadmin/superadmin-token.ts:44`; `apps/api/src/modules/internal/internal.router.ts:32-37`; `apps/bot-wallet/src/bot.ts:15,39`; `packages/auth/src/jwt.ts:43-48`
- **Суть:** один и тот же `JWT_SECRET` используется как: (1) ключ подписи КЛУБНЫХ JWT (`signToken`),
  (2) ключ подписи СУПЕРАДМИН-JWT (`signJwt` через `signSuperadminToken` — control-plane, управление
  всеми клубами), (3) bearer-секрет ВНУТРЕННЕГО контура `/api/internal/bot-clubs`, который отдаёт
  РАСШИФРОВАННЫЕ токены ботов всех клубов (`checkSecret` сравнивает заголовок `x-internal-secret`
  напрямую с `JWT_SECRET`), (4) HMAC-ключ подписи диплинков привязки аккаунта в боте (`LINK_SECRET`).
- **Риск:** компрометация ОДНОГО значения = полный pwn платформы: подделка суперадмин-токена
  (доступ ко всем клубам, провижининг, удаление), чтение токенов всех ботов через internal,
  подделка любых клубных сессий. Хуже — разделение контуров суперадмина построено НА ТОМ ЖЕ
  секрете (только клейм `scope` отличает): это «defense by claim», а не криптографическая граница.
  Любая утечка `JWT_SECRET` (бэкап env, лог, скомпрометированный бот-контейнер, у которого тот же
  secret в `env_file`) обрушивает control-plane.
- **Исправление:** развести секреты по контурам: `JWT_SECRET` (клубные токены), отдельный
  `SUPERADMIN_JWT_SECRET` (control-plane — РАЗНЫЙ ключ, тогда клубный токен физически не подпишет
  суперадмин-роут), `INTERNAL_API_SECRET` (bearer ботов), `LINK_SIGNING_SECRET` (HMAC диплинков).
  Минимум — выделить суперадмин-ключ и internal-секрет; это снимает самый широкий blast-radius.

### [P1] Fail-open проверки отзыва токена при недоступности Redis
- **Файл:** `apps/api/src/middleware/auth.ts:59-62`
- **Суть:** проверка blacklist (`revoked:<hash>`) обёрнута в `try { … } catch { /* fail-open */ }`.
  При недоступном/перегруженном Redis отозванные после logout/увольнения токены снова валидны.
  По `project_deploy_ops.md` VPS реально перегружается под сборкой — наихудший момент.
- **Риск:** logout, отзыв сессии, реакция на компрометацию перестают работать ровно в момент
  инфраструктурного стресса. Уволенный сотрудник с украденным токеном восстановит доступ,
  «уронив» Redis. Тот же fail-open в rate-limit (`rateLimit.ts:82-84`) и в PIN-backstop.
- **Исправление:** для критичных мутаций (POST/PATCH/DELETE денежных/staff/system-роутеров) при
  ошибке Redis отвечать 503, а не пускать. Альтернатива — короткий access-TTL (5-15 мин) + refresh,
  тогда blacklist менее критичен. Сейчас TTL 7-30 дней делает blacklist единственной защитой.

### [P1] Нет инвалидации токенов по событию + 30-дневные токены клиента/планшета
- **Файл:** `apps/api/src/middleware/auth.ts:44-66` (нет проверки `deletedAt`/роли/эпохи);
  `auth.router.ts:168,372,477` (TTL `'30d'` для tablet и wallet-кода); `staff.router.ts:142-172` (PATCH роли/прав)
- **Суть:** `requireAuth` проверяет только подпись + blacklist. Смена роли, снятие permissions,
  смена пароля и даже увольнение (`deletedAt`) НЕ инвалидируют уже выданные JWT — они живут до `exp`.
  Для планшета и входа в кошелёк по коду это **30 дней**. Понизили owner→staff или уволили — прежние
  права сохраняются до 30 дней. `deletedAt` учитывается ТОЛЬКО в passkey/telegram-входе, не в `requireAuth`.
- **Риск:** в мультиарендной среде увольнение/понижение/смена тарифа обязаны гасить токены мгновенно;
  сейчас — окно до 30 дней. Украденный планшетный токен (устройство на чужой точке) живёт месяц.
- **Исправление:** добавить `token_version`/`session_epoch` в `profiles`, класть в JWT и сверять в
  `requireAuth` (инкремент при смене пароля/роли/увольнении мгновенно гасит все токены владельца).
  Минимум — проверять `profiles.deletedAt` в `requireAuth` (quick-win, ~30 мин). Сократить tablet/wallet TTL.

### [P1] CORS завязан на единственный `FRONTEND_URL`, не покрывает клуб-поддомены
- **Файл:** `apps/api/src/app.ts:97-103`
- **Суть:** `cors({ origin: process.env['FRONTEND_URL'] ?? 'http://localhost:3000', credentials: true })` —
  один статический origin. При мультитенанте клубы живут на `<slug>.titanpos.ru`. Если фронт обращается
  к API cross-origin, браузерные запросы с клуб-поддоменов будут отклонены CORS (функциональный сбой),
  ЛИБО (если в проде `FRONTEND_URL` ослаблен/закомментирован) `credentials:true` с широким origin —
  риск кросс-сайтового чтения с cookie. С `credentials:true` нельзя использовать `*`.
- **Риск:** либо ломается вход на поддоменах клубов, либо (при «починке» через широкий origin)
  открывается CSRF/cross-origin-чтение. Для SaaS с поддоменами текущая конфигурация неверна by design.
- **Исправление:** origin как функция-allowlist: разрешать `https://<base>` и `https://*.<base>`
  (точная проверка `endsWith('.'+ROOT_DOMAIN)`, как уже сделано для WebAuthn `allowedOrigins`).
  Зафиксировать инвариант same-origin (фронт и API за одним nginx) либо явный список доменов.

### [P2] Код привязки планшета генерится через `Math.random()` (слабый PRNG)
- **Файл:** `apps/api/src/modules/spaces/spaces.router.ts:71`
- **Суть:** `String(Math.floor(100000 + Math.random() * 900000))` — 6-значный код привязки планшета
  (`/tablet-pair`), который в обмен выдаёт токен `role='tablet'` на **30 дней**. `Math.random()` —
  не криптостойкий PRNG (V8 xorshift128+, состояние предсказуемо/восстановимо по нескольким выходам).
- **Риск:** код живёт 5 мин в Redis, перебор ограничен per-IP лимитом (5/15мин, без глобального
  backstop — старый M3). Предсказуемость PRNG теоретически сужает пространство угадывания кода
  до выдачи 30-дневного токена киоска. Сравните: wallet-код корректно использует `randomInt`
  (`auth.router.ts:447`), а tablet-pair — нет (несогласованность).
- **Исправление:** заменить на `crypto.randomInt(100000, 1000000)` (как в wallet-code). Добавить
  глобальный backstop на `/tablet-pair` по аналогии с PIN. ~10 мин.

### [P2] Вход в кошелёк: 4-значный код + 30-дневный токен, поллинг-логика
- **Файл:** `auth.router.ts:423-479`; `apps/bot-wallet/src/bot.ts:254-277`; `058_wallet_login_codes.sql`
- **Суть:** PWA генерит 4-значный код (`randomInt`, ОК), клиент шлёт его боту, бот метит строку
  `claimed`+`profile_id`, PWA поллит `/wallet-code/status?ticket=<uuid>` и получает JWT на 30 дней.
  Брутфорс самого кода через API невозможен (бот привязывает строку к СВОЕМУ `tgId`, а статус
  поллится по UUID-тикету с высокой энтропией — корректный дизайн). НО: (1) уникальность кода
  проверяется только среди `pending` (`auth.router.ts:444-452`) — при коллизии двух одновременных
  pending-кодов одного значения бот берёт «самый свежий» (`bot.ts:266`), привязывая код к НЕ тому
  тикету (тонкая гонка: клиент A может «забрать» сессию клиента B, если оба показали один код);
  (2) выдаётся токен на 30 дней (см. P1); (3) `wallet-code/start` троттлится 15/10мин per-IP, но
  без глобального потолка.
- **Риск:** низкий по брутфорсу, но коллизия 4-значного кода (1/9000 на активную пару) при гонке
  может привязать чужую сессию. 30-дневный токен усугубляет.
- **Исправление:** в боте при `claimed` дополнительно сверять, что код уникален среди активных
  pending (иначе отклонять с просьбой обновить); поднять код до 6 знаков; сократить TTL токена.

### [P2] AI-SQL: блок-лист ключевых слов + `sql.raw` сгенерированного LLM-запроса
- **Файл:** `apps/api/src/modules/ai/ai.router.ts:233-256`
- **Суть:** `sanitizeSql` — regex-блок-лист (`insert|update|...|into`, `SENSITIVE_COL`), «только один
  SELECT/WITH», затем `runReadonly` → `sql.raw(wrapped)`. Смягчено: `SET TRANSACTION READ ONLY` +
  `statement_timeout 5s` + `LIMIT 200` + `requireRole('owner','staff')` + фильтр чувствительных таблиц/колонок.
- **Риск:** блок-листы обходятся (подзапросы, чтение `pg_*`/`information_schema`, функции). READ ONLY +
  таймаут снимают остроту (нет записи, нет долгих запросов), но чтение «не своих» метаданных остаётся.
  В database-per-club это локально для клуба (выполняется в `c.var.db`), что ограничивает утечку
  пределами одного клуба — но владелец клуба может читать колонки, не предназначенные для показа.
- **Исправление:** allow-list таблиц/вью вместо блок-листа; выполнять под отдельной БД-ролью с
  `GRANT SELECT` только на безопасные вью. Гейт уже корректно fail-closed для арендаторов (`requireAiPaid`).

### [P2] Telegram-логин: `JSON.parse` подписанного, но непроверенного `user` без try/catch
- **Файл:** `apps/api/src/modules/auth/auth.router.ts:408`
- **Суть:** `const tgUser = JSON.parse(userStr)` без обёртки. Хотя `initData` уже прошёл HMAC-проверку
  по одному из двух ботов (`auth.router.ts:399-401`), кривой `user`-JSON (теоретически от Telegram
  при изменении формата) уронит хендлер в 500 через `onError`. Старый аудит отмечал это (quick-win #2),
  не исправлено.
- **Риск:** DoS-мелочь; сам вход безопасен (без привязки `tgId` → 404, `deletedAt` учтён). Проверка по
  ДВУМ ботам (wallet+admin) расширяет доверенную поверхность на оба токена (приемлемо по бизнесу).
- **Исправление:** обернуть `JSON.parse` в try/catch → 400. ~5 мин.

### [P3] Утечка `e.message` наружу в upload/shifts
- **Файл:** `apps/api/src/modules/upload/upload.router.ts:103`; `apps/api/src/modules/shifts/shifts.router.ts:46,61`
- **Суть:** `return c.json({ error: e.message }, …)` — наружу уходит текст исключения (детали MinIO/драйвера БД).
  Эндпоинты под `requireAuth`(+роль), риск низкий, но это раскрытие инфраструктуры. WebAuthn `err.message`
  (`auth.router.ts:861,991`) — приемлемо (это сообщения библиотеки верификации, не инфра).
- **Исправление:** логировать детально в `console.error`, наружу — обобщённый текст (как `app.onError`).

### [P3] Passkey `userVerification: 'preferred'` (не `required`) для staff/owner/суперадмина
- **Файл:** `auth.router.ts:816,911`; `superadmin/auth.router.ts:156,297`
- **Суть:** passkey может пройти без user-verification (биометрия/PIN устройства), ослабляя «владение+знание»
  до «владения». Counter-проверка на клоны корректна. Особенно важно для СУПЕРАДМИНА (control-plane).
- **Исправление:** поднять до `userVerification: 'required'` на register и authenticate для staff/owner и
  ОБЯЗАТЕЛЬНО для суперадмина. ~10 мин.

### [P3] Per-IP идентификация частично подделываема (унаследовано, M3)
- **Файл:** `apps/api/src/lib/clientIp.ts:7-11`
- **Суть:** `x-real-ip` → последний элемент XFF → `'unknown'`. Корректно при гарантии «API только за nginx».
  Если API-порт открыт наружу в обход прокси — заголовки подделываются, per-IP бакеты обнуляются. Для
  `/login/password` и `/tablet-pair` нет глобального backstop (только per-IP) — в отличие от PIN.
- **Исправление:** заблокировать прямой доступ к API-порту (docker/firewall), задокументировать; добавить
  глобальный backstop на `/login/password` и `/tablet-pair`.

### [P3] Нет журнала событий безопасности (audit log) (унаследовано, M5)
- **Файл:** отсутствует. Релевантно: `staff.router.ts` (смена роли/прав), `superadmin/clubs.router.ts`
  (провижининг/удаление клуба, продление подписки), `system.router.ts` (restore/backup), passkey-удаление.
- **Суть:** привилегированные действия (выдача owner-прав, удаление клуба, restore БД, создание владельца
  суперадмином) нигде не фиксируются с актором/временем/IP. Для control-plane с доступом ко всем клубам
  отсутствие аудита особенно критично.
- **Исправление:** таблица `audit_log(actor_id, actor_kind, action, target_id, ip, meta, created_at)` в
  control-БД (для суперадмина) и в БД клуба (для staff). Писать на login success/fail, staff/role/permission
  change, club provisioning/deletion, subscription change, backup/restore, passkey-удаление.

## Возможности апгрейда (улучшения, не баги)

- **Криптографическая граница контуров вместо клейма.** Разнести `JWT_SECRET`/`SUPERADMIN_JWT_SECRET`/
  `INTERNAL_API_SECRET`/`LINK_SIGNING_SECRET` (см. P0). Даже если P0 не делать целиком — выделить хотя бы
  суперадмин-ключ: тогда подделка control-plane токена физически невозможна без второго секрета.
- **Короткий access-TTL + refresh-ротация.** Заменить 7-30-дневные JWT на access 5-15 мин + refresh-токен
  (httpOnly-cookie + CSRF, или ротация в БД). Снимает остроту fail-open blacklist (P1), даёт быструю
  инвалидацию, защищает от XSS-эксфильтрации localStorage. Самый высокоэффективный структурный апгрейд.
- **`session_epoch`/`token_version` в профиле.** Дёшево даёт «разлогинить всех», мгновенный отзыв при
  увольнении/смене роли, кнопку «выйти со всех устройств». Продаётся как премиум-фича SaaS (owner security
  dashboard: активные сессии, последние входы, всплески неудачных PIN).
- **Step-up auth на деньги/деструктив.** Повторный passkey/PIN перед restore БД, удалением клуба, выдачей
  owner-прав, ручной корректировкой баланса > порога — снижает урон от украденного токена.
- **WebAuthn `required` + attestation для суперадмина.** Control-plane заслуживает строжайшего второго фактора.
- **Per-tenant rate-limit и PIN keyspace.** Сейчас глобальные PIN-счётчики общие для инстанса; в чистом
  database-per-club они уже изолированы по БД, но Redis-ключи (`pin:fail:global`) — НЕТ (общий Redis на
  инстанс). Префиксовать ключи лимитов клубом (`<clubId>:pin:fail:global`), иначе DoS-локаут одного клуба
  через fan-out PIN затронет вход всех клубов инстанса.
- **Pepper для PIN/паролей** (HMAC-pepper из отдельного секрета перед bcrypt) — bcrypt(rounds=10) для
  4-значного PIN сам по себе слабоват против офлайн-перебора при утечке БД; pepper, которого нет в дампе, помогает.
- **Audit-log как продуктовая фича** (см. P3) — B2B-клиенты SaaS его запросят.
