# Аудит: Платежи & Фискализация 54-ФЗ (2026-06-18)

Аудитор: senior-аудитор платёжных систем РФ. Предмет: платёжный слой, добавленный
ПОСЛЕ аудита `01-payments.md` (12.06): провайдеро-независимый СБП-слой (`pay/*`),
фискализация 54-ФЗ (`pay/fiscal/*`), онлайн-платежи резидентов (`resident_payments`),
эквайринг-надбавка +8%. База — `01-payments.md` (оценка 62/100).

## Оценка: 71/100

Слой вырос качественно: HMAC-проверка подписи Т-Банка реальна, секреты провайдеров
шифруются AES-256-GCM, тело вебхука больше не авторитетно (серверная сверка статуса
с ретраями во ВСЕХ путях), фискальный воркер идемпотентен и изолирован от денежного
пути. Но появились новые денежные/правовые риски: **критический — Platega-вебхук
теперь за гейтами подписки/модуля → при истёкшей подписке клуба деньги списываются,
а чек не закрывается**; фискальный чек 54-ФЗ пробивается на товарную сумму, а клиент
заплатил +8% (или +чаевые) → **расхождение чека с фактически уплаченной суммой**;
RBS-провайдеры (Сбер/Альфа) вообще не проверяют подпись callback; рекомендация H1 из
прошлого аудита (idempotencyKey на проводку) не выполнена.

## Находки по severity

### [P0] Platega-вебхук за гейтами подписки/модуля → деньги списаны, чек не закрыт
**Файл:** `apps/api/src/app.ts:148,154,183`
**Суть:** `app.route('/api/platega', plategaRouter)` (стр. 183) монтируется ПОСЛЕ
`app.use('/api/*', requireActiveSubscription)` (148) и `app.use('/api/platega/*', requireModule('platega'))` (154).
Для клуб-поддомена с истёкшей/приостановленной подпиской входящий вебхук Platega
получает **402** (`subscription.ts:33`) и не доходит до обработчика; при
`club.modules.platega===false` — **403** (`module.ts:16`). `/api/pay` этого избегает —
смонтирован на стр. 140, ДО гейтов (и комментарий это явно фиксирует), а Platega — нет.
**Риск (деньги):** гость оплатил по СБП, Platega получила деньги, но чек у клуба с
просроченной подпиской НЕ закроется (402/403 → Platega ретраит, всё время 402 →
сдаётся). Выручка получена, в системе не отражена; ручной разбор. Подписочные платежи
(`payload sub:...`, продление самой подписки!) тоже блокируются — клуб не может
оплатить продление, потому что вебхук о его оплате режется истёкшей подпиской. Тупик.
**Исправление:** перенести `app.route('/api/platega', plategaRouter)` ВЫШЕ строки 148
(рядом с `/api/pay` и `/api/tg`), как внешний вебхук, не зависящий от подписки/модуля.
Либо добавить `/api/platega/webhook` в `isAllowlisted` (`subscription.ts:16`) и снять
`requireModule('platega')` с пути `/webhook`.

### [P1] Фискальный чек 54-ФЗ пробивается на товарную сумму, а клиент заплатил +8%/+чаевые
**Файл:** `apps/api/src/cron/fiscalize.ts:56-57`, `pay/fiscal/buildReceipt.ts:115-118`
**Суть:** воркер строит чек из `check.total_amount` (= БАЗОВАЯ товарная сумма; webhook
закрывает чек именно на неё, `settle.ts:102-103`). Но клиент по СБП фактически заплатил
`total × 1.08` (надбавка) и/или `+ tip`. Эквайринговая надбавка фиксируется в
`checks.acquiring_surcharge`, чаевые — в `checks.tip_amount`, но в фискальный чек НЕ
попадают. Для самостоятельных касс (АТОЛ/Ferma) пробивается чек на сумму МЕНЬШЕ
поступившей на счёт.
**Риск (закон, 54-ФЗ):** сумма пробитого чека не равна сумме, фактически принятой от
покупателя по эквайрингу. Если надбавка/чаевые — часть расчёта (а они проходят через
тот же СБП-платёж), это занижение фискальной выручки → нарушение 54-ФЗ, риск штрафа
ФНС. Минимум — надбавку 8% надо либо пробивать отдельной позицией («услуги эквайринга»),
либо не брать с клиента через фиск-канал.
**Исправление:** определиться юридически. Если надбавка/чаевые принимаются эквайрингом —
включать их в фискальный чек (отдельной строкой или в total). Воркеру передавать
фактически принятую сумму (`total + acquiring_surcharge + tip`), а не голый `total_amount`.

### [P1] ЮKassa-фискализация: чек на полную сумму (с надбавкой), а чек закрывается на базу — несходимость
**Файл:** `apps/api/src/modules/pos/pos.router.ts:1432`, `pay/fiscal/receipt.ts:34-60`
**Суть:** для ЮKassa (встроенная фискализация) `buildCheckReceipt(db, check, amount)`
получает `amount` = списываемая сумма (с надбавкой+чаевыми) — это правильно для самой
ЮKassa (чек обязан сойтись с платежом). Но позиции строит `buildReceiptLines(db, checkId, amount, ...)`
из позиций чека, масштабируя их до `amount`. То есть надбавка 8% «размазывается» по
товарным позициям как удорожание товара. Покупатель в чеке видит завышенные цены
товаров вместо честной строки «эквайринговая комиссия». Полусерая зона 54-ФЗ
(признак предмета расчёта для надбавки/чаевых — не «товар»).
**Риск (закон):** неверный признак предмета расчёта (надбавка/чаевые как товар);
расхождение цены позиции в чеке с реальной ценой в меню.
**Исправление:** надбавку и чаевые выносить отдельными позициями с корректными
`payment_subject` (например `payment` для чаевых, `service`/`another` для эквайринга),
не масштабировать товарные цены.

### [P1] RBS-провайдеры (Сбер/Альфа) не проверяют подпись callback
**Файл:** `apps/api/src/modules/pay/providers/rbs.ts:79-95`
**Суть:** `verifyWebhook` для Сбера/Альфы возвращает `ok: true` БЕЗ проверки checksum/
симметричного ключа (комментарий: «полагаемся на серверную сверку статуса»). Защита —
только последующий `fetchStatus` через `getOrderStatusExtended.do` (`pay.router.ts:54-62`).
Это работает как компенсация (как у Platega/ЮKassa), НО: (а) `checkId` берётся из
незаверенного callback (`orderNumber`); злоумышленник, знающий чей-то `orderId`+`orderNumber`,
может спровоцировать re-fetch и закрытие ЧУЖОГО заказа, если тот реально оплачен в RBS;
(б) re-fetch для RBS возвращает статус по `orderId` из тела — если подделать `mdOrder`
на реальный оплаченный заказ другого мерчанта в том же RBS-инстансе, можно закрыть не
тот чек. Риск ниже, чем при отсутствии re-fetch, но HMAC у RBS поддерживается и не
используется.
**Риск (деньги):** закрытие чужого/не того чека через подделанный callback при знании
идентификаторов. Для одного клуба умеренный; в SaaS выше.
**Исправление:** реализовать проверку RBS checksum (симметричный ключ из ЛК банка) в
`verifyWebhook`; не доверять `checkId` из тела для выбора чека без сверки принадлежности.

### [P1] idempotencyKey на платёжной проводке так и не пишется; нет unique на platega_tx_id
**Файл:** `settle.ts:95-101`, `platega.router.ts:324-330`, схема `checks` (нет unique на `platega_tx_id`)
**Суть:** рекомендация H1 прошлого аудита (quick win #3) не выполнена. `transactions`
и `checkPayments`, вставляемые во ВСЕХ путях settle, оставляют `idempotency_key = NULL`
(уникальный индекс из миграции 045 существует, но не задействован). Защита от повтора —
только in-app `if (check.status !== 'open') return 'noop'` под `FOR UPDATE`. Для
нормального двойного callback по одному чеку этого достаточно. Но БД-инварианта против
задвоения проводки нет: при гонке/смене статуса чека/ручной правке возможна повторная
вставка платёжной транзакции.
**Риск (деньги):** теоретическое задвоение проводки/бонусов; полагаться на единственный
app-guard в платежах недостаточно.
**Исправление:** писать `idempotencyKey: provider+':'+transactionId` в
`transactions.insert` (unique-индекс уже есть, 045) во всех settle-путях; добавить
частичный unique на `checks(platega_tx_id) WHERE platega_tx_id IS NOT NULL`.

### [P2] Остаточный риск Platega: всё ещё нет подписи тела, защита только через re-fetch
**Файл:** `apps/api/src/modules/platega/platega.router.ts:160-219`
**Суть:** re-fetch закрывает вектор подделки статуса, но: (а) `X-Secret` — bearer в
заголовке, риск утечки в логах прокси (L3 прошлого аудита не закрыт явно); (б) при
DoS на эндпоинт `/transaction/{id}` Platega (или сетевом сбое) все вебхуки уходят в
503 и чеки не закрываются — деградация под нагрузкой/атакой.
**Риск (деньги):** задержка закрытия чеков при недоступности API Platega.
**Исправление:** IP-allowlist Platega на nginx; перейти на HMAC, когда Platega его даст;
убедиться, что nginx не логирует заголовки `/api/platega/*` и `/api/pay/*`.

### [P2] C2 не закрыт полностью: ручной перевод всё ещё в «потерях эквайринга»
**Файл:** `apps/api/src/modules/analytics/analytics.router.ts:138-139,182`
**Суть:** SBP-комиссия = `sum(transfer-платежей, где surcharge=0) × 0.08`. Фильтр по
`surcharge=0` добавлен, но `method='transfer'` ставится и ручным переводом кассира
(без эквайринга). Нет фильтра `platega_tx_id IS NOT NULL` (или нового аналога для
pay-провайдеров — у них tx-id в `transactions.description`, отдельной колонки нет).
**Риск (деньги/учёт):** завышение расходов на 8% по каждому ручному переводу → искажён
P&L, по которому владелец принимает решения.
**Исправление:** считать комиссию только по чекам с реальным СБП-эквайером; завести
явную колонку `checks.sbp_provider`/`acquirer` вместо опоры на `platega_tx_id`
(pay-провайдеры её не заполняют — они вообще не пишут tx-id в `checks`).

### [P2] Ставка 8% зашита константой в 5 местах (M2 не закрыт)
**Файл:** `pos.router.ts:1406,1415`, `auth.router.ts:649`, `settle.ts:75,88`,
`platega.router.ts:298,315,317`, `analytics.router.ts:182`
**Суть:** множитель `1.08`/`0.08` продублирован. Реальная комиссия эквайринга СБП
0.4–0.7%; 8% — продуктовая надбавка, но не настраивается. В SaaS у клубов разные ставки.
**Риск:** нельзя поменять без релиза; неверная ставка → неверная сумма к оплате гостя.
**Исправление:** вынести `acquiring_surcharge_rate` в `app_settings`, читать в одном
helper, использовать везде.

### [P2] pay-провайдеры (Т-Банк/Сбер/Альфа) не фискализируют — 54-ФЗ только через воркер, RBS-чек теряется
**Файл:** `cron/fiscalize.ts:33-43` (окно 60 минут), `pay/fiscal/buildReceipt.ts:128`
**Суть:** для СБП-оплат через Т-Банк/Сбер/Альфа фискальный чек пробивает ТОЛЬКО фоновый
воркер по самостоятельной кассе (АТОЛ/Ferma). Если у клуба нет самостоятельной кассы,
а фиск-провайдер = ЮKassa — но платёж шёл через Т-Банк, то `buildCheckReceipt`
сработает только для активного провайдера ЮKassa → чек НЕ пробивается ни в одном
канале. Плюс воркер сканирует окно 60 минут по `closed_at`; чек, закрытый и упавший в
`failed` 5 раз за час, навсегда останется нефискализированным (выпадает из окна,
`attempts>=5`). Без контакта покупателя (телефона) — `failed`, исчерпает попытки → нет чека.
**Риск (закон):** пропуск фискального чека для части СБП-оплат → нарушение 54-ФЗ.
**Исправление:** гарантировать фискальный канал для каждой СБП-оплаты независимо от
эквайера; алертить владельцу о `failed`/`skipped (нет телефона)` чеках; реконсиляция
«закрыт, но не фискализирован» без ограничения окном.

### [P3] Сверка суммы допускает «коридор» переплаты до 8%+1₽ недетерминированно
**Файл:** `settle.ts:73-88`, `platega.router.ts:296-317`
**Суть:** при наличии `verifiedAmount` коридор `[total-0.01 ... expectedWithTip×1.08+1]`.
Атрибуция чаевых/надбавки решается порогами (`>= expectedWithTip-1`, `>= ×1.08-1`).
Переплата гостя по ошибке в этот коридор может быть зачтена как чаевые/надбавка.
**Риск:** редкие копеечные расхождения в учёте чаевых/комиссии.
**Исправление:** требовать `amount` от провайдера; сузить коридор; логировать расхождения.

### [P3] resident_payments: онлайн-пополнения депозита/долга/фонда не фискализируются
**Файл:** `pay/residentSettle.ts:80-93`, `auth.router.ts:626-708`
**Суть:** онлайн-платёж резидента (`purpose=deposit|debt|fund`) принимается по СБП с
надбавкой ×1.08, кредитует `profiles.balance` или копилку фонда, но фискальный чек не
пробивается ни в одном пути (воркер сканирует только `checks`, не `resident_payments`).
**Риск (закон):** если это приём предоплаты/аванса от физлица за услуги — может
требовать фискализации (аванс/предоплата 54-ФЗ). Юридически зависит от трактовки
(депозит/долг/взнос в фонд). Требует консультации.
**Исправление:** оценить юридически; при необходимости — фискализировать
`resident_payments` (признак расчёта «аванс»/«предоплата»).

### [P3] resident_payments: нет unique на transaction_id, applied_at без unique-инварианта
**Файл:** миграция `059_resident_payments.sql`, `residentSettle.ts:40-42`
**Суть:** идемпотентность держится на `FOR UPDATE` + `status !== 'pending'`. БД-unique
на `transaction_id` нет. Достаточно для нормального ретрая вебхука, но БД-инварианта нет
(как и у `checks`).
**Исправление:** частичный unique на `resident_payments(transaction_id) WHERE transaction_id IS NOT NULL`.

## Что сделано хорошо (подтверждено)

- **Секреты провайдеров шифруются** AES-256-GCM, мастер-ключ в env, plaintext не
  выходит наружу (`lib/secrets.ts`) — закрывает риск plaintext-ключей эквайринга.
- **Тело вебхука не авторитетно во ВСЕХ путях**: re-fetch статуса с 3 ретраями +
  обработка eventual-consistency (`platega.router.ts`, `pay.router.ts`).
- **Подпись Т-Банка реальна**: SHA-256 Token по корневым скалярам + пароль, сверяется
  на входящем вебхуке (`tbank.ts:93-117`).
- **Деньги — целые `numeric(12,2)`**, единый `round2`/`computeTotals`, копейки в
  суммах к провайдеру (`Math.round(amount*100)` для Т-Банк/RBS), серверный пересчёт
  суммы QR (клиенту не доверяют).
- **Фискальный воркер изолирован** от денежного пути (нулевой риск для продаж),
  идемпотентен по `check_id` (unique), ретраи с лимитом, сумма строк сводится к total.
- **Атомарность + FOR UPDATE** в settle/resident-settle; идемпотентность по статусу.
- **`/api/pay` и `/api/platega/webhook`** исключены из rateLimit / подписки (pay) —
  правильно для внешних вебхуков (КРОМЕ самого `/api/platega`, см. P0).

## Возможности апгрейда

1. **Единый платёжный леджер + реконсиляция.** Таблица входящих вебхуков (raw payload,
   provider, tx_id, результат, club_id) + крон-сверка «у эквайера CONFIRMED, а чек/
   resident_payment не закрыт» с алертом владельцу. Закрывает P0-последствия, P2-фискал-
   гэп, даёт аудит-трейл для споров.
2. **Фискализация как сквозной инвариант.** Каждая принятая СБП-оплата (чек И
   resident_payment) → ровно один фискальный чек на ФАКТИЧЕСКИ принятую сумму; надбавка/
   чаевые — отдельными позициями с верным признаком предмета расчёта. Снимает P1-1/P1-2/
   P2-фискал и юридический риск 54-ФЗ.
3. **Конфигурируемая ставка эквайринга per-club + явная колонка `acquirer` на чеке.**
   Ставка в `app_settings`, провайдер-маркер в `checks` → корректный P&L (закрывает C2/M2),
   надёжная атрибуция комиссии без опоры на `platega_tx_id`.
