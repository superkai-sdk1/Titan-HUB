# Аудит: Бэкенд бизнес-логика (2026-06-18)

Аудитор: senior backend. Периметр: корректность бизнес-логики `apps/api/src/modules/*`
ВНЕ платежей-провайдера, auth и многотенантности (их смотрят 01/03). Стек: Hono +
Drizzle ORM + Postgres, БД инжектится в `c.var.db` (синглтон на основном домене или
per-club инстанс по поддомену). Транзакции — `db.transaction(async tx => {})`, сырой
SQL через `sql\`...\``, блокировки строк через `SELECT ... FOR UPDATE` / `.for('update')`.

Контекст из аудита 12 июня (03–07): денежное ядро POS-чекаута уже было приведено к
`FOR UPDATE` + парные `transactions`; этот рефреш проверяет ТЕКУЩИЙ код + новые модули
(`collections` мигр. 053, `bookings` мигр. 055-057, `certificates`, `cashops`, `refunds`).

## Оценка: 71/100

Денежный «горячий путь» (POS `/pay`, погашение сертификата в POS, депозит/долг/бонусы,
закрытие смены) спроектирован грамотно: транзакции и `FOR UPDATE` на месте, идемпотентность
закрытия через `status='open'` под row-lock, единая денежная математика в `lib/money.ts`
(round2 / clamp скидок / max(0)). Двойного списания денег или склада в штатном потоке нет.

Снимают баллы системные пробелы на ПЕРИФЕРИИ денежного ядра, где транзакция/блокировка
отсутствует или поверхностна: задвоение возврата (refunds), задвоение/несогласованность
зарплаты, утечка/обезличивание баланса при удалении клиента, незащищённое изъятие кассы
в минус, дыры в детекции пересечения броней, и публичный виджет бронирования без анти-спам
барьера. Денег эти дефекты в основном не теряют напрямую, но рассинхронизируют учёт,
производные метрики и допускают редкие, но дорогие по последствиям расхождения.

## Находки по severity

### [P0] refunds.router.ts:73-244 — задвоение возврата (нет сериализации по чеку)
Возврат блокирует `checks ... FOR UPDATE` (стр.74), но лимит «уже возвращено» (`prevRefunds`,
стр.85) читается обычным `SELECT` без блокировки, а сам возврат в `checks` НЕ пишет — значит
`FOR UPDATE` на `checks` фактически НЕ сериализует два параллельных возврата по одному чеку.
На READ COMMITTED (дефолт Postgres) оба видят одинаковый `prevRefunds`, оба проходят `amt >
available` и оба вставляют → суммарно возвращается 2× оплаченного.
**Риск:** двойной возврат денег/склада/кассы по одному чеку (двойной клик/две вкладки).
**Фикс:** advisory-lock по `checkId` (`pg_advisory_xact_lock`) в начале транзакции, либо
`SERIALIZABLE`-изоляция, либо хранить «возвращено» прямо в строке `checks` и менять её под
`FOR UPDATE`, чтобы row-lock реально сериализовал.

### [P0] salary.router.ts:112-163 — задвоение начисления ЗП (нет дедупа по периоду)
Защита от дубля держится ТОЛЬКО на клиентском `idempotencyKey` (генерится на маунте фронта,
сбрасывается лишь `onSuccess`). На уровне БД нет уникальности `(profileId, period)`. Перезагрузка
страницы / другое устройство / прямой вызов API без ключа → `onConflictDoNothing({target:
idempotencyKey})` при `idempotencyKey=undefined` бьёт по nullable-колонке (NULL'ы в Postgres
не конфликтуют) → вставка всегда проходит. Создаётся вторая `salaryPayments` + вторая
`cashOperations type='salary'`.
**Риск:** двойная выплата зарплаты + двойное изъятие из кассы.
**Фикс:** уникальный частичный индекс `(profileId, period)`; сделать `idempotencyKey`
обязательным в `PaySalarySchema` или генерить серверный ключ из `profileId+period`.

### [P0] salary.router.ts:76-106 — две РАЗНЫЕ базы выручки в одном `calculateSalary`
Ветка `?day=` (стр.76) считает выручку КЛУБА `sum(totalAmount − eventBaseAmount)` без
`staffId`. Ветка `?from/to` (стр.95-102) — выручку по конкретному `staffId` и БЕЗ вычитания
`eventBaseAmount`. Один эндпоинт даёт несопоставимые цифры; фактическая выплата фронт берёт
из дневной (клуб-wide) ветки → при 2+ сотрудниках на смене каждый получает % от ПОЛНОЙ
выручки клуба.
**Риск:** завышение/задвоение фонда ЗП на сменах с несколькими сотрудниками.
**Фикс:** привести обе ветки к единой базе (вычитать `eventBaseAmount` в обеих, определиться
клубная/персональная), согласовать с моделью «одна выплата на смену».

### [P0] clients.router.ts:502-505 — мягкое удаление клиента игнорирует ненулевой баланс
`DELETE /:id` ставит `deletedAt` без проверки `balance`. Клиент с депозитом (+) или долгом (−)
уходит в архив и пропадает из всех списков (`balances`/`debtors`/`deposits` фильтруют
`isNull(deletedAt)`). Обязательство/деньги исчезают из учёта.
**Риск:** потерянные депозиты и непогашенные долги, рассинхрон кассы/отчётности.
**Фикс:** блокировать архивацию при `balance <> 0` (или требовать `?force` + компенсирующая
`transaction`).

### [P0] clients.router.ts:516-566 — permanent-delete обезличивает финансовую историю
`transactions.player_id` nullable → ветка зануления `UPDATE transactions SET player_id = NULL`:
все депозиты/долги/списания профиля теряют привязку. Сам `profiles`-row удаляется, его `balance`
никакой компенсирующей транзакцией не снимается — при ненулевом балансе деньги/долг исчезают
без следа. `bonus_history.profile_id` NOT NULL → бонус-история разных клиентов склеивается на
sentinel «Удалённый пользователь».
**Риск:** невосстановимая потеря денежной истории и обязательств; искажение аналитики.
**Фикс:** запрещать permanent-delete при `balance <> 0`; архивная выгрузка транзакций перед
занулением FK.

### [P1] cashops.router.ts:42-75 — изъятие кассы в минус без проверки остатка
`withdrawal`/`salary` валидирует только `amount.positive()`, не сверяясь с
`getShiftCashBalance(shift.id).expected`. Можно изъять больше, чем есть в кассе → отрицательный
ожидаемый остаток, маскировка недостачи при инкассации/закрытии смены.
**Риск:** целостность кассы; недостача прячется за отрицательным остатком.
**Фикс:** перед вставкой считать `expected` под блокировкой смены и отклонять `amount > expected`.

### [P1] pos.router.ts:867,984,1154,1190,1261-1271,1300,1316 — `recalcCheckTotal()` вне транзакции
После УЖЕ закоммиченной мутации позиции/скидки на сыром `db` вызывается `recalcCheckTotal`,
а внутри это многошаговая операция (авто-скидки delete+insert, апдейт `totalAmount`) без
блокировки чека. Два параллельных запроса по одному чеку (или сбой между шагами) →
`totalAmount`/`discountTotal`/строки `checkDiscounts` «уезжают». Отдельно стаф-скидка (стр.1248-1252):
cap-проверка `existingSum + discountAmount` читается заранее, два параллельных запроса проходят
cap каждый по старому `existingSum` → суммарно обнуляют чек сверх лимита (обход анти-злоупотребления).
**Риск:** неверная сумма к оплате/задвоенные авто-скидки; обходимый лимит стаф-скидки (бесплатный
чек руками сотрудника). Денег напрямую не теряет (финальный `/pay` под `FOR UPDATE`), но искажает итог.
**Фикс:** объединить мутацию позиции/скидки и `recalcCheckTotal` в одну транзакцию с `checks ...
FOR UPDATE`.

### [P1] events.router.ts:112-185 — дырявая детекция пересечения броней
(а) Для бессрочных событий (`endTime=null`) окно вырождается в точку: `COALESCE(endTime,startTime)`
→ два события 19:00 и 19:30 в одной зоне НЕ пересекаются. (б) `startTime/endTime` — `text`,
лексикографическое сравнение `>=/<=` ломается на ночных событиях через полночь (22:00→02:00),
валидации `endTime > startTime` нет. (в) `findOverlappingEvent` и `insert`/PATCH-апдейт идут
двумя отдельными запросами без общей транзакции/блокировки → два одновременных POST на одну
зону/время оба не находят конфликт и оба вставляются.
**Риск:** двойная бронь зоны, двойная тарификация, конфликт расписания.
**Фикс:** считать пересечение на timestamp (date+time), требовать `endTime` для titan-событий
(или трактовать null как конец дня), проверку выполнять внутри той же транзакции под advisory-lock
по `spaceId+date`.

### [P1] pos.router.ts:635-660 — открытие чека с зоной/событием без транзакции и блокировки
Анти-двойная-бронь зоны: `SELECT` занятости (стр.637) и `INSERT` чека (стр.646) без транзакции
(partial unique index `(spaceId) WHERE status='open'` обещан комментарием, но не внедрён) → два
одновременных открытия создают две аренды одной зоны. Лимит гостей события (стр.626) и инкремент
`events.attendeesCount` (стр.657) — тоже отдельными запросами без транзакции → гонка превышает
`maxGuests`, рассинхрон счётчика при сбое между вставкой чека и инкрементом.
**Риск:** двойная тарификация зоны, превышение лимита гостей, рассинхрон счётчика мероприятия.
**Фикс:** внедрить обещанный partial unique index; обернуть открытие чека+инкремент в транзакцию,
инкремент атомарным `attendeesCount = attendeesCount+1` с проверкой лимита в одном UPDATE.

### [P1] inventory ledger (ledger.ts:62-63 + inventory.router.ts:141,58) — оверселл-минус ломает ревизию
Продажа разрешает уход остатка в минус (`clamp:false`, pos.router.ts:171). Ревизия снапшотит
`expected = item.stockQuantity` (может быть −5) и считает `diff = actual − expected = 0−(−5) = +5`,
трактуя покрытие ранее проданного «в минус» как ИЗЛИШЕК 5 шт. Сам `count` с `clamp:true`
корректно подтягивает −5→0, но `surplusValue`/KPI излишков-недостач врут на величину накопленного
оверселла.
**Риск:** искажение метрик ревизии (излишки/недостачи) и стоимости остатка.
**Фикс:** клампить `expected` в ноль перед снапшотом/`diff` (считать diff от `max(0, expected)`).

### [P1] supplies.router.ts:325-363 — PATCH закупки не идемпотентен по аудиту + дрейф WAC
(а) Комментарий обещает «повторный PATCH тем же телом → дельта 0», но `supply_items` каждый
раз `DELETE`+`INSERT` и каждый раз пишется новая `supply_corrections` → ретрай задваивает историю
корректировок фантомными правками. (б) PATCH/DELETE меняют количество принятой партии (delta стр.345-352),
но WAC (`cost_price`) сознательно не пересчитывают → после смещения WAC вверх по партии себестоимость
остаётся завышенной на не принятый по факту товар.
**Риск:** дрейф средневзвешенной себестоимости (искажение маржи/`stockValue`), засорение аудита.
**Фикс:** no-op запись `supplyCorrections` при нулевой net-дельте; запретить правку количества
(только цена/примечание) либо разворачивать вклад партии в WAC.

### [P1] shifts.service.ts:24-33 — TOCTOU базиса кассы при открытии смены
Уникальный индекс `shifts_one_open` (мигр. 032) корректно ловит гонку самой вставки второй
открытой смены (23505). Но `getLastShiftCashEnd` и расчёт `expectedStart`/`diff` (стр.29-33)
выполняются ДО `database.transaction` (стр.43) → при гонке «закрытие прошлой ↔ открытие новой»
базис непрерывности кассы читается до блокировки.
**Риск:** ложное/пропущенное расхождение кассы на старте смены.
**Фикс:** читать `getLastShiftCashEnd` и считать `expectedStart` ВНУТРИ транзакции открытия.

### [P1] bookings.router.ts:95-142 — публичный приём брони без анти-спам барьера
`POST /api/bookings/public/` смонтирован ДО `requireActiveSubscription`, без auth. Защита =
только глобальный per-IP rate-limit (120/мин анон) + флаг `booking_enabled` + zod. Нет капчи,
нет лимита броней на телефон, нет защиты от ботов. Дедуп заказчика по телефону (стр.115-129) —
best-effort в `try/catch`, без блокировки → два одновременных POST одним номером создадут два
`customers` (read-then-insert вне транзакции). Уведомления владельцам (стр.136-138) — `await`
в цикле по всем `owner` (N+1), любой может массово слать брони → спам-флуд push владельцам.
**Риск:** спам/флуд заявок и push-уведомлений с одного IP до лимита, дубли заказчиков.
**Фикс:** капча/turnstile или жёсткий per-phone/per-IP лимит на создание брони (отдельный
от глобального), батч уведомлений, дедуп заказчика через `ON CONFLICT` по нормализованному телефону.

### [P1] pos.router.ts:1591-1597 — аренда зоны считается «вживую» от `Date.now()` без фиксации
`computeRental` берёт конец периода = `spaceEndAt ?? now`, итог чека пересчитывается от текущего
момента в каждой ветке (recalc/pay/webhook). При почти одновременной нал/безнал-оплате с активной
арендой каждая ветка считает аренду от своего `now` → суммы тендеров разъезжаются на копейки-рубли.
**Риск:** оплаченная сумма ≠ итог чека при одновременной оплате с активной арендой.
**Фикс:** фиксировать `spaceEndAt` в момент начала оплаты (одна точка времени на весь расчёт чека).

### [P2] collections.router.ts:316-349 — дубль-взнос даёт 500 вместо 409 (деньги безопасны)
`/pay` читает существование взноса (стр.318), затем вставляет (стр.344) в одной транзакции, но
на READ COMMITTED два параллельных запроса оба проходят проверку; уникальный индекс

ошибка → `app.onError` отдаёт 500 (вместо штатного 409 «уже отмечен»). Для `deposit/debt` баланс
списывается в той же транзакции до insert, на ошибке всё откатывается — **двойного списания
баланса НЕТ**. Это косметика UX, не потеря денег. Баланс под `FOR UPDATE` (стр.326), реверс
в delete тоже под `FOR UPDATE` (стр.367) — корректно.
**Фикс:** обернуть insert в try/catch на код `23505` → вернуть 409.

### [P2] bookings.router.ts:64-79,145-159 — `lookup`/`:token` без защиты от перебора
`GET /lookup?phone=` возвращает до 20 броней по последним 10 цифрам телефона (имя, телефон,

**Риск:** утечка ПДн (имя/телефон/комментарий) и угон чужой брони перебором телефона.
**Фикс:** не отдавать `claim_token` в `/lookup`; ограничить выдачу полей; rate-limit на `/lookup`.

### [P2] refunds.router.ts:198-206 — возврат на сертификат сверх номинала
`certCredit` прибавляется к `cert.balance` без проверки `<= nominal`. Частично потраченный в
другом чеке сертификат может «перезарядиться» выше номинала.
**Риск:** бесплатные средства на сертификате.
**Фикс:** `nb = min(round2(balance + certCredit), nominal)`.

### [P2] clients.router.ts:610-611 — сумма пополнения/списания без границ
`amount: z.number()` без `.min()/.max()/.finite()` (ср. `/bonus` ограничен `−1e6..1e6`). Лимит
долга ловит только отрицательные за пределами `max_client_debt`; положительные не ограничены —
опечатка кассира на много нулей мгновенно создаёт гигантский депозит.
**Риск:** грубая операторская ошибка в балансе без барьера.
**Фикс:** `.finite().min().max()` на `amount`, как в `/bonus`.

### [P2] pos.router.ts:1413-1416,1747-1761 — `acquiringSurcharge` не сбрасывается при оплате наличными

**Риск:** искажение отчёта по эквайрингу.

### [P2] spaces.router.ts:71 — код привязки планшета через `Math.random()`
6-значный код пейринга генерится `Math.random()` (предсказуем), при том что certificates.router.ts:11

### [P2] money.ts:31-33 — item-скидки клампятся только по итогу чека, не по позиции
`computeTotals` обрезает суммарную скидку `Math.min(discountTotal, gross)`, но несколько item-скидок

**Риск:** некорректная разбивка скидок по позициям (сумма сходится, строки нет).
**Фикс:** клампить item-скидки по базе позиции на этапе суммирования.

## Проверено и КОРРЕКТНО (для контекста)
- POS `/pay` (pos:1569-1805): вся денежная мутация в одной транзакции, чек+клиент+сертификат под
  `FOR UPDATE`, идемпотентность через `status='open'` под lock; двойной клик/ретрай → `CHECK_NOT_OPEN`.
- POS `/pay` ↔ webhook `settle.ts`: оба берут `checks FOR UPDATE` + guard `status!=='open'→noop` —
  двойного закрытия (касса + QR) нет.
- Погашение сертификата в POS (pos:1639-1642): одна строка под `.for('update')`, проверка остатка,
  `max(0, ...)` — двойного перерасхода нет (`validate` без резервации — лишь UX-нюанс).
- `clients` `/balance` (635-675): `FOR UPDATE` + идемпотентность через ПОЛНЫЙ unique-индекс
  `transactions_idempotency_key_uniq` (мигр. 045) + парная `transaction` в одной БД-транзакции.
- `clients` `/bonus`: атомарный `UPDATE ... WHERE bonus_points >= abs(amount) RETURNING` — нет
  ухода в минус и гонки.
- `closeShift` (shifts.service.ts:93-126): `FOR UPDATE` + повторная проверка статуса + подсчёт
  остатка под блокировкой — двойное закрытие закрыто.
- Идемпотентность поставок (supplies): `onConflictDoNothing` на полном unique-индексе (мигр. 011/034),
  побочки в той же транзакции; двойное применение черновика поставки/ревизии → 409 под `FOR UPDATE`.
- WAC (ledger.ts:73-78): деление на ноль защищено (`qtyAfter > 0`), отрицательная себестоимость
  защищена (`effectiveBefore = max(0, before)`).
- `cashops` идемпотентность: полный unique-индекс `cash_operations_idem_key_uniq` (мигр. 006).
- `collections` баланс: списание и реверс под `FOR UPDATE`, парная `transactions`, проверка лимита
  долга `max_client_debt`; `requireAuth` стоит ПЕРЕД `requireRole` (стр.15) — 401 вместо 500 (исправлено).
- Скидки: процент ≤100% при create/PATCH; стаф-лимит в деньгах; тир-скидка — одна с макс. эффектом.

## Возможности апгрейда
1. **Единый слой денежных мутаций.** Вынести «изменить `profiles.balance` + записать `transactions`
   под `FOR UPDATE` в одной транзакции» в одну функцию (`applyBalanceDelta(tx, playerId, delta,
   {type, description, idempotencyKey})`), переиспользуемую POS/clients/collections/residentSettle.
   Сейчас паттерн скопирован в 4+ местах — расхождения (отсутствие границ суммы, разные знаки)
   возникают именно из-за дублирования.
2. **Серверная идемпотентность для всех мутаций денег/склада/ЗП.** Обязательный `idempotencyKey`
   (или серверный ключ из бизнес-полей) + полный unique-индекс — единым декоратором/middleware,
   а не точечно. Закрыло бы P0 по ЗП и потенциальные ретраи возвратов/взносов одним механизмом.
   Заодно ловить `23505` централизованно и возвращать 409 вместо 500.
3. **Сериализация конфликтных ресурсов через advisory-locks.** Для «один открытый объект на
   сущность» (аренда зоны, бронь события, возврат по чеку) ввести `pg_advisory_xact_lock(hashtext(key))`
   в начале транзакции вместо несуществующих/обещанных partial unique index. Закрывает класс гонок
   refunds / события / открытие чека с зоной без переписывания схемы.
4. **Жизненный цикл профиля с финансовым инвариантом.** Запрет архивации/удаления при `balance<>0`,
   а для удаления — архивная выгрузка `transactions`/`bonus_history` (не зануление FK на sentinel).
5. **Защита публичного виджета бронирования.** Капча/Turnstile + отдельный per-phone/per-IP лимит
   создания брони, не отдавать `claim_token` в `/lookup`, дедуп заказчика через `ON CONFLICT`.
