# Аудит: Склад, поставки, ревизии

## Summary

Складской модуль построен грамотно: введён единый immutable-журнал `stock_movements` (миграция 044), любое изменение остатка проходит через одну воронку `recordMovement()` с `FOR UPDATE`-локом строки товара и пересчётом WAC в той же транзакции. Идемпотентность приёмок, черновики поставок/ревизий, аудит-корректировки закупок и «дельта-правка последней ревизии» реализованы аккуратно и транзакционно. Однако **расчёт COGS/себестоимости проданного фундаментально некорректен** (период считает себестоимость *поставок* за окно, а маржа товара — по *текущему* WAC, при том что точная себестоимость на момент продажи уже фиксируется в `stock_movements.unit_cost`, но нигде не используется), **отсутствует учёт по рецептуре/BOM** (продажа коктейля/чашки чая не списывает ингредиенты), и **WAC ломается на отрицательном остатке** после оверселла. Для штучного бара/анти-кафе база рабочая; для продаж напитков и точного P&L — нет.

## Production-readiness score: 62/100

Обоснование: транзакционная целостность и журнал движений — на твёрдую «4». Но финансовое ядро склада (COGS → прибыль) считается двумя разными неверными способами; для коммерческого продукта, где владелец принимает решения по марже, это критично. Отсутствие рецептур делает учёт напитков фиктивным. Минус за оверселл-порчу WAC и отсутствие БД-инварианта неотрицательности. Код чистый, поэтому исправления локальны и недороги.

## Findings

### 1. [critical] COGS периода = себестоимость поставок за окно, а не себестоимость проданного
**Файл:** `apps/api/src/modules/analytics/analytics.router.ts:135-140, 170, 239-240, 460-461`
Период P&L (`net = gross − refunds − commission − cogs − opex − salary`, строка 174) берёт `cogs` как `SUM(supply_items.quantity * cost_per_unit)` по поставкам, *пришедшим в окно периода*. Это не себестоимость *проданного*: купили 100 ящиков в конце месяца — COGS месяца взлетит, хотя ничего не продано; продали со старых остатков — COGS = 0. Прибыль за период систематически искажается в обе стороны и не бьётся с реальной маржой.
**Почему важно:** владелец и будущие клиенты-подписчики принимают решения о ценах/закупках по этой прибыли. Это денежная ошибка в ключевой метрике продукта.
**Фикс:** считать COGS как `SUM(check_items.quantity * стоимость_единицы_на_момент_продажи)`. Точная стоимость уже есть — `stock_movements.unit_cost` для движений `type='sale'` (ledger.ts:80 пишет туда WAC на момент списания). Джойнить продажи с движениями склада (или денормализовать `cost_at_time` в `check_items` при продаже) и суммировать по периоду закрытия чека.

### 2. [critical] Маржа товара/смены считается по ТЕКУЩЕМУ WAC, а не по себестоимости на момент продажи
**Файл:** `apps/api/src/modules/analytics/analytics.router.ts:882, 890, 902` и `:1228, 1272-1273`
Отчёты «себестоимость по сотрудникам/comp-чекам/товарам» делают `SUM(check_items.quantity * inventory.cost_price)` — берут **актуальный** WAC из карточки. WAC дрейфует с каждой новой приёмкой, поэтому себестоимость *исторических* продаж пересчитывается задним числом при каждой закупке. Один и тот же закрытый чек вчера и сегодня даст разную маржу.
**Почему важно:** отчёты по марже невоспроизводимы; нельзя доверять историческим показателям, аудит невозможен.
**Фикс:** тот же, что и в #1 — использовать `stock_movements.unit_cost` (зафиксированную себестоимость на момент списания) или денормализованный `cost_at_time` в `check_items`. Поле уже заполняется, его просто никто не читает (grep по `unit_cost` в модулях даёт только запись в ledger и вывод в ленте движений `inventory.router.ts:366`).

### 3. [critical] Нет учёта по рецептуре/BOM — продажа напитка не списывает ингредиенты
**Файл:** схема `packages/database/src/schema/menu.ts:22-51` (нет таблицы рецептов), путь продажи `apps/api/src/modules/pos/pos.router.ts:164-176`
Списывается только сам проданный `itemId`, если у него `trackStock=true`. Для бара/анти-кафе типовой кейс: «Чай» в меню → расходует заварку/сахар/стакан; «Коктейль» → 50 мл сиропа + лёд. Сейчас либо у напитка нет учёта вовсе, либо учёт идёт «в стаканах напитка», что не отражает реальный расход сырья. Ревизия по сырью сойтись не может.
**Почему важно:** для анти-кафе с барной зоной (целевой сегмент) себестоимость и остатки напитков фиктивны. Это блокер для продажи продукта барам.
**Фикс:** добавить `recipe_items (menu_item_id, ingredient_item_id, qty_per_unit, unit)`. При продаже в `addCheckItemTx` после основного движения списывать ингредиенты через `recordMovement` (`type='write_off'`/новый `type='consume'`). Здесь же решается и проблема дробных списаний (см. #6).

### 4. [high] WAC портится при приходе на отрицательный остаток (после оверселла)
**Файл:** `apps/api/src/modules/inventory/ledger.ts:68-69`
WAC: `(before*oldCost + applied*unitCost) / qtyAfter`. Продажа идёт с `clamp:false` (pos.router.ts:167) — остаток уходит в минус. Если затем приходит поставка на товар с `before = −5`, числитель `−5*oldCost + applied*unitCost` занижен (или отрицателен), и новый WAC получается неверным — вплоть до отрицательного `cost_price`, который дальше отравляет всю маржу и стоимость склада.
**Почему важно:** один оверселл + приёмка → искажённая себестоимость товара навсегда (правки WAC задним числом запрещены в коде, см. supplies.router.ts:274).
**Фикс:** в WAC использовать `effectiveBefore = Math.max(0, before)` — приход на «дыру» считать как чистый приход по своей цене: `((effectiveBefore*oldCost) + applied*unitCost) / Math.max(applied, qtyAfter)`. И/или поднять оверселл наверх (см. #5).

### 5. [high] Нет БД-инварианта неотрицательного остатка; оверселл разрешён по умолчанию для продаж
**Файл:** `apps/api/src/migrations/sql/044_stock_ledger.sql` (нет `CHECK (qty_after >= 0)`), `apps/api/src/modules/pos/pos.router.ts:161-167`
Неотрицательность остатка держится только на флаге `clamp` в приложении. Путь продажи осознанно ставит `clamp:false` (оверселл «по продукту»), но это делает возможным уход остатка в минус для отслеживаемых товаров штучной розницы (не только напитков), что не имеет физического смысла для запечатанного товара (бутылка, снек) и ломает WAC (#4) и ревизию.
**Почему важно:** «честный минус» как фича уместен для сырья под рецептуру, но для штучного запечатанного товара это маскирует кражу/недоучёт и портит финансы.
**Фикс:** сделать поведение оверселла настройкой на карточке товара (`allow_oversell boolean`) либо глобальной настройкой; для запрещённых — блокировать продажу с понятной ошибкой `INSUFFICIENT_STOCK` (уже есть в коде POS). Рассмотреть `CHECK` на инвариант для не-рецептурных товаров.

### 6. [high] Дробные количества для карточных товаров запрещены — нельзя продавать «на разлив»/вес
**Файл:** `apps/api/src/modules/supplies/supplies.router.ts:28-32, 201-202, 287-288`; `packages/database/src/schema/menu.ts:28` (`stock_quantity integer`)
Остаток в `inventory` — `integer`; приёмка карточного товара принудительно требует целое количество (refine «Для товара с карточкой количество должно быть целым»). Поле `unit` в `supply_items` есть, но для карточных позиций фронт жёстко шлёт `'шт'` (SuppliesTab.tsx:173, ItemsTab.tsx) и `step={1}`. Невозможен учёт сиропа/молока/табака по граммам/мл/кг, закупка «коробкой» с продажей «штукой».
**Почему важно:** весовой/объёмный учёт обязателен для бара и кальянной (табак в граммах). Сейчас такой товар учитывать нельзя.
**Фикс:** перевести `inventory.stock_quantity`, `stock_movements.delta/qty_after` на `numeric(12,3)`; ввести `base_unit` + опционально `purchase_unit`/`pack_size` (купил ящик 24 → принять 24 шт). Это связано с #3 (рецептура считает дроби сырья).

### 7. [medium] Риск дедлоков при конкурентных операциях со складом (нет упорядоченной блокировки)
**Файл:** `apps/api/src/modules/supplies/supplies.router.ts:331-339` (итерация по `Set`), `:382` (по строкам), `applyRevisionItems` в `inventory.router.ts:132-148`, POS `addCheckItemTx`
Несколько товаров локаются `FOR UPDATE` в порядке появления в массиве/`Set`, без сортировки по `item_id`. Две транзакции, трогающие пересекающийся набор товаров в разном порядке (например, продажа vs. приёмка, или две ревизии), могут зайти в дедлок Postgres. На одном клубе с малым параллелизмом редко, но проявится; в SaaS-нагрузке — регулярно.
**Почему важно:** ошибки 500 на кассе/приёмке под нагрузкой, проваленные транзакции.
**Фикс:** перед циклом сортировать `itemId` (`[...allIds].sort()`, `items.sort by itemId`) — единый глобальный порядок блокировок устраняет цикл ожидания. Дёшево.

### 8. [medium] Ревизия — частичный счёт без явной семантики «непосчитанное»; нет блокировки склада на время счёта
**Файл:** `apps/api/src/modules/inventory/inventory.router.ts:126-148`, RevisionTab.tsx (счёт только добавленных позиций)
Ревизия применяет `count` только к позициям, которые оператор вручную добавил (`order`), а `expected` снимается в момент *применения* (а не начала счёта). Если между началом физического пересчёта и нажатием «Провести» прошла продажа/приёмка, `expected` уже сместился → расхождение «съест» движение, случившееся во время счёта, и оператор не узнает. Полная инвентаризация «всё, что не посчитано → 0» не поддержана.
**Почему важно:** ревизия — инструмент поимки недостач; «плавающий expected» и отсутствие заморозки занижают/завышают расхождения, подрывая доверие к инструменту.
**Фикс:** фиксировать `expected` на момент *начала* ревизии (снапшот в `draft_data`) и показывать в дельте «движения во время счёта» отдельной строкой; либо предупреждать, если по позиции были движения после старта черновика. Добавить режим «полная инвентаризация».

### 9. [medium] Откат приёмки и правка закупки не разворачивают WAC — себестоимость «залипает»
**Файл:** `apps/api/src/modules/supplies/supplies.router.ts:274 (комментарий), 359-363, 386-390`
И DELETE, и PATCH проведённой закупки честно правят *остаток* (компенсирующее `adjustment`-движение), но **сознательно не трогают `cost_price`** (WAC). После ошибочной приёмки по неверной цене и её отката средневзвешенная остаётся искажённой навсегда.
**Почему важно:** ошибка в цене закупки → перманентно неверная себестоимость → неверная маржа (усугубляет #2).
**Фикс:** это снимется, если COGS перейдёт на зафиксированный `unit_cost` движений (#1/#2) — тогда «залипшая» карточная WAC перестаёт влиять на исторические отчёты. Для текущего остатка можно при откате пересчитывать WAC из журнала движений (`SUM(receipt.delta*unit_cost)/SUM(receipt.delta)` по непогашенным приходам).

### 10. [low] `recordMovement` не пишет строку журнала при `applied == 0`, но изменивший WAC приход теряет след
**Файл:** `apps/api/src/modules/inventory/ledger.ts:72-93`
Если `applied == 0` (например, clamp прижал к нулю или приход с нулевой эффективной дельтой), но `avgCost` изменился, карточка обновится (строка 72-76), а строки в журнале не будет (строка 79). Инвариант «`stockQuantity == SUM(delta)`» сохраняется, но изменение себестоимости без движения становится неаудируемым. Краевой случай.
**Почему важно:** мелкая дыра в аудит-следе себестоимости.
**Фикс:** при `applied == 0 && avgCost !== oldCost` всё же писать движение (`delta=0`, `type='adjustment'`, причина «Пересчёт себестоимости») — либо документировать как принятое поведение.

### 11. [low] `overview` использует `min_threshold`/`reorder_point` напрямую в SQL без COALESCE-нуля корректно, но `out_count` считает `<= 0` для всех учётных
**Файл:** `apps/api/src/modules/inventory/inventory.router.ts:254-267`
`out_count` = `stock_quantity <= 0` — при разрешённом оверселле (#5) сюда попадут товары с отрицательным остатком, что корректно как «нет в наличии», но KPI «нет в наличии» смешивает «ровно 0» и «минус N» (дефицит). Для владельца полезно различать. Незначительно.
**Фикс:** добавить отдельный счётчик `negative_count` (oversold), показывать в дашборде как сигнал к срочной ревизии/приёмке.

## Что сделано хорошо (не findings)

- Единый журнал `stock_movements` + `recordMovement` с `FOR UPDATE` и пересчётом WAC в одной транзакции — правильная архитектура (ledger.ts, миграция 044).
- Идемпотентность приёмки через полный уникальный индекс + `onConflictDoNothing` + возврат существующей записи (supplies.router.ts:81-117) — двойной клик не задвоит COGS.
- Корректировки закупки требуют причину и пишут аудит `supply_corrections` с суммами до/после (миграция 035, supplies.router.ts:344-350).
- Правка ревизии — только последней, дельтой к текущему остатку, с гардом внутри транзакции (inventory.router.ts:218-243) — движения после ревизии не теряются.
- Возвраты не восстанавливают сток сверх проданного (`restored_items` cap, finance.ts:228-231).
- Бэкфилл-миграция 044 неразрушающая, досевает `opening`-движение для схождения `SUM(delta)` с остатком.

## New feature ideas (мафия-клубы / анти-кафе)

- **Рецептуры/техкарты (BOM)** — продажа «Чай/Коктейль/Кальян» списывает заварку/сироп/табак. Прямо закрывает #3 и даёт реальную себестоимость напитков.
- **Учёт по весу/объёму** — табак в граммах, сиропы в мл (см. #6); критично для кальянной/бара.
- **Заявка на закупку из дефицита** — кнопка «дозаказать до par_level» по товарам ≤ `reorder_point` (поля `reorder_point`/`par_level` уже есть в схеме, но не используются для генерации заказа).
- **Себестоимость порчи/угощений по сотрудникам** — отчёт «кто сколько списал» (тип `write_off` уже разделён); полезно против злоупотреблений «угощениями» в клубе.
- **«Расход на мероприятие»** — привязать списания склада к `event_id` (как у расходов), чтобы видеть себестоимость закуски/напитков на конкретный миникап.
- **Алерты низкого остатка в смену** — push «осталось 3 колы» прямо бариста (low-stock уже вычисляется в POS на продаже, pos.router.ts:172-175, но только возвращается в ответе, не пушится).

## SaaS / multi-club implications

- **Полное отсутствие изоляции по клубу.** В `inventory`, `supplies`, `supply_items`, `stock_movements`, `revisions`, `revision_items` нет колонки `club_id`/`tenant_id`. Журнал, остатки, WAC, ревизии — все глобальные. При мультиклубе остатки и себестоимость одного клуба смешаются с другим — это утечка данных и неверный учёт. Для SaaS обязательна сквозная tenant-колонка + RLS/фильтр в каждом запросе склада. Это самый дорогой архитектурный пункт.
- **Идемпотентность ключей глобальна** (`idempotency_key` уникален по всей таблице `supplies`) — при мультиклубе ключ одного клуба может «съесть» приёмку другого. Уникальность должна стать `(club_id, idempotency_key)`.
- **WAC и `cost_price` на карточке `inventory`** при мультиклубе должны быть per-club: один и тот же SKU стоит по-разному в разных городах. Сейчас карточка одна.
- **Ревизия «только последняя»** (gt по `created_at` глобально, inventory.router.ts:114, 223) сломается между клубами: ревизия клуба Б заблокирует правку ревизии клуба А. Гард должен учитывать `club_id`.
- **Единицы/рецептуры** при тиражировании на разные форматы (анти-кафе vs кальянная vs бар) делают #3/#6 обязательными — продукт без весового учёта и техкарт не продать барам.
