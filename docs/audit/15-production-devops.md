# Аудит: Продакшн-готовность и DevOps

## Summary

Инфраструктура Titan HUB на удивление зрелая для соло-проекта: healthcheck-цепочка `depends_on: service_healthy` закрывает окно 502 при холодном старте, миграции идут в транзакции до начала обслуживания, бэкап снимается перед каждым деплоем, rate-limit двухуровневый (nginx + Redis), а secrets не утекают в логи (есть редактор query-токенов и обобщённый `onError`). Однако для **коммерческого SaaS** не хватает целого слоя production-практик: нет error-tracking (Sentry), нет ротации Docker-логов (диск на 4-ГБ VPS забьётся), нет CI/CD, `.env.example` рассинхронизирован с реальными переменными, валидация env на старте проверяет только 2 секрета из ~15, восстановление БД не транзакционно, а API-контейнер ходит под root с примонтированным rclone и правом DROP базы. Самый крупный коммерческий блокер — **отсутствие фискализации (54-ФЗ/ОФД)** и **однотенантность**, что делает легальную продажу подписки другим клубам невозможной без доработки.

## Production-readiness score: 58/100

**Обоснование.** Базовый деплой работает и переживёт типовые сбои (это +). Но «production для одного владельца» ≠ «production для платящих чужих клубов». Минусы, тянущие оценку вниз: нет наблюдаемости (error-tracking/метрики/алертинг) — инциденты у клиента вы узнаете постфактум; нет ротации логов — предсказуемый отказ по диску; нет CI (любой `git reset --hard` тащит непротестированный код прямо в прод); рассинхрон env и неполная boot-валидация — тихие отказы passkey/push/оплат; нет фискализации и мультитенантности — юридический и архитектурный блокер для SaaS. Для одного клуба сегодня — ~75/100; как платформа для продажи — 58/100.

## Findings

### CRITICAL

#### C1. Нет фискализации (54-ФЗ / ОФД / онлайн-касса) — юридический блокер коммерции
- **Где:** весь платёжный/POS-слой; `apps/api/src/modules/platega/platega.router.ts`, `apps/api/src/modules/pos/pos.router.ts`. Греп по `фискал|ОФД|54-ФЗ|atol|kkt` — совпадений с фискальным смыслом **ноль** (только «касса» в значении cash-drawer).
- **Что не так:** приём денег от физлиц (наличные, СБП через Platega) в РФ требует пробития кассового чека через онлайн-ККТ и передачи в ОФД (54-ФЗ). Сейчас система формирует внутренние «чеки» (`checks`), но это не фискальные документы.
- **Почему важно:** продавать подписку клубам, которые принимают деньги без фискального чека, — значит продавать инструмент нарушения закона; штрафы по ст. 14.5 КоАП. Это блокирует легальный выход на рынок.
- **Fix:** интеграция с фискальным оператором (АТОЛ Онлайн / Бизнес.Ру / ЛайфПей / Модулькасса API) — после успешной оплаты пробивать чек и сохранять `fiscal_receipt_url`/`fn_number`/`fd_number`. Минимум — флаг «фискализация включена» на клуб и абстракция-провайдер, чтобы клуб мог подключить свою ККТ. До реализации — явно зафиксировать в договоре, что фискализация на стороне клиента.

#### C2. Однотенантность — на одной БД нельзя обслуживать несколько клубов
- **Где:** `packages/database/src/schema/*` — греп по `tenant|club|venue|organization` дал ноль колонок-изоляторов; `packages/database/src/client.ts` — один `DATABASE_URL`, один пул.
- **Что не так:** все данные в одной плоской схеме без `tenant_id`. Бэкап/restore (`apps/api/src/lib/backup.ts`) — это дамп **всей** БД целиком, владелец одного клуба может восстановить базу поверх данных всех клубов.
- **Почему важно:** SaaS на этой архитектуре = «один VPS на клуб» (дорого, не масштабируется) либо риск утечки данных между клубами. Кнопка «Восстановить» в текущем виде в мультитенанте = катастрофа.
- **Fix:** стратегическое решение — (а) schema-per-tenant / database-per-tenant (проще изоляция, дороже эксплуатация), либо (б) shared schema + `tenant_id` во всех таблицах + RLS в Postgres. Для старта продаж быстрее (а) с автоматизацией провижининга. Backup/restore переписать на per-tenant (`pg_dump --schema=...`).

#### C3. Восстановление БД не транзакционно и не блокирует приём денег
- **Где:** `apps/api/src/lib/backup.ts:112-117` (`restoreFromPath`) — `psql -v ON_ERROR_STOP=0`, и `:115` гасит чужие подключения, но API продолжает обслуживать запросы.
- **Что не так:** `ON_ERROR_STOP=0` означает, что при ошибке посреди дампа psql **продолжит** — база остаётся в частично восстановленном (битом) состоянии без падения. Параллельно с restore POS может пробивать оплаты в полу-восстановленную базу.
- **Почему важно:** «Восстановить» вызывается owner'ом из UI в проде. Частичный restore = потеря/порча финансовых данных без явной ошибки. Это деньги.
- **Fix:** `ON_ERROR_STOP=1` + `--single-transaction` у psql (весь restore атомарно, либо целиком, либо откат). На время restore — переводить API в read-only/maintenance (флаг в Redis, middleware возвращает 503 на мутации). Логировать результат, а не глотать.

### HIGH

#### H1. Нет ротации Docker-логов → переполнение диска → отказ всего сайта
- **Где:** `docker-compose.yml` — ни у одного сервиса нет `logging:`/`max-size`. API на каждый запрос пишет 2 строки в stdout (`apps/api/src/app.ts:77,80`), драйвер по умолчанию `json-file` без лимита.
- **Что не так:** на VPS с 4 ГБ RAM и небольшим диском логи Docker растут безгранично. При забитом диске Postgres перестаёт писать, nginx-cache ломается → 502/полный отказ.
- **Почему важно:** предсказуемый отказ в течение недель-месяцев непрерывной работы; у платящего клиента это «сайт лёг сам по себе».
- **Fix:** в `docker-compose.yml` добавить глобально (через `x-logging` anchor) `logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }` на все сервисы. Или системный `/etc/docker/daemon.json` с default-лимитами.

#### H2. Нет error-tracking / алертинга (Sentry и т.п.)
- **Где:** греп `sentry|rollbar|bugsnag|opentelemetry|prometheus` — ноль. Ошибки только в `console.error` (`apps/api/src/app.ts:127`).
- **Что не так:** упавший платёж, исключение в webhook Platega, провал миграции у клиента — всё уходит в stdout, который никто не читает в реальном времени.
- **Почему важно:** в SaaS вы обязаны узнавать об инциденте раньше клиента. Сейчас обратная связь — звонок разозлённого владельца.
- **Fix:** подключить Sentry (`@sentry/node` в API, `@sentry/nextjs` в web) с DSN из env. Алерты в Telegram-бот (он уже есть — `apps/bot-admin`) на: провал миграции, 5xx-всплеск, `AMOUNT_MISMATCH` в Platega, неудачу бэкапа.

#### H3. Boot-валидация проверяет 2 секрета из ~15 → тихие отказы в проде
- **Где:** `apps/api/src/index.ts:9-22` (`assertEnv`) проверяет только `JWT_SECRET` и `DATABASE_URL`.
- **Что не так:** не валидируются `PLATEGA_SECRET`/`PLATEGA_MERCHANT_ID` (без них webhook оплат молча отклоняет всё — `platega.router.ts:35-37`), `VAPID_*` (push молча не работает), `WEBAUTHN_RP_ID`/`ORIGIN` (фолбэк `localhost` → passkey в проде ломается — `auth.router.ts:25-26`), `MINIO_*`, `REDIS_URL`. Сервис стартует «здоровым», а фичи отказывают.
- **Почему важно:** healthcheck зелёный, nginx пускает трафик, но оплаты/push/passkey не работают — диагностируется только по жалобам.
- **Fix:** расширить `assertEnv` (или zod-схема env) — для прод-режима требовать все секреты, которые реально используются. Минимум: Platega-пара, VAPID-тройка, WEBAUTHN_RP_ID≠localhost при `NODE_ENV=production`.

#### H4. API-контейнер работает под root и имеет право снести БД + доступ к rclone-кредам
- **Где:** `apps/api/Dockerfile` — нет `USER`, рантайм под root; `docker-compose.yml:74-77` монтирует `/opt/backups` (rw) и `/root/.config/rclone` с Google-токенами; `backup.ts` шеллит `pg_dump/psql/rclone` с `--clean` (DROP+CREATE).
- **Что не так:** компрометация API-процесса (RCE через зависимость или AI-модуль) даёт root в контейнере, токены Google Drive, и возможность дропнуть/перезаписать всю БД и все бэкапы.
- **Почему важно:** максимальный blast radius. В мультитенанте — доступ ко всем клубам сразу.
- **Fix:** добавить непривилегированного `USER node` в API Dockerfile (как уже сделано в web Dockerfile:33,39). rclone-конфиг монтировать `:ro` (уже так), но лучше вынести бэкап в отдельный sidecar/cron-контейнер, а не давать API право DROP. Минимум — отдельная БД-роль для restore.

#### H5. Нет CI/CD — непротестированный код едет в прод `git reset --hard`
- **Где:** нет `.github/workflows/`; `scripts/deploy.sh:12-13` делает `git fetch && git reset --hard origin/main` прямо на проде.
- **Что не так:** нет автоматического `lint`/`type-check`/`build`/тестов перед деплоем. Любой пуш в main, который компилируется локально, но падает в проде, доедет до клиентов. Деплой собирает образы **на самом проде** (CPU/RAM-пик → известный разрыв SSH).
- **Почему важно:** в SaaS падение сборки = простой всех клубов. Сборка на проде — корень проблемы «SSH рвётся под нагрузкой».
- **Fix:** GitHub Actions: на PR — `pnpm lint && type-check && build`; на merge в main — собрать образы в CI/registry (GHCR), на VPS только `docker compose pull && up -d` (без локальной сборки). Это убирает CPU-пик на проде и SSH-разрывы разом.

### MEDIUM

#### M1. `.env.example` рассинхронизирован с кодом
- **Где:** `.env.example` vs реальные `process.env`. Отсутствуют в примере: `VAPID_PUBLIC_KEY/PRIVATE_KEY/SUBJECT`, `POLZA_API_KEY/BASE_URL/MODEL`, `WEBAUTHN_RP_ID/RP_NAME/ORIGIN`, `RATELIMIT_ANON/AUTH`, `WALLET_BOT_USERNAME`, `ADMIN_BOT_USERNAME`, `BACKUP_*`. При этом пример документирует `ANTHROPIC_API_KEY`/`AI_MODEL`, а код AI читает `POLZA_*` (`ai.router.ts:39-42`) — документация вводит в заблуждение.
- **Почему важно:** новый деплой (в т.ч. провижининг клуба) по `.env.example` поднимется с нерабочими push/passkey/AI; диагностика — часы.
- **Fix:** синхронизировать `.env.example` с фактическими ключами, убрать неиспользуемый `ANTHROPIC_API_KEY` или пометить legacy, добавить комментарий «обязательно/опционально».

#### M2. nginx: нет `server_tokens off`, CSP, Referrer-Policy, Permissions-Policy, OCSP stapling
- **Где:** `nginx/nginx.conf` — есть HSTS/X-Frame-Options/X-Content-Type-Options (стр. 56-58), но нет `server_tokens off` (утечка версии nginx), Content-Security-Policy, Referrer-Policy, Permissions-Policy, `ssl_stapling`.
- **Почему важно:** для коммерческого продукта (особенно с PII клиентов по 152-ФЗ) это базовый security-минимум; отсутствие CSP — XSS-поверхность для PWA с пользовательским вводом.
- **Fix:** `server_tokens off;` в `http{}`. Добавить `add_header Referrer-Policy "strict-origin-when-cross-origin" always;`, `Permissions-Policy`, аккуратную CSP (с учётом inline-стилей Next). Включить `ssl_stapling on; ssl_stapling_verify on;`.

#### M3. Деплой ставит pnpm и зависимости на хост при каждом запуске
- **Где:** `scripts/deploy.sh:16-17` — `npm install -g pnpm@11` + `CI=true pnpm install --frozen-lockfile` на хосте каждый деплой.
- **Что не так:** хост-нода/pnpm вообще не нужны для рантайма (всё в Docker). Это лишний сетевой/CPU-шаг, ещё одна причина деградации под нагрузкой и связывание прода с host-toolchain.
- **Почему важно:** хрупкость деплоя, лишние ~минуты простоя, точка отказа при флакающей сети npm.
- **Fix:** убрать host-`pnpm install` из deploy.sh (зависимости ставятся внутри Dockerfile). Это шаг к схеме «собираем в CI, на проде только pull».

#### M4. Бэкап-стратегия: только pg_dump, нет PITR, RPO до 24ч, restore не тестируется
- **Где:** `scripts/backup-db.sh` (cron-ежедневно) + бэкап перед деплоем; ротация 14 дней; offsite в Google Drive опционально.
- **Что не так:** между суточными бэкапами теряется до 24ч транзакций (нет WAL-archiving/PITR). Нет автоматической проверки, что дамп **восстанавливается** (валидируется только размер >1КБ). MinIO (файлы, медиа) и Redis в бэкап **не входят**.
- **Почему важно:** для финансовой системы RPO 24ч высок; «бэкап, который не восстановили» = бэкапа нет. Медиа (чеки/фото) теряются безвозвратно.
- **Fix:** включить `pgBackRest`/WAL-G с PITR (RPO минуты). Раз в неделю автоматически восстанавливать последний дамп в одноразовый контейнер и гонять smoke-проверку. Добавить бэкап `minio-data` (rclone sync бакета).

#### M5. Single-instance, нет горизонтального масштабирования и фоновых воркеров отдельно
- **Где:** `docker-compose.yml` — по одному контейнеру каждого; cron «дни рождения» живёт в `setInterval` внутри API-процесса (`index.ts:40-55`).
- **Что не так:** API одновременно обслуживает запросы и крутит cron; при `replicas > 1` дни рождения разошлются N раз, а миграции попытаются запуститься параллельно (гонка на `_migrations`). Масштабироваться нельзя без рефакторинга.
- **Почему важно:** упёрлись в один процесс — рост числа клубов потребует вертикального масштабирования (дорого) либо переписывания.
- **Fix:** вынести cron/воркеры в отдельный сервис (BullMQ уже в стеке). Миграции — отдельный one-shot job (а не на каждом старте API), чтобы реплики не гонялись. Тогда API можно реплицировать за nginx.

#### M6. 152-ФЗ (ПДн): нет политики хранения, шифрования PII, журнала доступа, локализации
- **Где:** PII клиентов (`profiles`, `customers` — телефоны, дни рождения, Telegram id) хранится в открытом виде; бэкапы (включая Drive) не шифруются.
- **Что не так:** 152-ФЗ требует от оператора ПДн: уведомление РКН, политику обработки, меры защиты, хранение ПДн граждан РФ на серверах в РФ (локализация). Бэкап с ПДн уезжает в Google Drive (зарубежный сервис) — прямое нарушение локализации.
- **Почему важно:** при продаже SaaS оператором ПДн становитесь вы (или клуб); РКН-проверки и штрафы реальны, особенно для растущего сервиса.
- **Fix:** offsite-бэкап только в РФ-облако (Yandex Object Storage / VK Cloud / Selectel), шифровать дампы (`gpg`/`rclone crypt`). Подготовить политику обработки ПДн, страницу согласия. Юрчасть — отдельно, но архитектурно убрать вывоз ПДн за рубеж.

### LOW

#### L1. Bot-контейнеры без healthcheck
- **Где:** `docker-compose.yml:130-160` — `bot-admin`/`bot-wallet` без `healthcheck`. Упавший long-poll бот считается «running», но не работает.
- **Fix:** добавить лёгкий healthcheck (проверка процесса/heartbeat в Redis) или хотя бы алерт при рестарт-петле.

#### L2. `git reset --hard origin/main` затрёт локальные правки и nginx/ssl при ручном вмешательстве
- **Где:** `deploy.sh:13`. SSL-сертификаты лежат в `nginx/ssl/` под git-деревом (`renew-ssl.sh:5-6` копирует их туда) — если они не в `.gitignore`, reset может их затереть/закоммитить.
- **Fix:** проверить, что `nginx/ssl/` в `.gitignore`; вынести изменяемые на проде артефакты из git-дерева.

#### L3. Логи приложения неструктурированы (plain text), сложно агрегировать
- **Где:** `apps/api/src/app.ts:77,80` — `console.log` строками.
- **Почему важно:** при росте клубов нужен поиск по логам (по клубу, по чеку); plain-text не парсится агрегатором.
- **Fix:** структурный логгер (pino) с JSON-выводом, `requestId`, (в будущем) `tenantId`. Совместимо с Loki/Sentry.

#### L4. CORS: единственный `FRONTEND_URL`, в мультитенанте каждый клуб = свой домен
- **Где:** `apps/api/src/app.ts:86-91` — `origin: process.env['FRONTEND_URL'] ?? 'http://localhost:3000'`.
- **Fix:** при мультитенанте — функция-валидатор origin по списку доменов клубов.

## New feature ideas (мафия-клубы / антикафе)

1. **Фискализация «из коробки» как часть подписки** — интеграция с АТОЛ Онлайн/Модулькасса: клуб вводит токен своей ККТ, чеки пробиваются автоматически. Это одновременно закрывает C1 и становится продающей фичей («подключи кассу за 5 минут»).
2. **Status-страница для клубов** (`status.titanpos.ru`) — аптайм, инциденты, плановые работы. Доверие платящих клиентов + снижает поток «у вас лежит?».
3. **Self-service провижининг клуба** — мастер «Создать клуб»: поддомен, изолированная схема, сид-данные, приглашение владельца. Превращает ручной деплой в продукт.
4. **Алерты владельцу в Telegram через bot-admin** — «бэкап не сделан 2 дня», «диск 85%», «всплеск 5xx», «оплата зависла». Бот уже есть — переиспользовать как канал ops-алертов.
5. **Тарифные планы и биллинг подписки** — Free/Pro/Network, лимиты (число столов/смен/AI-запросов), автосписание через ту же Platega. Без этого нет монетизации.
6. **Экспорт данных клуба (data portability)** — кнопка «Выгрузить все мои данные» (152-ФЗ/доверие): per-tenant дамп + медиа в zip.

4. **Синхронизировать `.env.example`** с реальными ключами (M1) и убрать вводящий в заблуждение `ANTHROPIC_API_KEY`. ~20 мин.
5. **Расширить `assertEnv`** проверкой `PLATEGA_SECRET`/`VAPID_PUBLIC_KEY`/`WEBAUTHN_RP_ID≠localhost` при `NODE_ENV=production` (H3). ~20 мин.
6. **`USER node`** в `apps/api/Dockerfile` (часть H4) — снять root с API-рантайма. ~10 мин (проверить права на `/backups`).
7. **Healthcheck для bot-контейнеров** (L1). ~15 мин.

## SaaS / multi-club implications (для этой зоны)

- **Деплой → провижининг.** Текущий `deploy.sh` обновляет один инстанс. SaaS требует автоматического создания клуба (схема/БД, поддомен, сертификат, сид). Без CI-сборки образов (H5) каждый новый клуб усиливает CPU-пик на общем VPS.
- **Бэкап/restore становятся опасными.** C2+C3: full-dump restore поверх общей БД сотрёт всех. Нужен per-tenant бэкап и изоляция кнопки «Восстановить».
- **Наблюдаемость обязательна.** С одним клубом владелец = сам себе мониторинг. С десятками — без Sentry/метрик/алертов (H2) вы слепы; SLA продать нельзя.
- **Стоимость.** Сейчас всё на одном 4-ГБ VPS с жёсткими `mem_limit`. Каждый клуб добавляет нагрузку; модель «БД-на-клуб» множит инфраструктуру линейно. Нужен план масштабирования (M5) до начала продаж, иначе 5-10 клубов положат VPS.
- **Юридический периметр.** 54-ФЗ (C1) и 152-ФЗ (M6) — не «техдолг», а условие легальности. Вывоз ПДн в Google Drive нужно убрать до первой продажи; фискализацию — заложить в продукт или явно делегировать клиенту договором.
