# Аудит: Доступность и производительность фронтенда

## Summary

Фронтенд Titan HUB (Next.js 15 App Router PWA, React 19, ~24k LOC) написан аккуратнее, чем ожидалось от продукта на инлайновых стилях: есть глобальный `:focus-visible`, `prefers-reduced-motion`, осмысленная семантика навигации (`<nav>`, `aria-current`), все иконки — инлайновые SVG (нет иконочного шрифта). Однако есть несколько системных проблем, бьющих по Core Web Vitals и доступности: шрифты грузятся через render-blocking `@import` в CSS и тянут **полный вариативный шрифт Material Symbols, который нигде не используется** (десятки-сотни КБ впустую); модальное окно `Sheet` (основной паттерн всех форм) не имеет `role="dialog"`, фокус-ловушки, обработки `Escape` и возврата фокуса; нет ни одного `React.memo`, ни виртуализации длинных списков, ни code-splitting тяжёлых клиентских экранов (`CheckDetailView` ~2400 строк, `dashboard` ~1800 строк целиком в бандле). Производительность приемлема на каталоге одного клуба, но архитектурно не готова к крупным меню/историям при SaaS-масштабировании.

## Production-readiness score: 68/100

Обоснование: базовая клавиатурная доступность и снижение анимаций реализованы (редкость для таких проектов), навигация семантична, запросы данных грамотно гейтятся через `enabled` по вкладкам (нет waterfall). Минус баллы за: (1) гарантированную трату трафика на неиспользуемый шрифт + render-blocking загрузку шрифтов (прямой удар по LCP/FCP на iPhone по мобильной сети), (2) модалки без WAI-ARIA dialog-семантики и фокус-менеджмента (нарушение WCAG 2.1, проблема для скринридеров и аппаратной клавиатуры на iPad), (3) отсутствие виртуализации и мемоизации — деградация при росте данных в SaaS. Ничего из этого не теряет деньги и не блокирует запуск для одного клуба, поэтому не «critical», но для коммерческой подписки это потолок.

## Findings

### 1. [HIGH] Полный шрифт Material Symbols грузится, но не используется
**Файл:** `apps/web/src/app/globals.css:2`
`@import url('...Material+Symbols+Outlined:opsz,wght,FILL,GRAD@20..48,100..700,0..1,-50..200&display=swap')` подключает вариативный иконочный шрифт со всеми осями. Grep по всему `apps/web/src` показывает, что класс `material-symbols`/`font-family: Material Symbols` **не встречается нигде** — иконки рисуются инлайновым SVG (`src/components/Icon.tsx`). Это чистая трата: вариативный Material Symbols — сотни КБ, грузится на каждом холодном старте PWA.
**Почему важно:** прямой удар по LCP/FCP и расходу трафика на мобильном (целевое устройство — iPhone-PWA). Бесплатный выигрыш.
**Фикс:** удалить `Material+Symbols+Outlined` из `@import` (оставить только `Inter` и `JetBrains+Mono`).

### 2. [HIGH] Шрифты грузятся через render-blocking `@import`, без `next/font`
**Файл:** `apps/web/src/app/globals.css:2`
Шрифты подключены `@import url(...)` внутри CSS. Браузер обязан сначала скачать и распарсить CSS, и только потом обнаружит и начнёт грузить шрифты — это сериализованная цепочка (request waterfall), блокирующая рендер. `grep next/font` — пусто, то есть оптимизация Next.js (self-hosting, `font-display`, preload, удаление layout-shift) не задействована.
**Почему важно:** деградация FCP/LCP и риск FOIT/CLS на медленной мобильной сети.
**Фикс:** перейти на `next/font/google` (`Inter`, `JetBrains_Mono`) с `display: 'swap'` и `subsets: ['cyrillic','latin']` — Next захостит шрифты локально, добавит preload и зарежет нужные веса. Минимум — заменить `@import` на `<link rel="preconnect">` + `<link rel="stylesheet">` в `<head>`.

### 3. [HIGH] Модалка `Sheet` без dialog-семантики, фокус-ловушки, Escape и возврата фокуса
**Файл:** `apps/web/src/components/manage/DesignSystem.tsx:118-446`
`Sheet` — базовый компонент всех форм/деталей (клиенты, меню, склад, смены и т.д.). При открытии: нет `role="dialog"` + `aria-modal="true"`, нет `aria-labelledby` на заголовок, нет фокус-ловушки (Tab уводит фокус под оверлей в фоновый контент), нет обработчика `Escape` (grep по файлу — `NO Escape handler`), нет возврата фокуса на триггер при закрытии, нет автофокуса на первый элемент. Закрытие возможно только кликом по оверлею/крестику/свайпом.
**Почему важно:** нарушение WCAG 2.1 (2.1.2 No Keyboard Trap наоборот — фокус «протекает»; 4.1.2 Name/Role/Value). Скринридер не объявляет открытие диалога; пользователь аппаратной клавиатуры (iPad с клавиатурой, десктоп-касса) не может закрыть по Escape и проваливается в фон.
**Фикс:** на панель добавить `role="dialog" aria-modal="true" aria-labelledby={titleId}`; повесить `keydown`-листенер на `Escape → onClose`; реализовать focus trap (например, через `inert` на фоне или цикл Tab внутри панели); сохранять `document.activeElement` при открытии и возвращать фокус при закрытии; автофокус на первый интерактивный элемент/крестик.

### 4. [MEDIUM] Toast без `aria-live` — уведомления не объявляются скринридером
**Файл:** `apps/web/src/components/Toast.tsx`
В контейнере тостов нет `role="status"`/`role="alert"` и `aria-live` (grep — `NO aria-live in Toast`). Toast используется для подтверждений сохранения, ошибок оплаты и т.п.
**Почему важно:** незрячий/слабовидящий кассир не получает обратную связь об успехе/ошибке критичных операций (оплата, возврат). WCAG 4.1.3 Status Messages.
**Фикс:** обернуть контейнер тостов в `<div aria-live="polite" role="status">` (для ошибок — `assertive`/`alert`).

### 5. [MEDIUM] `SwipeableRow` (удаление свайпом) недоступен с клавиатуры
**Файл:** `apps/web/src/components/SwipeableRow.tsx:10-77`
Удаление реализовано только через `onTouchStart/Move/End`. Нет `<button>`, `onKeyDown`, `role` или видимой кнопки удаления — действие физически недостижимо с клавиатуры/мыши и для скринридера.
**Почему важно:** деструктивное действие (удаление) доступно только тач-жестом. На десктоп-кассе/iPad с клавиатурой пользователь не может удалить элемент; скринридер не знает о действии. WCAG 2.1.1 Keyboard.
**Фикс:** добавить фоновую кнопку удаления как настоящий `<button aria-label="Удалить">`, видимую/фокусируемую как fallback, либо контекстное действие в строке; жест оставить как прогрессивное улучшение.

### 6. [MEDIUM] Нет виртуализации длинных списков (меню, реестр движений склада)
**Файлы:** `apps/web/src/app/manage/menu/page.tsx:399-505`; `apps/web/src/app/manage/inventory/tabs/ItemsTab.tsx:5-20` (реестр движений `moves.map`)
Grep по `react-window|react-virtual|virtuoso` — `NONE FOUND`. Меню рендерит все позиции выбранной папки разом; история движений товара (`/inventory/:id/movements`) рендерит весь массив без лимита/пагинации. Список клиентов, к чести разработчика, **пагинирован** (`apps/web/src/app/manage/clients/page.tsx:302-315`, «Показать ещё») — это правильный паттерн, который стоит распространить.
**Почему важно:** на каталоге одного клуба (десятки позиций) проблемы нет, но крупное меню/длинная история движений дадут просадку рендера и скролла на iPhone. Для SaaS с разными клубами размер данных непредсказуем.
**Фикс:** добавить виртуализацию (`@tanstack/react-virtual`) для плоских списков длиннее ~50 строк (история движений, плоский поиск по меню) либо пагинацию/`limit` на стороне API для движений, как уже сделано для клиентов.

### 7. [MEDIUM] Тяжёлые клиентские экраны не код-сплитятся (`next/dynamic`/`lazy` не используются)
**Файлы:** `apps/web/src/components/CheckDetailView.tsx` (2406 строк), `apps/web/src/app/dashboard/page.tsx` (1829 строк), `apps/web/src/app/pos/page.tsx` (1372)
Grep `next/dynamic|React.lazy` — нет (есть только два `<Suspense>` вокруг `useSearchParams`, не для разбиения кода). Всё — `'use client'`, поэтому каждый маршрут тащит весь свой объём JS в первый бандл, включая framer-motion. Для PWA это раздувает hydration-стоимость и TBT.
**Почему важно:** большой клиентский бандл → дольше hydration и TTI на iPhone, выше Total Blocking Time.
**Фикс:** вынести редко-открываемые тяжёлые поддеревья (например, графики аналитики, модалки оплаты внутри `CheckDetailView`) в `next/dynamic(() => import(...), { ssr: false })`; рассмотреть деление dashboard-вкладок на динамические чанки.

### 8. [LOW] `cats.find()` внутри `.map()` по всем позициям — O(n²)
**Файл:** `apps/web/src/app/manage/menu/page.tsx:401,502`
В рендере списка позиций для каждого `item` вызывается `cats.find((c) => c.id === item.category)` — линейный поиск внутри цикла по позициям.
**Почему важно:** на малых каталогах незаметно, но это лишняя работа на каждый ре-рендер; масштабируется квадратично.
**Фикс:** один раз построить `Map<catId, cat>` (`useMemo`) и брать `catMap.get(item.category)`.

### 9. [LOW] `<img>` пользовательских фото без `loading="lazy"`/оптимизации и без `next/image`
**Файлы:** `apps/web/src/app/manage/clients/page.tsx:403` (фото клиента), QR-коды (`tablet/page.tsx:428`, `CheckDetailView.tsx:2150`, `clients/page.tsx:377`)
`grep next/image` — пусто; `loading="lazy"`/`decoding="async"` на `<img>` нет. У всех `<img>` корректно проставлен `alt` (хорошо). QR-коды — data-URL (оптимизация не нужна), но аватар клиента (`photoUrl`) — реальная сетевая картинка без lazy/ресайза.
**Почему важно:** низкий приоритет (аватар один, в детальной шторке), но при появлении фото-меню/галерей отсутствие `next/image` (ресайз, AVIF/WebP, lazy) станет ощутимым.
**Фикс:** для пользовательских изображений использовать `next/image` (или хотя бы `loading="lazy" decoding="async"` + фиксированные `width/height` против CLS). Хост `titanpos.ru` уже в `images.remotePatterns` — инфраструктура готова.

### 10. [LOW] Отсутствует `aria-label` на `<nav>` (две навигации на странице)
**Файлы:** `apps/web/src/components/BottomNav.tsx:93`; `apps/web/src/components/Sidebar.tsx:116`
Оба `<nav>` без `aria-label`. На мобильном виден один, на десктопе — sidebar, но семантически два навигационных лендмарка без различимых имён.
**Почему важно:** скринридер объявит два безымянных «navigation» лендмарка. Мелочь, но дёшево исправить. Внутри элементы уже имеют корректный `aria-current="page"` — это сделано хорошо.
**Фикс:** `aria-label="Основная навигация"` на sidebar и `aria-label="Нижняя навигация"` на bottom-nav.

### 11. [LOW] Контраст приглушённого текста на тёмном фоне у границы AA
**Файлы:** глобально, напр. `apps/web/src/app/globals.css` (`--on-surface-variant: #ccc3d8`) и многочисленные инлайны вида `rgba(204,195,216,0.4)` / `rgba(204,195,216,0.45)` (например `menu/page.tsx:396,410,435`)
Базовый `--on-surface-variant` на тёмном фоне контрастен, но варианты с `opacity 0.4-0.45` для вторичных подписей и плейсхолдеров рискуют не дотягивать до WCAG AA 4.5:1 для мелкого текста (11-13px).
**Почему важно:** слабовидящие и яркое солнце на улице у входа в клуб — читаемость подписей падает.
**Фикс:** проверить пары контраста для текста <14px; для важных подписей не опускать прозрачность ниже ~0.6 или повысить базовый тон. Violet-акцент `#8B5CF6` на тёмном фоне для текста-ссылок тоже стоит проверить (на крупном жирном — ок).

## Идеи новых фич (под мафия-клубы / антикафе)

- **Скелетоны и оптимистичный UI для кассы по слабой сети.** В клубах Wi-Fi часто перегружен; добавить оптимистичные мутации (создание чека, добавление позиции) с откатом — POS будет ощущаться мгновенным даже при лагах API.
- **Высококонтрастный «ночной/барный» режим.** Антикафе и мафия-клубы работают в полумраке; переключатель повышенного контраста + крупного шрифта помог бы кассиру в тёмном зале и улучшил доступность.
- **Полностью клавиатурный режим кассы для стационарного терминала.** Если клуб ставит ноутбук/моноблок на ресепшн — навигация по тарифам/позициям с клавиатуры (стрелки + Enter, хоткеи «оплата», «новый чек») резко ускорит обслуживание очереди на входе.
- **Lazy-галерея фото позиций меню.** Для антикафе с едой/напитками — карточки с фото; реализовать сразу на `next/image` с виртуализацией, чтобы не повторить долг по производительности.
- **Индикатор оффлайн-режима PWA + очередь действий.** Явный баннер «нет сети, действия в очереди» с автодосылкой — критично для мероприятий/выездных миникапов.

## Quick wins (<1 час)

1. Удалить `Material+Symbols+Outlined` из `@import` в `globals.css:2` — мгновенная экономия трафика и улучшение LCP (Finding 1).
2. Обернуть контейнер Toast в `aria-live="polite" role="status"` (Finding 4).
3. Добавить `aria-label` к обоим `<nav>` (Finding 10).
4. Добавить `keydown`-обработчик `Escape → onClose` в `Sheet` (частичный фикс Finding 3 — самая заметная для пользователя часть).
5. Добавить `loading="lazy" decoding="async"` + явные `width/height` к `<img>` аватара клиента (`clients/page.tsx:403`) (Finding 9).
6. Заменить `cats.find()`-в-цикле на `useMemo`-`Map` в `menu/page.tsx` (Finding 8).

## SaaS / мульти-клуб следствия для этой области

- **Размер данных непредсказуем.** Для одного клуба-эталона списки малы, поэтому отсутствие виртуализации/мемоизации не видно. При продаже разным клубам каталог меню, база клиентов и история движений склада могут быть на порядок больше — без виртуализации (Finding 6) и `next/image` для фото-меню (Finding 9) UX просядет именно у самых крупных (читай — самых ценных) подписчиков.
- **Бандл — общий для всех тарифов.** Лишний шрифт (Finding 1) и отсутствие code-splitting (Finding 7) бьют по каждому клубу при каждом холодном старте PWA. На фоне подписочной модели, где удержание зависит от «ощущения скорости», это системный, а не точечный долг.
- **Доступность как требование комплаенса/тендеров.** Если приложение начнут покупать сети/франшизы или продавать по контрактам, dialog-семантика модалок и status-сообщения (Findings 3, 4) могут стать формальным требованием. Дешевле починить базовый `Sheep`/`Toast` сейчас (один компонент → чинит все экраны), чем по месту в каждом клубе.
- **Брендирование под клуб.** При white-label важно, чтобы violet-акцент был переменной (он уже `--primary-violet`) — но контрастные пары (Finding 11) надо валидировать для любой темы клиента, а не только для текущей фиолетовой.
