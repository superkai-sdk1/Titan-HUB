# Titan HUB — Резюме аудита готовности к продакшну (Executive Summary)

> Сводка 16 специализированных отчётов о готовности Titan HUB (POS + управление для мафия-клубов и анти-кафе) к **продакшну**, **коммерции** и **подписочной модели (SaaS)** для других клубов.
> Дата: 2026-06. Прод: `titanpos.ru`, PWA на iPhone. HEAD `13aba2b`, SW v210, миграции до 047.

---

## 1. Общий вердикт

**Общая оценка готовности: 58 / 100.**

| Цель | Вердикт | Кратко |
|------|---------|--------|
| **Продакшн для ОДНОГО своего клуба** | 🟠 **GO с оговорками** | Денежное ядро крепкое (серверный пересчёт сумм, `FOR UPDATE`, идемпотентность, immutable-склад). До запуска закрыть HMAC-вебхука Platega, утечку зарплат, скидки-в-ноль, ротацию логов, graceful shutdown, фискализацию (54-ФЗ — юридически или интеграцией). |
| **Коммерческая продажа (1 клуб = 1 инстанс)** | 🟠 **CONDITIONAL GO** | Возможна как «managed-инсталляция на клиента» после P0+P1. Блокеры: фискализация (54-ФЗ), ПДн/152-ФЗ (открытый текст + бэкап в Google Drive за рубеж), отсутствие error-tracking и CI/CD. |
| **SaaS-подписка (много клубов в одной БД)** | 🔴 **NO-GO** | Приложение строго **одно-тенантное**: во всей схеме БД **ноль** колонок `tenant_id`/`club_id` (подтверждено grep'ом). Любой owner-токен видит и меняет данные всех клубов. Нет биллинга, тарифов, онбординга. Требуется ~3–4.5 мес. работы. |

**Главный вывод.** Продукт — это технически зрелое **single-venue** приложение с сильным денежным ядром и богатой доменной функциональностью, но **архитектурно не готовое к мультитенантности** и **юридически не готовое к коммерческой эксплуатации в РФ** (54-ФЗ фискализация, 152-ФЗ персональные данные). Путь к подписке проходит через row-level `tenant_id` + Postgres RLS и слой биллинга, который сейчас отсутствует полностью.

## 3. 🔴 P0 — Блокеры до первого платящего клиента

> Без этих пунктов нельзя брать деньги ни с одного клиента. Отсортированы по критичности.

1. **Однотенантность — нет изоляции арендатора** _(обл. 14, 02, 08; `packages/database/src/schema/*`, `packages/auth/src/jwt.ts:14`)_
   В схеме БД, JWT и запросах **ноль** `tenant_id`. Как только в одной БД окажутся два клуба — owner клуба A прочитает и изменит данные клуба B (включая `/system/backup` всей базы). **Для SaaS — фундаментальный блокер. До внедрения RLS — строго один клуб на инстанс/БД.**

2. **Вебхук Platega без HMAC-подписи тела** _(обл. 01; `apps/api/src/modules/platega/platega.router.ts:34-39`)_
   Тело callback'а (`status`, `payload=checkId`, `amount`) ничем не подписано — проверяется лишь статический `X-Secret` в заголовке. Утечка секрета → атакующий закрывает любой неоплаченный чек как оплаченный по СБП **с произвольной суммой**. **Подделка выручки.** Фикс: HMAC-подпись или повторная сверка через `GET /transaction/{id}` внутри вебхука + IP-allowlist.

3. **Нет фискализации (54-ФЗ / ОФД / онлайн-касса)** _(обл. 15; `pos.router.ts`, `platega.router.ts`)_
   Приём наличных и СБП формирует только внутренние «чеки» — нет интеграции с ОФД. В РФ приём денег от физлиц без онлайн-ККТ **незаконен**. Минимум до запуска — делегировать клиенту договором; правильно — интеграция (АТОЛ Онлайн / Модулькасса).

4. **Ручные скидки складываются без лимита → бесплатный товар** _(обл. 05; `apps/api/src/lib/money.ts:24-34`, `pos.router.ts:1098-1155`)_
   Кассир (`staff`) может добавить две скидки по 60% → `total=0`. Прямой канал злоупотреблений. Фикс: клампить суммарный процент скидок к 100% в `computeTotals`, потолок `max_discount_pct` в настройках, крупные скидки — под роль owner.

5. **Утечка зарплатных данных между сотрудниками** _(обл. 06; `apps/api/src/modules/salary/salary.router.ts:78`)_
   `GET /salary/estimate?staffId=<чужой_uuid>` отдаёт любому `staff` выручку и расчётную ЗП коллеги. Фикс (1 строка): для не-owner форсить `user.sub`.

6. **PIN = вектор DoS-локаута всего персонала** _(обл. 02; `apps/api/src/modules/auth/auth.router.ts:44-45,135-204`)_
   4-значный PIN сверяется со ВСЕМИ staff/owner; единственная реальная защита — глобальный счётчик (50 неудач/15 мин). Любой может намеренно загнать счётчик и заблокировать вход всему персоналу/кассе/планшетам. Фикс: вход по явному `userId` (per-account lockout), 6-значный PIN.

7. **Двойное бронирование пространства в POS** _(обл. 06; `apps/api/src/modules/pos/pos.router.ts:547`)_
   `POST /checks` создаёт арендный чек на зону без проверки занятости — два параллельных чека на один стол/VR. Фикс: частичный `UNIQUE INDEX ... WHERE status='open' AND space_id IS NOT NULL` + проверка в транзакции.

8. **Bootstrap чистой БД невозможен из деплоя** _(обл. 08; `apps/api/src/migrations/runner.ts:51-67`, `scripts/deploy.sh:42`)_
   Базовые таблицы создаёт только `drizzle-kit push`, который **не вызывается** в деплое — runner применяет лишь ALTER-ы. Новый инстанс/новый клуб поднять воспроизводимо нельзя (миграции упадут на `ALTER TABLE checks`). Блокирует disaster recovery с нуля и SaaS-онбординг. Фикс: `sql/000_baseline.sql` или `db:push` в entrypoint + smoke-тест «empty DB → up → green».

## 4. 🟠 P1 — Критично для коммерческого запуска

> Стабильность, целостность данных, прод-инфра, юридические требования РФ.

**Стабильность и прод-инфра**
- **Нет graceful shutdown** — каждый деплой рвёт in-flight POS-транзакции, бэкап/restore и SSE _(обл. 09; `apps/api/src/index.ts:28-35`)_.
- **Health-check тривиален** — `{ok:true}` даже при мёртвом PG/Redis; nginx шлёт трафик на нерабочий API _(обл. 09, 15; `app.ts:96-97`)_.
- **Restore БД не транзакционен** (`ON_ERROR_STOP=0`) и не блокирует приём денег → битая БД + параллельные оплаты _(обл. 09, 15; `lib/backup.ts:112-117`)_.
- **Нет ротации Docker-логов** → переполнение 4-ГБ диска → отказ Postgres/nginx → 502 _(обл. 15; `docker-compose.yml`)_.
- **Нет error-tracking (Sentry) и CI/CD** — упавший платёж уходит в stdout; код собирается на проде (CPU-пик, разрыв SSH) _(обл. 15)_.
- **API-контейнер под root** с правом DROP БД и доступом к rclone-токенам Google Drive _(обл. 15; `apps/api/Dockerfile`)_.
- **Публичный MinIO-bucket** (`Principal:*`) — анонимное чтение любого файла по прямой ссылке _(обл. 09; `upload.router.ts:88-92`)_.
- **AI text-to-SQL без cost-guard и rate-limit на LLM** — украденный/staff-токен жжёт токены бесконтрольно _(обл. 09, 02; `ai.router.ts:222-268`)_.
- **Boot-валидация проверяет 2 секрета из ~15** — Platega/VAPID/WebAuthn отказывают молча, сервис «healthy» _(обл. 15; `index.ts:9-22`)_.

**Целостность денег и данных**
- **COGS периода и маржа считаются по текущему WAC**, а не по себестоимости на момент продажи — P&L систематически искажён, аудит невозможен (поле `stock_movements.unit_cost` уже пишется, но не читается) _(обл. 04; `analytics.router.ts:137,882`)_.
- **WAC портится при приходе на отрицательный остаток** после оверселла → отрицательная себестоимость отравляет всю маржу _(обл. 04; `ledger.ts:69`)_.
- **Баланс клиента без двойной записи / инварианта целостности** — нет сверки `balance == SUM(проводок)` _(обл. 07; `clients.router.ts:438`)_.
- **Корректировка баланса с экрана «Клиенты» без idempotencyKey** — двойной клик задваивает депозит/долг _(обл. 07; `manage/clients/page.tsx:153,172`)_.
- **Ночные мероприятия (через полночь) ломают проверку пересечений** — лексикографическое сравнение времени строкой _(обл. 06; `events.router.ts:107`)_.
- **Гранулярные permissions хранятся, но нигде не энфорсятся** — ложное чувство безопасности _(обл. 06; `middleware/auth.ts:64`)_.

**Юридическое (РФ)**
- **152-ФЗ: ПДн без согласия/шифрования/аудита/экспорта**, бэкап с телефонами и ДР уезжает за рубеж (Google Drive) _(обл. 07, 15; `schema/profiles.ts:41-45`, `scripts/backup-db.sh`)_. Фикс: согласие при создании клиента, offsite только в РФ-облако, шифрование дампов.

**Безопасность аутентификации**
- **JWT 7–30д без инвалидации** при смене роли/пароля/увольнении; права уволенного живут до exp _(обл. 02; `auth.store.ts`, `middleware/auth.ts`)_.
- **Отзыв токена fail-open при недоступности Redis** — отозванные токены снова валидны _(обл. 02, 09; `middleware/auth.ts:53-56`)_.
- **Энумерация ников + ветка plaintext-паролей** _(обл. 02; `auth.router.ts:228,232-237`)_.

## 5. 🟡 P2 — Важно для качества и масштаба

**Надёжность фронтенда (реальные прод-дефекты на iPhone)**
- **SSE-уведомления умирают после первого блипа сети** (одноразовый тикет, опора на авто-реконнект → 401) — кассир молча перестаёт получать заказы _(обл. 10; `lib/sse.ts:8`)_.
- **Обновление Service Worker роняет активного кассира** на `ChunkLoadError` без graceful-reload _(обл. 10; `public/sw.js:15-33`)_.
- **Нет route-level error boundaries** — любая ошибка рендера сбрасывает весь экран и открытый чек _(обл. 10; `providers.tsx`)_.
- **Касса (CheckDetailView) не подписана на SSE** — лаг до 10с, усиливает окно потерянного обновления _(обл. 03; `CheckDetailView.tsx:213-217`)_.
- **Нет оптимистической блокировки чека** — потерянные обновления при двух официантах/планшет+касса _(обл. 03; `checks.ts:29`)_.
- **Планшет без оффлайн-очереди** — заказ молча теряется при потере Wi-Fi _(обл. 03; `tablet/order/page.tsx:140-161`)_.

**Производительность и UX**
- Render-blocking `@import` шрифтов + полный неиспользуемый Material Symbols (сотни КБ впустую) _(обл. 11, 13; `globals.css:2`)_.
- Нулевое code-splitting при компонентах-гигантах (CheckDetailView 2406 строк) — медленный первый запуск кассы по 4G _(обл. 10, 13)_.
- Sheet (базовая модалка всех форм) без `role=dialog`/Escape/focus-trap; Toast без `aria-live` _(обл. 13; `DesignSystem.tsx:118-446`)_.

**Мобильные дефекты (iPhone PWA — основное устройство)**
- Инпуты 15px → авто-зум iOS на каждой форме _(обл. 11, 12; `DesignSystem.tsx:13`)_.
- Стекло без `-webkit-backdrop-filter` не размывается в Safari _(обл. 11; `customers/page.tsx:84`)_.
- Клавиатура перекрывает композер в TITAN AI _(обл. 12; `TitanAiChat.tsx:166-191`)_.
- Нижняя нав игнорирует home-indicator; заблокирован pinch-zoom (a11y/сторы) _(обл. 12; `BottomNav.tsx`, `layout.tsx:44-45`)_.

**Дизайн-долг (важно для white-label SaaS)**
- Дизайн-система определена, но почти не внедрена: 843 хардкода `borderRadius`, бренд-градиент скопирован 44 раза, токены `var(--r-*)` — 0 обращений. Любая кастомизация под клуб = ручная правка сотен мест _(обл. 11; `globals.css`)_.

## 6. 🟢 P3 — Новые фичи и рост

**Домейн-фичи для мафия-клубов / анти-кафе (продают подписку)**
- **Онлайн-бронирование зон** с виджетом и предоплатой через Platega + календарь занятости (фича №1 для продажи) _(обл. 16, 08; БД готова под `EXCLUDE USING gist`)_.
- **Публичный QR-самозаказ «со своего телефона»** поверх готового `pending_orders` — рост среднего чека без планшетов в каждой кабинке _(обл. 16; `tablet/order`)_.
- **Рецептуры/техкарты (BOM)** — продажа коктейля/кальяна списывает ингредиенты, реальная себестоимость напитков _(обл. 04)_.
- **Учёт по весу/объёму** (табак в граммах, сиропы в мл) — критично для бара/кальянной _(обл. 04)_.
- **Split bill** — деление счёта на компанию/по гостям (базовый сценарий, сейчас считается вне системы) _(обл. 03, 16)_.
- **Пакеты и капы тарификации времени** («3 часа = N₽», безлимит-вечер, бесплатные первые 15 мин) _(обл. 16; `money.ts:45`)_.
- **Абонементы/клубные карты** и **депозит-пакеты** (внеси 5000 — на счёт 6000) — повторяющаяся выручка _(обл. 05, 07)_.
- **Триггерный CRM**: авто-поздравление с ДР (+бонус) и реактивация спящих — сегменты уже считаются _(обл. 16; `analytics.router.ts:824`)_.
- **Расписание и рейтинг ведущих**, сбор оценок гостя, лист ожидания на пиковые вечера, визуальная карта зала _(обл. 16, 06)_.

**Монетизация и упаковка SaaS**
- Тарифы подписки (Start / Pro / Network) + биллинг через ЮKassa/CloudPayments + фич-гейты (число зон, AI-лимиты, бронь как Pro) _(обл. 14, 16)_.
- Тема под клуб (white-label акцент) — почти бесплатно после консолидации токенов, апсейл верхнего тарифа _(обл. 11)_.
- Сеть клубов под одним владельцем: иерархия tenant → филиалы, сводная аналитика _(обл. 14)_.

## 7. ⚡ Быстрые победы (quick wins)

Высокий эффект при усилии ≤ ~30 мин — взять до и параллельно с P0/P1:

**Деньги и безопасность**
- Форсить `user.sub` для не-owner в `salary.router.ts:78` — закрывает утечку зарплат **(1 строка)**.
- Добавить `idempotencyKey: crypto.randomUUID()` в `adjBal.mutate` (`manage/clients/page.tsx:172`) — убирает двойное списание баланса.
- Исключить `/api/platega/webhook` из rate-limit (`rateLimit.ts:32-35`) — callback'и не ловят 429.
- Писать `idempotencyKey:'platega:'+transactionId` в `transactions.insert` — БД-защита от задвоения (индекс из 045 уже есть).
- Единый 401 на `/login/password` вместо 404 — устранить энумерацию ников.
- Проверять `deletedAt` и актуальную роль в `requireAuth` — мгновенно гасит токены уволенных.

**Инфра**
- Ротация Docker-логов: `x-logging` anchor `max-size:10m max-file:3` на все сервисы — убирает класс отказов по диску.
- Graceful shutdown в `index.ts` (~15 строк) — конец обрывов запросов/SSE при деплое.
- `/health/ready` с `SELECT 1` + Redis PING.
- `USER node` в `apps/api/Dockerfile` — снять root с рантайма.
- `ON_ERROR_STOP=1 --single-transaction` в restore — атомарное восстановление.
- Расширить `assertEnv` (Platega/VAPID/WebAuthn≠localhost) — fail-fast вместо тихого отказа.
- Синхронизировать `.env.example` с реальными ключами.

**Фронтенд / UI / a11y**
- Подписать `CheckDetailView` на SSE — убирает 10с лаг кассы.
- `input/textarea/select { font-size: max(16px,1em) }` в `globals.css` — снимает авто-зум iOS на всех формах.
- Парный `WebkitBackdropFilter` в ~12 местах — чинит стекло на iPhone.
- `app/error.tsx` + `app/pos/error.tsx` с `reset()` — изоляция ошибок без полной перезагрузки.

## 8. Дорожная карта к SaaS

```
Фаза 0           Фаза 1                Фаза 2              Фаза 3
Стабилизация  →  Мультитенантность  →  Коммерческий    →  Рост
(P0 безопас.     + биллинг (RLS)       запуск             (домейн-фичи,
 + инфра)                              (54-ФЗ/152-ФЗ)      монетизация)
~3–5 нед.        ~3–4.5 мес.           ~3–6 нед.           непрерывно
```

### Фаза 0 — Стабилизация (одно-клубный прод) `~3–5 нед.`
Сделать своего клиента/инстанс надёжным и безопасным.
1. P0-безопасность: HMAC Platega (или re-fetch), скидки-в-ноль, утечка зарплат, PIN per-account, двойная бронь зоны.
2. P1-инфра: graceful shutdown, `/health/ready`, ротация логов, error-tracking (Sentry), `USER node`, расширенный `assertEnv`, атомарный restore + maintenance-флаг.
3. Целостность денег: COGS/маржа по `unit_cost`, фикс WAC на оверселле, инвариант баланса (cron-сверка).
4. Все quick wins выше.
5. **Bootstrap пустой БД из миграций** (`000_baseline.sql`) + smoke-тест — необходимое условие любого онбординга.

### Фаза 1 — Мультитенантность + биллинг `~3–4.5 мес.`
Фундамент подписки. Без этого второго клиента в общую БД пускать нельзя.
1. Таблица `tenants` + `tenant_id NOT NULL` во все доменные таблицы; составные уникальности `(tenant_id, nickname)`, `(tenant_id, code)`, `(tenant_id, key)` для `app_settings`.
2. Клейм `tid` в JWT → `ctx.tenantId` → **Postgres RLS** (`SET LOCAL app.tenant_id`) как защита в самой БД от забытого WHERE.
3. Изолировать опасные каналы: AI text-to-SQL под RLS-ролью, кэши с ключом `tenant`, Redis-префиксы `t:{tid}:`, backup/restore пер-тенант.
4. Слой биллинга: `plans` / `subscriptions` (trialing/active/past_due/canceled) / `invoices`; middleware-гейт по статусу; рекуррентная оплата (ЮKassa/CloudPayments); разделить эквайринг арендатора (деньги гостей) и биллинг платформы.
5. Онбординг: `POST /signup` → tenant + owner + сид справочников; setup-wizard в вебе с пресетами «анти-кафе»/«мафия-клуб».

### Фаза 2 — Коммерческий запуск `~3–6 нед.`
Юридическая и операционная готовность продавать.
1. **Фискализация 54-ФЗ** (АТОЛ Онлайн / Модулькасса) — провайдер-абстракция + флаг на клуб.
2. **152-ФЗ**: согласие на ПДн, экспорт/удаление данных субъекта, шифрование дампов, offsite только в РФ-облако.
3. CI/CD (GitHub Actions: lint/type-check/build/тесты → образы в GHCR → на проде только `pull`).
4. Status-страница, ops-алерты в Telegram bot-admin, PITR-бэкапы + авто-тест restore.

### Фаза 3 — Рост `непрерывно`
Домейн-фичи как драйверы конверсии и удержания.
1. Онлайн-бронирование зон + публичный QR-самозаказ (фичи №1 продажи).
2. Рецептуры/BOM + весовой учёт (реальная себестоимость бара).
3. Пакеты/капы тарификации, абонементы, триггерный CRM, рейтинг ведущих, лист ожидания.
4. White-label тема под клуб, тарифные планы по объёму, реферальная программа между клубами.
