# Провижининг новой БД клуба (database-per-club)

Этот каталог — фундамент Фазы 1 (мультитенантность). **Пока не подключён к рантайму** —
существующий одно-клубный прод работает как раньше. См. общий план
`docs/audit/PLAN-PHASE1-TENANCY.md`.

## Зачем

Базовые таблицы приложения исторически создавались `drizzle-kit push`, а НЕ миграциями
(`apps/api/src/migrations/sql/*` только `ALTER`/добавляют). Поэтому **с нуля** поднять
БД нового клуба из миграций нельзя (это P0-блокер #7 аудита: новый клуб и disaster
recovery невозможны). `baseline.sql` закрывает это.

## Что здесь

- **`baseline.sql`** — полный снимок текущей схемы прод-БД (`pg_dump --schema-only`,
  Postgres 16). Создаёт ВСЕ типы/таблицы/индексы/constraints приложения на ПУСТОЙ БД.
  Это «squash» всех миграций 001..049 в одно состояние на момент снятия снимка.

## Как провижинить новый клуб (целевая процедура, реализуется в Фазе 1)

```
1. CREATE DATABASE club_<slug>;                  -- через админ-коннект Postgres
2. psql club_<slug> < baseline.sql               -- полная схема приложения
3. На club_<slug>: создать _migrations и пометить ВСЕ уже сквошнутые миграции
   (001..049) применёнными, чтобы раннер их не прогонял повторно:
     CREATE TABLE _migrations (id text PRIMARY KEY, applied_at timestamptz DEFAULT now());
     INSERT INTO _migrations (id) SELECT unnest(ARRAY['001_*.sql', ..., '049_*.sql']);
   (Список = имена файлов из apps/api/src/migrations/sql/ на момент снятия baseline.)
4. Будущие миграции (050+) применяются раннером штатно — и на этом клубе, и на всех.
5. Сидинг: типы вечеров (evening_types), дефолтные app_settings, bootstrap-владелец.
6. Запись клуба в control-plane (clubs/club_modules/subscriptions).
```

## Важно

- `baseline.sql` прогоняется через **psql** (как restore в `lib/backup.ts`), а НЕ через
  drizzle-раннер: дамп содержит psql-метакоманды (`\restrict`) и `SET`-директивы.
- **НЕ кладите `baseline.sql` в `apps/api/src/migrations/sql/`** — тот каталог
  авто-применяется на старте на СУЩЕСТВУЮЩЕЙ прод-БД; baseline там не нужен и опасен.
- **Пересоздание baseline** при изменении схемы: снять новый снимок
  `pg_dump --schema-only` с прода (или с эталонной БД после прогона всех миграций) и
  обновить список «уже применённых» в шаге 3. Делать редко (squash-точки).
